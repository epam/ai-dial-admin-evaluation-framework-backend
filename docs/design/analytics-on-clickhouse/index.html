Analytics on ClickHouse

A research-backed migration guide: what the analytics Postgres actually does today, the three ways to move it to ClickHouse, and a step-by-step plan for the recommended path — including the data backfill and rollback.

Verdict

The analytics store is almost ideally ClickHouse-shaped, and the codebase already has the seam to swap it. All four tables are strictly append-only (batched INSERT … ON CONFLICT DO NOTHING, zero runtime UPDATE/DELETE, no locks, no cross-table transactions), versioned by computation_id instead of mutation, and read mostly through aggregates and per-run scans. Every analytics repository and query-DSL resolver is already gated on datasource.analytics.vendor=POSTGRES, and Flyway already resolves db/migration/analytics/${vendor}.

Recommended path: full cutover behind the existing vendor seam (Path A below), executed with a parity-verification phase in staging and a one-time backfill via ClickHouse's postgresql() table function. CDC replication (Path B) is ruled out as a target architecture because the evaluation pipeline itself reads Phase-1 rows immediately after writing them — replication lag would sit inside the job pipeline, not just behind dashboards.

Part I

Current state: how analytics storage actually works

1.1 The four tables

Migrations live in src/main/resources/db/migration/analytics/POSTGRES/ (V1.1–V1.18, V1.9 never existed). No foreign keys, no triggers, no sequences, no CHECK constraints, no partitions — the schema was deliberately kept vendor-neutral: UUIDs as VARCHAR(36), all timestamps as epoch-ms BIGINT.

TableRoleGrain / cardinalityJSONB columnsNatural unique key (the ON CONFLICT target)
test_case_run_results Phase-1 raw execution facts (largest table) ≈ cases × repetitions × requests × turns per run test_case_data, request_body, response_body, extracted_columns, extraction_warnings, log_details (run_id, test_case_id, run_index, request_index, turn_index, created_at_ms)
test_case_eval_summaries Phase-2 denormalized read surface — 1 row per result row per computation, even at zero metrics result rows × computations test_case_data, extracted_columns, metric_values, metric_infos, extraction_warnings same + computation_id
run_metric_snapshots TSMD definition freeze per computation single digits per computation config_bindings, input_bindings, output_schema (computation_id, tsmd_id)
metric_score_result Phase-3 aggregated scores (AVG/P10/P90/MIN/MAX/overall); documented as regenerable statistics × metric fields per (run, computation) — (run_id, computation_id, metric_score_name, metric_name)

The two big tables share the composite PK (created_at_ms, id) — created_at_ms is the run's creation timestamp (identical for every row of a run), chosen explicitly as a future partition key. That design decision transfers 1:1 to a ClickHouse partition key.

1.2 The write path — everything is an idempotent batched insert

  • No runtime UPDATE, DELETE, upsert, MERGE, FOR UPDATE, or advisory lock exists anywhere on the analytics side (verified by grep across data/db/analytics and query/). The only non-INSERT DML ever executed is one-off migration backfill (V1.8, V1.12).
  • All four repositories write via per-row dsl.insertInto(…).onConflict(<natural key>).doNothing() collected into one dsl.batch(queries).execute() — one JDBC round trip per flush, boosted by reWriteBatchedInserts=true on the analytics JDBC URL only.
  • Phase 1: PostgresResultBatchWriter flushes every 100 rows (test-suite-run.execution.result-batch-size), one TransactionTemplate tx per flush. Phase 2: eval summaries chunked at ≤10,000 (analytics.eval-summaries.batch.max-items), one tx per chunk. CSV import: one long tx over 1,000-row chunks (≤100k rows).
  • Recomputation never updates. Each re-evaluation mints a new computation_id; "latest" is resolved at query time by ORDER BY computed_at_ms DESC LIMIT 1 over eval summaries (covering index idx_eval_summaries_run_computed_at). No is_latest flag, no DISTINCT ON, no window functions.
  • Everything runs at READ COMMITTED with no isolation overrides. The famous REPEATABLE READ + SQLSTATE 40001 retry (suite-run snapshot phase) is entirely meta-DB-side and is untouched by this migration.
  • No cross-DB atomicity exists or is expected. Meta commits first, then an afterCommit hook writes analytics with markRunFailed compensation. Orphaned analytics rows after a run delete are accepted by design (nothing deletes analytics rows).
  • Analytics writes ignore TransactionTimestampContext (the aspect skips the analytics tx manager) — all timestamps are passed explicitly. Nothing time-context-magical to port.

1.5 Seams that already exist

  • @ConditionalOnProperty(name = "datasource.analytics.vendor", havingValue = "POSTGRES") on all 4 analytics repositories and both analytics query-DSL entity resolvers — the swap point is designed in.
  • Flyway location is already vendor-keyed: classpath:db/migration/analytics/${datasource.analytics.vendor}.
  • JsonPathAccessor is an interface with a single Postgres impl — the intended JSON porting seam. (Gap: PostgresJsonPathAccessor is an unguarded @Component; it needs the vendor condition added.)
  • Repositories are interfaces (TestCaseRunResultRepository etc.); services depend on the interface, not the Postgres class.
  • DatasourceValidationConfiguration currently hard-rejects any non-POSTGRES analytics vendor — the one guard to relax.
Part II

The fork: three paths

Path A · Recommended

Full cutover behind the vendor seam

Implement vendor=CLICKHOUSE: CH repositories, JSON accessor, entity resolvers, no-op tx manager, CH Flyway dir. One-time backfill, flip the property, keep Postgres warm for rollback.

  • ＋ One storage engine long-term; no sync machinery; smallest steady-state ops surface
  • ＋ Uses seams the codebase already has; work is additive, not invasive
  • － Whole read+write surface must be ported and verified before the flip
  • － Needs a write-quiesce window for the backfill (natural: analytics is only written during active runs/imports)
Path B

CDC sidecar (PeerDB), Postgres stays source of truth

Keep all writes on Postgres; replicate to ClickHouse via PeerDB/ClickPipes; route expensive client reads (aggregate, DSL, export, comparison) to CH.

  • ＋ Zero write-path change; Postgres ON CONFLICT dedup preserved; instant rollback (stop routing)
  • － Killer: Phase 2 pages test_case_run_results seconds after Phase 1 writes them, and Phase 3 reads Phase-2 rows — replication lag sits inside the job pipeline, so internal reads must stay on PG. You only offload client reads, yet still pay the full CH read-port cost.
  • － Permanent dual infra + lag monitoring + two schemas to migrate forever
Path C

Dual-write bridge, then decommission

Application writes both stores for a verification window; reads flip to CH once parity checks pass; then drop the PG leg.

  • ＋ Best production-data verification; no bulk backfill for new rows (old rows still need one)
  • － Longest project; a temporary dual-writer component you'll throw away; failure-mode matrix (one leg fails) needs design even though writes are idempotent
  • － Converges to Path A anyway — it's Path A plus a costlier verification phase
Why Path A wins here The workload has none of the properties that usually force B or C: no in-place mutation (append-only + computation_id versioning), no transactional invariants on analytics (idempotent batches, compensation already in place, orphans tolerated), and a hard read-your-writes requirement inside the pipeline that async replication can't meet. Verification value of C can be captured cheaply by replaying real production runs against a CH staging instance (§7) instead of running dual writes in prod. If zero write downtime ever becomes a hard requirement, use PeerDB once, as a backfill tool for Path A's cutover — not as an architecture.
Part III

How-to: the cutover, step by step

Everything below is additive until step 8 — Postgres remains the default vendor throughout development, and each step is testable in isolation. The meta database is untouched.

0

Prerequisites & versions

  • ClickHouse ≥ 25.3 (native JSON type GA; lightweight UPDATE exists from 25.7 but this workload never needs it). Prefer the current LTS.
  • jOOQ ≥ 3.20 — the CLICKHOUSE dialect ships in the open-source edition (experimental). The project's codegen classpath already pins jooq-codegen:3.21.6 (build.gradle:30); confirm the Spring Boot 4.1.1-managed runtime org.jooq:jooq resolves to ≥ 3.20 (./gradlew dependencies --configuration runtimeClasspath | grep org.jooq).
  • Dependencies to add: com.clickhouse:clickhouse-jdbc (current V2 driver) and org.flywaydb:flyway-database-clickhouse (community plugin).
  • Treat the jOOQ CH dialect as experimental: every ported query shape gets a functional test (§7); anything the dialect renders wrong drops to DSL.field(sql, …)/plain SQL inside the CH repository — which is exactly what the repository layer exists for.

Wiring: datasource, transaction manager, Flyway, validation

Mirror AnalyticsPostgresConfiguration with a CH twin; everything keeps the same bean names so no consumer changes.

  • DatasourceValidationConfiguration — allow CLICKHOUSE for analytics (meta stays POSTGRES-only). The same-host/same-db collision check becomes a no-op across engines.
  • AnalyticsClickHouseConfiguration (@ConditionalOnProperty("datasource.analytics.vendor")="CLICKHOUSE"): HikariCP over the CH JDBC driver, URL like jdbc:ch://host:8123/evaluation_analytics?compress=1. Note the Azure AD token path (DynamicPasswordHikariDataSource) is Postgres-flexible-server-specific — CH auth is its own config block.
  • analyticsTransactionManager — ClickHouse has no usable transactions, and the existing DataSourceTransactionManager would call setAutoCommit(false) and fail. Provide a resourceless no-op PlatformTransactionManager under the same bean name so every existing @Transactional("analyticsTransactionManager") and TransactionTemplate still binds and simply demarcates nothing. (Semantics implications in §6 — they're all acceptable for this workload.)
  • analyticsDsl — same shape, SQLDialect.CLICKHOUSE. Keep TransactionAwareDataSourceProxy (harmless with a no-op manager) or drop it; keep the exception-translator listener.
  • Flyway — AnalyticsFlywayConfiguration already resolves db/migration/analytics/CLICKHOUSE from the vendor property; it just needs the CH plugin on the classpath. Remember CH DDL auto-commits statement-by-statement: keep migrations single-purpose, and know a failed migration does not roll back (repair = fix forward).
  • Health — AnalyticsDatabaseHealthIndicator runs a plain probe over analyticsRawJdbcTemplate; SELECT 1 works on CH unchanged.
  • Config & docs — new clickhouse.analytics.datasource.* properties (URL, user, password, database), rows in docs/configuration.md (all six columns, per project rule), and reWriteBatchedInserts documented as Postgres-only.

ClickHouse schema — one consolidated init migration

Do not port 17 incremental migrations; write V1.1__Init.sql expressing the current schema. Three deliberate mappings:

  • Engine = ReplacingMergeTree, ORDER BY = the natural unique key. This is the ON CONFLICT DO NOTHING replacement: duplicate deliveries (double flush, retried import) collapse to one row at merge time, and reads that must be exact use FINAL (§3). Rows are immutable, so "replace" and "do nothing" are equivalent outcomes.
  • PARTITION BY month of created_at_ms — the PG schema was already designed around created_at_ms as the pruning key (composite PK, equality pin on every read). Same idea, now enforced by the engine, and it makes retention (TTL or DROP PARTITION) free later.
  • JSONB → String first, native JSON as a follow-up. Conservative default: JSON payloads round-trip byte-exactly (the codebase is explicit about preserving {"key": null} entries in metric_values — see the NON_NULL serializer rule in AGENTS.md), and every filter/aggregate works via JSONExtract over String at excellent speed. Once cut over, A/B the native JSON type on metric_values/extracted_columns/test_case_data for columnar subcolumn reads — but verify explicit-null round-tripping before switching, and note Nullable(JSON) is not supported (relevant to request_body/response_body/metric_infos/log_details, which are nullable and projection-only — keep those Nullable(String) permanently).
-- V1.1__Init.sql (excerpt: the two big tables; snapshots + scores follow the same pattern)

  • IDs stay String(36), not CH UUID, mirroring the PG VARCHAR(36) decision — but see the type-inference gotcha in §5.

Repositories & the write path

Add ClickHouse*Repository implementations of the four existing interfaces, gated on vendor=CLICKHOUSE. The *RecordMapper components are reusable as-is if you run a second jOOQ codegen pass against the CH schema (a generateJooqClickhouse task using Testcontainers + org.jooq.meta.clickhouse.ClickHouseDatabase, output to a sibling package); alternatively hand-map with Record-by-name access — the tables are only four.

Writes

  • Drop onConflict(…).doNothing() — plain INSERT; the engine dedups. Prefer bind-value batching of a single statement (one INSERT … VALUES with addBatch, which the CH driver turns into one efficient insert) over jOOQ's multi-statement dsl.batch(queries).
  • All rows of one flush share created_at_ms ⇒ one partition ⇒ each batch is atomic (single-part insert), preserving today's per-flush atomicity without transactions.
  • ClickHouse prefers fewer, larger inserts: raise test-suite-run.execution.result-batch-size (100 → 1,000–5,000) and/or set async_insert=1&wait_for_async_insert=1 on the JDBC URL so small flushes coalesce server-side. Keep wait_for_async_insert=1 — the pipeline's read-your-writes depends on the ack.
  • On a replicated/SharedMergeTree deployment, exact retried batches are additionally dropped by insert-block dedup; ReplacingMergeTree covers partial overlaps either way.

Reads

  • Duplicates exist only until parts merge, and only after a retry — but counts/aggregates must be exact, so run reads with FINAL. Simplest global switch: set final = 1 (plus do_not_merge_across_partitions_select_final = 1) in the CH user profile of the app's read user — zero query changes, applies query-level FINAL to every MergeTree read. Per-run data volumes make FINAL cost negligible.
  • Keyset pagination ports verbatim: CH compares tuples lexicographically, so (created_at_ms, id) < (?, ?) + ORDER BY created_at_ms DESC, id DESC LIMIT size+1 works unchanged (no B-tree behind it, but every such read is already pinned to one run's key range).
  • The projection tiers (list/export/export+bodies/detail) port as-is and matter more on CH: selecting fewer columns is the columnar win. The LEFT JOIN to results for bodies is a per-run join — fine.
  • Run comparison: keep the DISTINCT-probe + LEFT JOIN shape; replace FILTER (WHERE …) with countIf/avgIf if jOOQ's CASE emulation proves awkward.

JSON access seam

Implement ClickHouseJsonPathAccessor next to the Postgres one (and add the missing @ConditionalOnProperty guard to PostgresJsonPathAccessor — it's currently an unguarded @Component):

-- Postgres today                          → ClickHouse (String columns + JSONExtract)
col ->> :key                                JSONExtract(col, {key}, 'Nullable(String)')
col -> :key                                 JSONExtractRaw(col, {key})
(col -> :k1 ->> :k2)::numeric               JSONExtract(col, {k1}, {k2}, 'Nullable(Float64)')
  • Use the 'Nullable(T)' return-type form, not JSONExtractString/JSONExtractFloat — the latter return ''/0 for missing keys, which would silently corrupt null vs absent semantics that the aggregate endpoint's count() depends on.
  • Render path components as inlined, escaped string literals (DSL.inline(...)) rather than bind params — sidesteps any constant-argument requirements in the JSON functions, and CH gains nothing from bind-parameter plan reuse. Path components are already validated upstream; inlining via jOOQ's escaping keeps this injection-safe.
  • Numbers become Float64 instead of PG numeric/BigDecimal. Metric values are doubles end-to-end in Java, so this is faithful — but expect last-ulp differences in aggregates; comparison tests should assert with an epsilon.

Testing strategy

  • @ClickHouseFunctionalTests mirroring @PostgresFunctionalTests: Testcontainers clickhouse module for analytics + the existing PG container for meta (the dual-datasource split makes this trivial). Run the analytics-touching functional suites (results, eval summaries, snapshots, scores, export, comparison, query DSL) against both vendors in the CI matrix.
  • Fixture helpers: extend AnalyticsTestDataHelper with a CH-backed implementation behind the same interface — test classes stay unchanged.
  • Function-parity fixtures: golden-value tests for quantileExactInclusive vs percentile_cont, arrayAUC vs roc_auc_score (including ties and single-class inputs — the PG function returns NULL when a class is absent; confirm CH matches or wrap with nullIf), and the null-polarity rewrites (build a truth table: null/true/false operand × nc/ne/not).
  • Production-replay parity (the cheap version of Path C): stand up CH in staging, backfill a copy of prod analytics (§8 mechanics), and diff REST/DSL responses (list, aggregate, export CSV, comparison, metric scores) between vendors for a sample of real runs. This is the gate for cutover.

Data migration runbook

Analytics is only written while a run/import is active — draining runs is a natural quiesce, so the backfill needs no CDC. Use ClickHouse's built-in postgresql() table function, pulling from the CH side:

  1. Provision ClickHouse; deploy the app with vendor=CLICKHOUSE in staging first so Flyway creates the schema and the full test gate (§7) passes.
  2. Quiesce prod writes: block new suite runs and CSV imports (maintenance flag), wait for RUNNING runs to reach a terminal state. Reads can stay up.
  3. Backfill each table (no FK ordering constraints exist): 
    INSERT INTO test_case_run_results
SELECT id, test_suite_run_id, test_suite_id, test_case_id, test_case_name,
       run_index, request_index, total_requests, turn_index, total_turns,
       test_case_data, request_body, response_body, response_status_code,
       execution_status, exec_started_at_ms, exec_completed_at_ms,
       exec_duration_ms, retry_count, log_details, trace_id,
       extracted_columns, extraction_warnings, created_at_ms
FROM postgresql('pg-host:5432', 'evaluation_analytics_db',
                'test_case_run_results', 'user', 'pass', 'public');
-- JSONB arrives as String — no cast needed with the String-column schema.
-- For very large tables, chunk with WHERE created_at_ms ranges.
    For terabyte-scale or a strict zero-write-downtime requirement, swap this step for a one-shot PeerDB mirror (open source, self-hostable; parallel snapshotting) — same target schema, same verification.
    Implemented in-app This step (and the count verification below) now ships as ClickHouseAnalyticsBackfillMigration — a repeatable Flyway Java migration, so the Postgres credentials come from application properties (clickhouse.analytics.backfill.*) instead of being hardcoded in a SQL script. Set clickhouse.analytics.backfill.enabled=true for the cutover deploy; re-runs are idempotent (ReplacingMergeTree dedup). See docs/patterns/clickhouse-analytics.md § "Data backfill from Postgres".
  4. Verify: per-table count(); per-run counts (GROUP BY test_suite_run_id) diffed between engines; checksum-style probes (sum(exec_duration_ms), sum(cityHash64(id)) vs a PG equivalent); API-level parity on sampled runs (§7's harness).
  5. Cut over: flip datasource.analytics.vendor=CLICKHOUSE + the CH datasource properties, deploy, re-enable runs. Execute one real suite run end-to-end (Phase 1→2→3, export, comparison) as the smoke test.
  6. Keep Postgres analytics up, read-only, for the rollback window (2–4 weeks).
9

Rollback & post-cutover wins

Rollback

Append-only data makes rollback mechanical: flip the vendor property back, then copy rows created during the CH period back to PG — they're exactly the rows whose test_suite_run_id is absent in PG (or filter on created_at_ms > cutover, since it's the run-creation timestamp). Postgres ON CONFLICT DO NOTHING makes the reverse copy idempotent too.

What you gain once stable

  • Retention for free: today nothing ever deletes analytics rows (orphans accumulate by design). Add TTL fromUnixTimestamp64Milli(created_at_ms) + INTERVAL N MONTH or scheduled DROP PARTITION — the retention story PG never had without painful bulk deletes.
  • Compression: the JSON-heavy payloads (request/response bodies, metric maps) typically compress an order of magnitude better in columnar parts than in TOAST.
  • Aggregate headroom: the aggregate endpoint, Phase-3 statistics, and run comparison move from row-store JSONB scans to columnar scans; cross-run/suite-level dashboards (currently absent, likely requested next) become cheap.
  • No more index-swap migrations: the V1.13/V1.17-style unique-index rebuilds with exclusive-lock warnings disappear; widening the dedup key is an ORDER BY change on a new table + INSERT SELECT.
  • Native JSON follow-up: once round-trip fidelity (explicit nulls) is verified on your payloads, migrate metric_values/extracted_columns/test_case_data to the GA JSON type for typed subcolumn pruning on metric filters.
