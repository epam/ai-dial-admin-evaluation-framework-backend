Structured Query Model — v8

A purpose-built top-level JSON query model with borrowed sub-grammars, providing a single grammar for filtering, sorting, pagination, projection, and aggregation across all listable entities (both meta and analytics). Clients send a structured query object (never SQL); the server validates it against a per-entity allowlist and translates it to parameterized SQL. How the translation is implemented (query-building library, etc.) is out of scope for this spec — this document defines the wire contract and the validation/translation semantics only.

Each top-level section is independently bounded so it can be allowlisted per entity, and the section structure maps onto the scan → filter → group_by → having → sort → page pipeline (with aggregate functions appearing as output columns in select).

0. Problem statement

The legacy query DSL — exposed across list endpoints as filter=, sort=, page, size, cursor query parameters — grew organically per capability and hit several structural limits. This model exists to resolve them. The numbered problems below are referenced throughout the spec (e.g. "#3").

  1. URL length cap. Non-trivial filter sets bump against typical proxy/server URL limits (~8 KB), making complex client queries (e.g. dashboards with many active facets) silently truncated or rejected.
  2. No boolean composition. The legacy DSL supports only an implicit AND of flat predicates. OR, NOT, and nested groups — (A AND B) OR (C AND D) — cannot be expressed at all, forcing clients to issue multiple requests and merge results.
  3. Spotty property coverage. Each entity exposes a hand-picked allowlist of filterable/sortable fields. Many DTO fields (especially in analytics responses) are not queryable even when the underlying column would support it, and adding a property today requires a code change per entity.
  4. Two incompatible pagination models. The meta layer uses offset-based paging; the analytics layer uses opaque keyset cursors. Clients must implement both, and cross-entity tooling (export, bulk operations, generic UI grids) cannot share pagination logic.
  5. No aggregation primitives. Analytics consumers need group-by, count/sum/avg, and having-style filtering. Today this is solved per-endpoint with bespoke aggregation routes, which scales poorly as new metric views are added.
  6. No client-driven projection. Every list response carries the full DTO shape. Clients that need only a few fields pay the full payload + serialization cost, and large JSONB columns trigger TOAST decompression even when not consumed.

The cumulative effect is that clients work around the API instead of with it, the surface area grows with every new entity, and analytics use cases in particular are blocked on capabilities the data layer already supports.

How this model addresses each problem

  • #1 — Queries are submitted in a request body (a structured JSON object), not encoded into the URL, so there is no practical length limit.
  • #2 — The filter grammar (§3) is a recursive boolean tree with and/or/not and arbitrary nesting.
  • #3 — Field queryability is governed by a data-driven per-entity allowlist (§9) declared once per entity, so exposing a property is configuration, not a per-entity code change.
  • #4 — A single pagination contract (§7) models two client-selectable strategies (offset and cursor) behind one shape, so all entities and tooling share one model. (The current translator executes offset only; cursor is modeled but not yet implemented — §7.)
  • #5 — Aggregation is first-class (§5): group_by, aggregate functions, and having-style filtering, available uniformly across entities rather than per bespoke route.
  • #6 — Clients project exactly the fields they need (§4 select), avoiding full-DTO payloads and unnecessary large-column reads.

Conventions

  • JSON keys are snake_case.
  • Filter nodes are discriminated by op (CQL2-JSON shape).
  • Expression nodes are discriminated by type.
  • Pagination nodes are discriminated by type.
  • The filter op convention and the type conventions are intentionally separate: filters follow CQL2-JSON (op is intrinsic to it); expressions and pagination are our own grammars (type is the natural fit).
  • // ← comments are annotations, not part of the JSON.

1. Top-level envelope

{
  "entity": "orders",          // required; resolved against the entity registry (allowlist root)
  "filter":   { ... },         // optional; WHERE — boolean tree of filter nodes (§3)
  "mode":     "row",           // "row" | "aggregate" (§2)
  "distinct": false,           // optional; statement-level SELECT DISTINCT (row dedup) (§5)
  "select":   [ ... ],         // output columns — list of { expr, as } (§5); used in BOTH modes
  "group_by": [ ... ],         // aggregate mode only — grouping keys (§5)
  "having":   { ... },         // aggregate mode only — filter over aggregate aliases (§5)
  "sort":     [ ... ],         // ordering (§6)
  "page":     { ... }          // pagination — discriminated, offset or cursor (§7)
}

Only entity is always required; the rest are constrained by mode (§2). Output columns are listed in select in both modes (§5); there is no separate aggregate section — an aggregate output column is simply a select entry whose expression is an aggregate function.

2. Modes: row vs aggregate

SQL forbids mixing non-grouped raw columns with aggregates, so the model has two mutually exclusive modes, switched by mode. Both modes list their output columns in select (§5); what is legal inside a select entry differs by mode.

  • row — projection of individual rows. Allowed: filter, distinct, select, sort, page. Each select entry is a scalar expression (optionally aliased). Implementation note: group_by/having are conceptually not part of row mode; the current translator does not reject them when present — it simply ignores them (they are never read in the row-mode build path).

  • aggregate — grouped aggregation. Allowed: filter (pre-aggregation WHERE), group_by, select, distinct, having (post-aggregation), sort, page. (distinct is structurally mode-independent — see §5.3 — and the current translator applies it in both modes.) Each select entry must be either a group_by member (a field whose name is a grouping key) or an aggregate-function output column. Group-by keys are not implicitly projected — to appear in the output a key must be listed explicitly in select (matching SQL, where GROUP BY a, b does not auto-select a, b). having/sort may reference group_by keys or output-column aliases only — never raw non-grouped columns.

Open decision D1 (carried): require mode explicitly, or infer it from the presence of group_by. This spec shows it explicit.

3. Filter sub-grammar (CQL2-JSON op / args)

A filter is a recursive tree of filter nodes. A node is either a logical node or a predicate node, discriminated by op.

Logical nodes

{ "op": "and", "args": [ <node>, <node>, ... ] }
{ "op": "or",  "args": [ <node>, <node>, ... ] }
{ "op": "not", "args": [ <node> ] }

Predicate nodes

{ "op": "<code>", "args": [ <expr>, <expr> ] }
  • Both operands are expressions (§4) — field, value, param, fn, or array. There is no separate "property" node: a column reference is just a field expression ({ "type": "field", "name": "amount" }).
  • Because operands are full expressions, either side may be computed. The left operand is not required to be a bare column — e.g. length(test_suite_id) = 3 puts a fn on the left and a value on the right (see §8.4).
  • in is structurally an ordinary binary predicate; its right operand is typically an array expression (§4.6). The model does not encode "left must be scalar / right must be a set" — that is a type/semantic constraint validated at a later stage, not part of the grammar.

Operator codes

Code Name SQL emission
eq EQUALS = (special-cased for a null operand → IS NULL, see §4.2)
ne NOT_EQUAL <> (special-cased for a null operand → IS NOT NULL)
co CONTAINS left ILIKE '%' || ? || '%' (case-insensitive substring; literal %/_ in the pattern operand are escaped)
nc NOT_CONTAINS left NOT ILIKE '%' || ? || '%' (same escaping)
lt LESS_THAN <
gt GREATER_THAN >
le LESS_THAN_OR_EQUAL <=
ge GREATER_THAN_OR_EQUAL >=
in INCLUDES IN (?, ?, …)

Notes: - co/nc are positional (not commutative): the left operand is the value being searched, the right operand supplies the substring pattern. They are case-insensitive (ILIKE) and escape %/_ in the pattern operand so the user's literal characters are not treated as wildcards.

Collision note

Logical keywords appear only as the op value (not as object keys alongside field names), so there is no field-name/operator collision in this shape — one reason it was chosen over the underscore-keyed GraphQL shape.

Example

(status = 'OPEN' AND amount > 100) OR (status = 'PENDING' AND priority = 'HIGH'):

{
  "op": "or",
  "args": [
    { "op": "and", "args": [
        { "op": "eq", "args": [ { "type": "field", "name": "status" }, { "type": "value", "value_type": "string",  "value": "OPEN" } ] },
        { "op": "gt", "args": [ { "type": "field", "name": "amount" }, { "type": "value", "value_type": "decimal", "value": "100" } ] }
    ]},
    { "op": "and", "args": [
        { "op": "eq", "args": [ { "type": "field", "name": "status" },   { "type": "value", "value_type": "string", "value": "PENDING" } ] },
        { "op": "eq", "args": [ { "type": "field", "name": "priority" }, { "type": "value", "value_type": "string", "value": "HIGH" } ] }
    ]}
  ]
}

Null check (shipped_at IS NULL):

{ "op": "eq", "args": [ { "type": "field", "name": "shipped_at" }, { "type": "value", "value_type": "null", "value": null } ] }

4. Expression grammar

A uniform grammar used wherever a value can appear: select entries, function arguments, filter/having operands, and sort targets. An expression is one of five kinds, discriminated by type.

4.1 The five kinds

// column reference
{ "type": "field", "name": "amount" }

// literal — value ALWAYS a JSON string; value_type governs parsing (§4.2)
{ "type": "value", "value_type": "decimal", "value": "100.00" }

// runtime parameter — bound at execution from a trusted server-side context (§4.3)
// NOTE: accepted by the wire model but NOT YET SUPPORTED at execution — the current
// translator rejects any `param` with a ValidationException (§4.3).
{ "type": "param", "name": "min_threshold" }

// function call — arbitrary arity; args are themselves expressions; nestable (§4.4)
// optional `distinct` applies to the function's argument(s), e.g. COUNT(DISTINCT …)
// AVG(ABS(amount)) — an aggregate wrapping a scalar function over a field
{ "type": "fn", "name": "avg", "args": [
    { "type": "fn", "name": "abs", "args": [ { "type": "field", "name": "amount" } ] }
]}

// COUNT(DISTINCT length(test_suite_id)) — distinct attaches to the FUNCTION, over any expression
{ "type": "fn", "name": "count", "distinct": true, "args": [
    { "type": "fn", "name": "length", "args": [ { "type": "field", "name": "test_suite_id" } ] }
]}

// array — an ordered collection of expressions; items are themselves expressions (§4.6)
{ "type": "array", "items": [
    { "type": "value", "value_type": "string", "value": "SUCCESS" },
    { "type": "value", "value_type": "string", "value": "PARTIAL" }
]}

Java mapping (sealed interface + records ⇒ recursive Jackson deserialization via @JsonTypeInfo(use = NAME, property = "type") + @JsonSubTypes, and exhaustive switch in the translator):

@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, property = "type")
@JsonSubTypes({
    @JsonSubTypes.Type(value = FieldExpr.class, name = "field"),
    @JsonSubTypes.Type(value = ValueExpr.class, name = "value"),
    @JsonSubTypes.Type(value = ParamExpr.class, name = "param"),
    @JsonSubTypes.Type(value = FnExpr.class,    name = "fn"),
    @JsonSubTypes.Type(value = ArrayExpr.class, name = "array")
})
public sealed interface Expr permits FieldExpr, ValueExpr, ParamExpr, FnExpr, ArrayExpr {}

public record FieldExpr(String name) implements Expr {}
public record ValueExpr(ValueType valueType, String value) implements Expr {} // value: always String
public record ParamExpr(String name) implements Expr {}
public record FnExpr(String name, boolean distinct, List<Expr> args) implements Expr {}
public record ArrayExpr(List<Expr> items) implements Expr {}

4.2 Literals and value_type

  • value is always a JSON string. value_type tells the parser what to parse it into. This eliminates JSON-number precision loss (decimals/money exact) and gives one parsing path.
  • value_type is a stable, documented, allowlisted enum: string, integer, long, decimal, boolean, date, timestamp, uuid, null (extend deliberately).
  • null: a reserved value_type representing SQL NULL. value is ignored when value_type is null. Whether an implementation tolerates or rejects a non-empty value alongside value_type: null is an implementation detail, out of scope for this spec.
  • null is only meaningful with eq / ne. When either operand of an eq/ne predicate is a null value literal (in practice the right operand), the translator emits IS NULL (for eq) or IS NOT NULL (for ne) against the other operand. The validator rejects a null operand with any other operator.
  • Temporals are always instants. timestamp must carry a zone designator (Z or an explicit offset), e.g. 2020-10-11T11:55:31Z; a zoneless string is invalid. date is ISO-8601 YYYY-MM-DD. Locale→instant conversion is the client's responsibility (frontend or calling API). Maps to Postgres timestamptz / Java Instant.

Parse stage produces a typed Java value per value_type with specific, attributable errors (e.g. "value '10x' is not a valid integer"; "timestamp must include a zone offset or Z").

4.3 Runtime parameters (param)

  • Resolved at execution from a trusted server-side context (per-request), NOT from client-supplied SQL or arbitrary column names. Emitted as a bind parameter.
  • The resolution source must be explicitly constrained (a fixed server-provided map per request, etc.) so a param can never become a vector for the client to control query structure. (Open decision D10: define the parameter source/registry.)

Not yet supported. param is part of the wire model (it deserializes), but the current translator has no server-side parameter registry and rejects any param expression at execution with a ValidationException ("param expressions are not supported by the experimental query translator"). This is the same model-vs-execution split as cursor pagination (§7); both await D10/implementation.

4.4 Functions (fn) — and the safety boundary

  • args is an array of expressions ⇒ arbitrary arity and arbitrary nesting; operands may freely mix field, value, param, array, and nested fn.
  • Aggregates are just functions (sum, count, avg, min, max, …). count with no args ⇒ COUNT(*).
  • distinct (optional, default false) applies to the function's argument(s) — i.e. argument-level deduplication such as COUNT(DISTINCT x). Because the argument is any expression, this generalizes to COUNT(DISTINCT length(x)). This is distinct from statement-level SELECT DISTINCT (§5), which dedupes whole result rows and is a top-level query flag, not a function property.
  • The function set is a registry/allowlist — this is the core safety property. Each registered function declares: a SQL template/emitter, arity rule (fixed/variadic), argument type constraints, and an is_aggregate flag. A fn name not in the registry is rejected at validation — there is no code path that emits an unregistered name, so a client cannot invoke pg_sleep, pg_read_file, or any unblessed function. "Custom functions" means functions you register (a config/admin step), never functions named inline by the client.
  • Currently registered functions. The current translator allowlists exactly: scalar — lower, upper, length, trim, abs, width_bucket; aggregate — count (no args ⇒ COUNT(*)), sum, avg, min, max; ordered-set aggregate — percentile_cont, percentile_disc. Any other name (e.g. round, div) is rejected with unsupported function '…' in query expression.

4.5 Flat property abstraction (field references and physical sources)

A field reference names a flat, allowlisted property as published by the entity's schema endpoint — a single name from a flat list of available columns. The client always works in this flat namespace and never expresses how a property is physically stored.

  • A property may map to a plain column or to a derived source — for example a value nested inside a JSONB column, exposed under a flat name. The per-entity allowlist (§9) holds, for each property: its declared type, its permitted operators/capabilities, and its server-side resolution to a physical source (column access, JSONB navigation, casts, etc.). This resolution happens during translation and is invisible to the DSL.
  • Consequently the DSL contains no JSONB navigation, path, or cast syntax. A client filters, projects, groups, and aggregates a derived property exactly as it would a plain column (see §8). Adding or changing a derived property is an allowlist change, not a grammar or client change (#3).
  • Null semantics of a derived property collapse to SQL NULL. A derived property resolves to SQL NULL whenever its underlying value is unavailable — this includes both an absent source (e.g. a missing JSONB key) and a present-but-null source (e.g. a key whose value is JSON null). These cases are not distinguished at the DSL level; value_type: null with eq/ne (§4.2) tests the resolved SQL NULL, covering both.

4.6 Arrays

{ "type": "array", "items": [ <expr>, <expr>, ... ] }
  • An array is an ordinary expression kind — it may appear wherever an expression may appear (the most common use is the right operand of in, but it is not restricted to that; e.g. it may be a function argument). Whether a given context accepts a collection-typed operand is a type-compatibility matter resolved during validation, the same as for any other expression — it is not a placement rule in the grammar. (For example, using an array where a scalar is expected, such as gt, is a type error; the grammar permits the structure, the validator rejects the incoherent use.)
  • items are expressions. The key is deliberately items (a collection), distinct from a function's args (ordered positional arguments to a callable).
  • Homogeneity: an array's items must be type-compatible with one another (homogeneous).
  • Which expression kinds are admissible as items in a given position (e.g. literals only vs. also field/param/fn), and how an empty array is handled, are determined by the DSL processor at query construction and are not specified here.

5. Output columns (select), group_by, distinct, and having

5.1 Output columns — select

Both modes list output columns in select. Each entry is an output column:

{ "expr": <expression>, "as": "<alias>" }
  • expr — any expression (§4): field, value, param, fn, array.
  • as — output alias. Optional when expr is a plain field (the output key defaults to the field name); required otherwise (a computed/function result has no natural name). Aliases must be unique within a query.

An aggregate output column is simply one whose expr is an aggregate function — there is no separate aggregate section. Examples (aggregate mode):

"select": [
  { "expr": { "type": "field", "name": "region" } },                 // group_by key, projected explicitly
  { "expr": { "type": "field", "name": "status" } },                 // group_by key, projected explicitly
  { "expr": { "type": "fn", "name": "sum",   "args": [ { "type": "field", "name": "amount" } ] }, "as": "total" },
  { "expr": { "type": "fn", "name": "avg",   "args": [ { "type": "field", "name": "amount" } ] }, "as": "avg_amount" },
  { "expr": { "type": "fn", "name": "count", "args": [] }, "as": "cnt" },
  { "expr": { "type": "fn", "name": "count", "distinct": true, "args": [ { "type": "field", "name": "customer_id" } ] }, "as": "unique_customers" }
]

Row-mode example (a plain field, an aliased field, and a computed column):

"select": [
  { "expr": { "type": "field", "name": "id" } },
  { "expr": { "type": "field", "name": "test_case_name" }, "as": "name" },
  { "expr": { "type": "fn", "name": "length", "args": [ { "type": "field", "name": "test_suite_id" } ] }, "as": "suite_id_len" }
]

Absent/empty select: in row mode, the current translator projects all columns of the backing table (SELECT <table>.*) — there is no per-entity default projection and no heavy-column exclusion yet (a future #6 optimization; cf. open decision D2-style per-entity default). In aggregate mode, select is required (an empty select is rejected with a ValidationException).

Java mapping:

public record OutputColumn(Expr expr, String as) implements ... {}  // as nullable

5.2 Grouping — group_by (aggregate mode)

"group_by": ["region", "status"]      // grouping keys (flat property names)

Grouping keys are not auto-projected: to appear in output, a key must be listed in select as a field expression (§5.1). Every aggregate-mode select entry must be either a group_by member or an aggregate-function output (§2).

5.3 Statement-level distinct — distinct

"distinct": true       // top-level; SELECT DISTINCT over the output columns (row dedup)
  • A top-level boolean flag (default false) producing SELECT DISTINCT … — deduplication of whole result rows across the select columns. This is distinct from a function's argument-level distinct (§4.4): statement-level dedups rows, function-level dedups a function's argument values.
  • Structurally independent of mode; combining it with group_by is permitted but typically redundant and not specially policed.

5.4 having (aggregate mode)

having reuses the §3 filter grammar. Its field references resolve to output-column aliases and/or group_by keys, never raw columns — a field whose name matches an as alias refers to that output column:

"having": {
  "op": "and",
  "args": [
    { "op": "gt", "args": [ { "type": "field", "name": "total" }, { "type": "value", "value_type": "decimal", "value": "50000" } ] },
    { "op": "ge", "args": [ { "type": "field", "name": "cnt" },   { "type": "value", "value_type": "integer", "value": "10" } ] }
  ]
}

Translation note: HAVING is a filter applied after aggregation; its aliases resolve to aggregate output, not base columns. The validator must check having/sort references against group_by ∪ {output-column aliases}, and must enforce SQL context rules: no aggregate nested inside an aggregate; raw non-grouped columns are illegal outside an aggregate; having is aggregate-level.

6. Sort

"sort": [
  { "field": "total",  "dir": "desc" },   // output-column alias (aggregate mode) ...
  { "field": "region", "dir": "asc" }      // ... or group_by key / projectable field (row mode)
]
  • dir ∈ asc | desc.
  • References must be sortable per allowlist (row mode) or in group_by ∪ {output-column aliases} (aggregate mode).
  • Null ordering (NULLS FIRST/LAST) must be deterministic (open decision D8: default null ordering); it affects both page-boundary determinism (offset) and seek correctness (cursor).
  • Total order: if the client's sort is not a total order, the server appends a stable unique tiebreaker (open decision D5; default: primary key). For cursor pagination this is strictly required (keyset seek breaks without it); for offset it is required for deterministic page boundaries — which is the stated purpose of offset mode. The tiebreaker therefore applies to both pagination types.

7. Pagination (#4)

One pagination contract with two client-selectable strategies, discriminated by type. This unifies the legacy split (meta = offset, analytics = opaque cursors) into a single model both layers share: clients implement one shape; the strategy is a field, not a different API.

  • offset — deterministic pagination: page numbers, jump-to-page, "page 3 of 17" UIs.
  • cursor — stable iteration: infinite scroll, exports, large scans.

Implementation status. The current translator implements offset only. A cursor page is accepted by the wire model (it deserializes) but is rejected at execution with a ValidationException ("cursor pagination is not supported by the experimental query translator; use offset paging"). The cursor strategy below (§7.1–§7.4) is therefore the target contract; only the offset paths run today.

7.1 Request

// offset strategy
"page": {
  "type": "offset",
  "offset": 200,                // 0-based row offset
  "limit": 100,
  "include_total": true         // optional, default false — opt-in total count (§7.3)
}

// cursor strategy
"page": {
  "type": "cursor",
  "cursor": "eyJ2IjoxLCJrIjpb...",  // opaque token; omit/null for the first page
  "limit": 100
}

Java mapping (same discriminator pattern as expressions):

@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, property = "type")
@JsonSubTypes({
    @JsonSubTypes.Type(value = OffsetPage.class, name = "offset"),
    @JsonSubTypes.Type(value = CursorPage.class, name = "cursor")
})
public sealed interface Page permits OffsetPage, CursorPage {}

public record OffsetPage(long offset, int limit, boolean includeTotal) implements Page {}
public record CursorPage(String cursor, int limit) implements Page {}   // cursor null on first page

Validation: fields foreign to the declared type (e.g. offset on a cursor page, or cursor on an offset page) are rejected with a specific error, consistent with the rest of the model.

7.2 The cursor is opaque

The cursor is a server-issued opaque token. The client echoes it verbatim and never constructs, modifies, or inspects one. Its encoding, contents, versioning, and staleness/invalidation behavior (e.g. what happens if filter/sort change between pages) are implementation details outside this spec. The only contract-level guarantees:

  • A next_cursor returned by the server is valid input for the next request of the same query.
  • An invalid or stale cursor is rejected with a specific error (not silently reinterpreted).

7.3 Strategy semantics and tradeoffs (normative notes)

  • offset is deterministic, not write-consistent. Page boundaries are deterministic for a fixed dataset and total-order sort, but under concurrent writes rows can shift between pages (skips/repeats across page fetches). This is inherent to offset paging and accepted; clients needing a stable scan should use cursor.
  • offset cost grows with depth. The database scans past offset rows; deep offsets on large tables are expensive. See governance (§7.5).
  • cursor (keyset/seek): the next page is fetched via a seek predicate over the sort keys — (k1, k2) < (?, ?) with per-column direction handling — built like any other filter, so it inherits parameterization. Requires the total-order sort invariant (§6).
  • Total count: available only as opt-in (include_total: true, offset strategy) — it is a second, potentially expensive query. Cursor responses do not carry totals.

7.4 Response envelope

The current implementation returns a single flat shape for both modes — there is no per-strategy response envelope and no echoed page object. The response is the StructuredQueryResultDto:

{
  "rows": [ ... ],     // projected rows as field-name → value maps, in field order;
                       // JSONB-backed columns are returned as nested JSON, not escaped strings
  "totalCount": 1432   // present (non-null) ONLY for row-mode offset paging with
                       // include_total=true; null otherwise (including aggregate mode)
}

The client computes the next offset itself (offset + limit) — the server does not return a next-page pointer. totalCount lets an offset client size the result set when it opts in.

Target vs current. An earlier draft of this section specified per-strategy envelopes ({ data, page: { type, offset/next_cursor, limit, total } }). That shape is not what the implementation emits; the flat { rows, totalCount } DTO above is authoritative. A cursor next-page token is not returned because cursor paging is not yet executed (§7 status note).

7.5 Governance (target)

The items below are the intended governance contract. Current status: only limit clamping is implemented (default 100, max 1000); the rest are targets the experimental translator does not yet enforce, and only the offset strategy executes at all (§7 status note).

  • limit is clamped to a server-defined maximum. (Implemented — default 100, max 1000.)
  • Statement timeout and row cap apply at execution regardless of strategy. (Not yet wired in the experimental translator.)
  • The server MAY cap the maximum offset for the offset strategy (deep-offset cost protection); exceeding it is a specific error. (Not implemented.)
  • The per-entity allowlist MAY constrain which pagination types an entity supports (e.g. an analytics entity over a very large table may permit only cursor). (Not implemented — there is no per-entity pagination-type allowlist; cursor is currently rejected for every entity.)

8. Worked examples

These examples query the analytics entity test_case_eval_summaries (metric-enriched test case run results; one row = one test case execution). They illustrate the flat-column abstraction (§4.5): metric outputs that are physically nested inside a JSONB column are exposed to the client as flat, allowlisted property names (e.g. accuracy_score, relevance_score). The client never expresses JSONB navigation or casts; the server resolves each flat property to its underlying source during translation. The DSL requests below therefore look identical to any other entity's; the JSONB expansion is visible only in the intended SQL.

8.1 Row mode: filter by a metric threshold + projection + offset page with total

Select a few flat columns (some plain, some metric-derived), keep cases for one run whose Accuracy score is below a threshold, newest first.

Request:

{
  "entity": "test_case_eval_summaries",
  "mode": "row",
  "filter": {
    "op": "and",
    "args": [
      { "op": "eq", "args": [ { "type": "field", "name": "test_suite_run_id" }, { "type": "value", "value_type": "uuid",    "value": "8f3a…" } ] },
      { "op": "eq", "args": [ { "type": "field", "name": "computation_id" },    { "type": "value", "value_type": "uuid",    "value": "1c20…" } ] },
      { "op": "lt", "args": [ { "type": "field", "name": "accuracy_score" },    { "type": "value", "value_type": "decimal", "value": "0.5" } ] }
    ]
  },
  "select": [
    { "expr": { "type": "field", "name": "id" } },
    { "expr": { "type": "field", "name": "test_case_name" } },
    { "expr": { "type": "field", "name": "execution_status" } },
    { "expr": { "type": "field", "name": "accuracy_score" } },
    { "expr": { "type": "field", "name": "accuracy_confidence" } },
    { "expr": { "type": "field", "name": "relevance_score" } }
  ],
  "sort": [ { "field": "accuracy_score", "dir": "asc" }, { "field": "id", "dir": "asc" } ],
  "page": { "type": "offset", "offset": 0, "limit": 25, "include_total": true }
}

Intended SQL (parameterized; flat metric properties expanded server-side to their JSONB sources; total fetched as a separate count query when requested):

SELECT
    id,
    test_case_name,
    execution_status,
    (metric_values -> 'Accuracy'  ->> 'score')::numeric      AS accuracy_score,
    (metric_values -> 'Accuracy'  ->> 'confidence')::numeric AS accuracy_confidence,
    (metric_values -> 'Relevance' ->> 'score')::numeric      AS relevance_score
FROM test_case_eval_summaries
WHERE test_suite_run_id = ?
  AND computation_id    = ?
  AND (metric_values -> 'Accuracy' ->> 'score')::numeric < ?
ORDER BY accuracy_score ASC, id ASC
LIMIT ? OFFSET ?;          -- 25 (clamped), 0

Note how accuracy_score lt 0.5 in the DSL becomes the expanded, cast JSONB predicate in SQL — the client wrote only the flat name and a decimal literal.

8.2 Aggregate mode: group-by + avg + having + cursor page

Average Accuracy score per execution status for one run, keeping only statuses with a meaningful number of scored cases. avg/count over a metric-derived column ignore SQL NULLs (a failed or missing score resolves to NULL), so they don't skew the result.

Request:

{
  "entity": "test_case_eval_summaries",
  "mode": "aggregate",
  "filter": {
    "op": "and",
    "args": [
      { "op": "eq", "args": [ { "type": "field", "name": "test_suite_run_id" }, { "type": "value", "value_type": "uuid", "value": "8f3a…" } ] },
      { "op": "eq", "args": [ { "type": "field", "name": "computation_id" },    { "type": "value", "value_type": "uuid", "value": "1c20…" } ] }
    ]
  },
  "group_by": ["execution_status"],
  "select": [
    { "expr": { "type": "field", "name": "execution_status" } },
    { "expr": { "type": "fn", "name": "count", "args": [] }, "as": "total_cases" },
    { "expr": { "type": "fn", "name": "avg", "args": [ { "type": "field", "name": "accuracy_score" } ] }, "as": "avg_accuracy_score" }
  ],
  "having": { "op": "ge", "args": [ { "type": "field", "name": "avg_accuracy_score" },
              { "type": "value", "value_type": "decimal", "value": "0.6" } ] },
  "sort": [ { "field": "avg_accuracy_score", "dir": "desc" } ],
  "page": { "type": "offset", "offset": 0, "limit": 100 }
}

Intended SQL (the avg argument's flat property is expanded to its JSONB source):

SELECT
    execution_status,
    COUNT(*)                                                AS total_cases,
    AVG((metric_values -> 'Accuracy' ->> 'score')::numeric) AS avg_accuracy_score
FROM test_case_eval_summaries
WHERE test_suite_run_id = ?
  AND computation_id    = ?
GROUP BY execution_status
HAVING AVG((metric_values -> 'Accuracy' ->> 'score')::numeric) >= ?
ORDER BY avg_accuracy_score DESC
LIMIT ? OFFSET ?;

Aggregate-mode response — the same flat { rows, totalCount } shape as row mode (§7.4). Group keys and aggregate aliases are flattened into each row as ordinary field-name → value entries; there is no separate keys/metrics grouping and no echoed page. totalCount is null in aggregate mode:

{
  "rows": [
    { "execution_status": "SUCCESS", "total_cases": 1840, "avg_accuracy_score": 0.83 },
    { "execution_status": "PARTIAL", "total_cases": 212,  "avg_accuracy_score": 0.61 }
  ],
  "totalCount": null
}

(One flat rows schema serves any grouping/aggregate combo; aggregate values are not statically typed per-column — an inherent dynamic-shape tradeoff for aggregation. A draft of this spec proposed a typed keys+metrics envelope, but the implementation emits the flat row shape above. Open decision D6.)

8.3 Null handling on a metric-derived column

A flat metric column resolves to SQL NULL whenever its score is unavailable — this covers both an absent JSONB key and a key present with JSON null. The two cases are not distinguished at the DSL level (see §4.5). To keep only cases that have an Accuracy score:

{
  "op": "ne",
  "args": [ { "type": "field", "name": "accuracy_score" }, { "type": "value", "value_type": "null", "value": null } ]
}

→ WHERE (metric_values -> 'Accuracy' ->> 'score')::numeric IS NOT NULL (per §4.2, ne + null ⇒ IS NOT NULL).

8.4 Computed operand: function on the left of a comparison

Either side of a predicate is a full expression, so the left operand need not be a bare column. To keep only rows whose test_suite_id is exactly three characters long (WHERE length(test_suite_id) = 3):

{
  "op": "eq",
  "args": [
    { "type": "fn", "name": "length", "args": [ { "type": "field", "name": "test_suite_id" } ] },
    { "type": "value", "value_type": "integer", "value": "3" }
  ]
}

→ WHERE length(test_suite_id) = ? — length must be a registered scalar function and test_suite_id must be filterable (§9). The literal is bound as a parameter.

8.5 Set membership: in with an array operand

WHERE execution_status IN ('SUCCESS', 'PARTIAL') — an ordinary binary predicate whose right operand is an array expression (§4.6):

{
  "op": "in",
  "args": [
    { "type": "field", "name": "execution_status" },
    { "type": "array", "items": [
        { "type": "value", "value_type": "string", "value": "SUCCESS" },
        { "type": "value", "value_type": "string", "value": "PARTIAL" }
    ]}
  ]
}

→ WHERE execution_status IN (?, ?) — each array item bound as a parameter.

9. Validation / allowlist hooks

Checked before execution — in the current implementation the checks are interleaved with jOOQ query construction (each violation throws a ValidationException mid-build), so no SQL runs unless the whole query translates. The list below describes the checks the translator actually performs; it does not yet implement a separate pre-validation pass.

  1. Entity resolves in the registry, else reject.
  2. Mode coherence (partial). Aggregate mode requires a non-empty select (else reject), and every non-group-key select entry requires an as alias. The translator does not reject sections that are illegal for the mode — a row-mode query carrying group_by/having has them silently ignored rather than rejected (§2).
  3. Expression operands are walked as trees. Filter/predicate operands, select entry exprs, group_by keys, sort targets, and having operands are expressions (§4), so translation recurses through each tree. Each field must resolve to a binding the entity published — a flat name → generated jOOQ column + declared QueryFieldType (QueryFieldBinding), or, for a complex entity, a flattened JSONB path (the data:/response:/metric:/metricInfo: namespaces, §4.5); an unknown name is rejected with unknown field '<name>'. There are no per-capability flags (filterable/projectable/groupable/aggregatable/sortable) and no per-field operator allowlist in the current model — a resolvable field may be used in any position. Each fn resolves in the function allowlist (item 4); each value/param/array is checked per items 5–7. A field reference may sit anywhere in the tree (e.g. inside length(test_suite_id)), not only as a top-level operand.
  4. Functions — every fn name resolves in the function allowlist (item 4 of §4.4), else reject with unsupported function '…'; arity is checked (e.g. single-arg scalars, width_bucket requires four args, percentile_* requires a numeric-literal fraction in [0,1] plus a column). SQL aggregate/scalar context rules (no aggregate-in-aggregate; raw non-grouped column outside an aggregate; having is aggregate-level) are not pre-validated — they are enforced by PostgreSQL at execution, surfacing as a query error.
  5. Literals — value parses per value_type; null only with eq/ne; temporals are valid instants; parsed type compatible with usage context.
  6. Arrays — an array is valid only as the right operand of in; used anywhere else it is rejected (array expressions are only valid as the right operand of 'in'). The in operator requires a non-empty array whose items are value literals. Item homogeneity is not separately enforced beyond the per-item literal parse (§4.6).
  7. Output columns (select) — in aggregate mode, select is required (non-empty, else reject) and every entry that is not a group_by-member field requires an as alias (aggregate output column requires an 'as' alias). Not currently enforced: alias uniqueness across the query, a row-mode "scalar-only / no aggregate" restriction, and a row-mode as-required rule — a row-mode non-field expression without as simply takes jOOQ's default column name.
  8. having / sort references — having (aggregate mode) resolves a field against output-column aliases and group keys (and base bindings). sort resolves to an output-column alias when one matches, otherwise to any resolvable field; it is not restricted to group_by ∪ {output-column aliases} in the current translator.
  9. param — rejected (not yet supported): there is no runtime-parameter source, so any param expression fails translation (§4.3, D10).
  10. Pagination — offset is the only executable strategy; a cursor page is rejected (§7). A negative offset is rejected; limit is clamped (default 100, max 1000; a non-positive limit falls back to the default). There is no per-entity pagination-type allowlist and no maximum-offset cap in the current translator; statement timeout / row cap (§7.5) are governance targets, not yet wired here.
  11. Rejections surface as ValidationException messages, e.g. unknown field 'internal_notes', unsupported function 'round' in query expression, null literal is only valid with 'eq'/'ne', or cursor pagination is not supported by the experimental query translator; use offset paging.

The per-entity field set is schema-derived — base columns come from the entity's generated jOOQ table (JooqTableSchemaResolver), and a complex entity additionally publishes flattened JSONB property names via its schema provider. Exposing a plain column is largely schema-driven; exposing a new derived/JSONB property still requires a provider change today (#3 target, not yet fully config-only).

10. Open decisions

  • D1 — explicit vs inferred mode.
  • D5 — auto tiebreaker key when client sort isn't a total order (default: primary key); applies to both pagination strategies (§6).
  • D6 — aggregate response typing. Current: the implementation returns the flat { rows, totalCount } shape (group keys + aggregate aliases flattened into each row, §7.4/§8.2). Open question: keep this dynamic flat shape or generate per-query typed shapes.
  • D8 — default null ordering (NULLS FIRST/LAST); affects offset page-boundary determinism and cursor seek correctness.
  • D10 — runtime-parameter (param) source/registry definition and its trust boundary.

(Resolved and baked into the spec: filter grammar = CQL2-JSON op/args with the fixed operator codes; predicate operands are expressions (no separate "property" node); array as a fifth expression kind with homogeneous items, with item-kind and empty-array handling left to the DSL processor (former D9 resolved); output columns unified as { expr, as } in both modes (no separate aggregate section; an aggregate output column is just a select entry whose expression is an aggregate function); aggregate mode lists group-by keys explicitly in select (no implicit projection); two distincts — statement-level SELECT DISTINCT as a top-level distinct flag, argument-level COUNT(DISTINCT …) on the fn node; aggregation via explicit group_by; expression discriminator = type; value always a string with value_type governing parsing; null as a value_type replacing a separate is_null operator; temporals always instants; pagination = dual-strategy discriminated by type, with cursor structure an implementation detail and former D4 moved to the implementation.)
