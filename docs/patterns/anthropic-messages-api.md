# Anthropic Messages API support

Invoking a Claude-style deployment through DIAL Core's Anthropic Messages API is recognized by URL path alone — no new deployment-type enum, no `interfaces`/`InterfaceType` gating (DIAL Core's `interfaces` metadata is not a reliable signal of which deployments actually work with the Messages shape, so it's never read). A suite author declares `endpointRef.relativeUrlPattern = "/anthropic/v1/messages"` (DIAL Core's real, deployment-less route — there is no per-deployment suffix to abbreviate, unlike `/chat/completions`); that's the entire recognition mechanism.

Two seams, both narrow extensions of existing mechanisms:

- **`DialCoreUrlBuilder.buildUrl(deploymentId, resolvedUrl)`** — a fixed-path branch (`ANTHROPIC_MESSAGES_URL = "/anthropic/v1/messages"`, matched against `resolvedUrl` and returned unchanged), checked after `OPENAI_STANDARD_PATHS` and before the generic passthrough fallback. Unlike every other branch, `deploymentId` is intentionally unused here: DIAL Core's Messages endpoint takes no deployment ID in the URL at all — it resolves the deployment from the **`model` field inside the JSON request body**, mirroring Anthropic's native API contract. The suite author must write that field as a literal (e.g. `"model": "claude-3-5-sonnet-v2"`) — there is no JSONata binding exposing `deploymentId` to request-body resolution, and adding one is out of scope.
- **`StreamingResponseAccumulator`** — a third assembly mode alongside OpenAI mode and Structured SSE mode. `isAnthropicMode` requires the first SSE event to be **named** `message_start` with a `message` field in its data (OpenAI mode requires an *unnamed* event, so the two can't collide; a named `message_start` without a `message` field degrades gracefully to Structured SSE mode rather than misassembling). `assembleAnthropicResponse` deep-copies the `message` object off `message_start` as the base response, delegates per-block accumulation to `AnthropicContentAccumulator` (mirrors `CustomContentAccumulator`: `text` blocks concatenate `delta.text`, `tool_use` blocks concatenate `delta.partial_json` and parse it into `input` at the end, falling back to the raw string on parse failure; any other block type passes through unchanged from its `content_block_start` shape), and merges `message_delta`'s `delta`/`usage` into the base message. `content_block_stop`/`message_stop`/`ping` are no-ops. On truncation, mirrors OpenAI mode's contract: `responseBody` becomes a plain JSON string of the concatenated `text`-block content (not the full object) and `executionStatus` is `ERROR`.

A soft validation nudge in `SuiteValidationService.validateRequest` (gated on `endpoint.getRelativeUrlPattern().equals(DialCoreUrlBuilder.ANTHROPIC_MESSAGES_URL)`) compares a literal `model` value in the request body against the suite's `deploymentRef.id`, warning (never blocking) on a mismatch. It only fires for a literal `JsonRequestBodyDto` body with a non-placeholder `String` `model` value — `jsonataContent` bodies and `${{...}}` placeholders are skipped as not statically checkable.

**Non-goals**: no `interfaces`/`InterfaceType`-based gating or discovery (see above); no support for the companion `/anthropic/v1/messages/count_tokens` endpoint; no reconstruction of `thinking`/`redacted_thinking` content blocks (only `text` and `tool_use` get delta-reconstructed).
