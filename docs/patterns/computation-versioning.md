# Computation Versioning (No `is_latest` flag)

Entities versioned by `computation_id` (UUID) use append-only writes — the analytics result tables, and the meta `run_metric_snapshots` table that captures each computation's metric catalog. "Latest" is resolved at query time (`ORDER BY computed_at_ms DESC LIMIT 1`); API callers pass `computation=<uuid>` or `computation=latest` (or omit).

**Resolution reads `test_case_eval_summaries`, not `run_metric_snapshots`** — `ComputationResolver.resolve` delegates to `EvalSummaryRepository.findLatestComputationId` (backed by `idx_eval_summaries_run_computed_at`), so "latest" means "latest computation with readable rows" and a metric-less run still resolves; do not re-point it at the snapshot table. Since meta V1.32 that table is in the **meta** database, so re-pointing it would also turn a single-datasource read into a cross-database one.

**Resolution rule, in full:** max `computed_at_ms`; ties broken by greater `computation_id` under **text** (lexicographic) ordering of the canonical `VARCHAR(36)` UUID string — `ORDER BY computed_at_ms DESC, computation_id DESC`, never `java.util.UUID.compareTo`. `findLatestComputationId` and the suite pass-rate endpoint's `countPassRateByLatestComputation` (see `docs/patterns/eval-summaries-read-surface.md`) both apply this exact rule so a run's "latest computation" never disagrees between call sites. Ties are theoretical in practice — a computation writes one `computed_at_ms` — but the tie-break is load-bearing for determinism, not defensive dead code.

Performance note: with the second `ORDER BY` key, `findLatestComputationId` is no longer a pure top-1 index descent on `idx_eval_summaries_run_computed_at` — that index's third column (`computation_id`) is ascending, not descending, so it cannot also satisfy `computation_id DESC` for free. Postgres instead does a bounded index scan on the index's leading `(test_suite_run_id, computed_at_ms DESC)` prefix (all rows for the run, in `computed_at_ms` order) and sorts the newest `computed_at_ms`'s rows by `computation_id` — an index-only operation over at most a handful of rows (rows sharing one run's max `computed_at_ms`), an accepted cost rather than a regression. A follow-up could flip the index's third column to `DESC` to restore a pure top-1 descent; out of scope for this change.

The one legitimate snapshot-based lookup is `EvalSummariesSchemaProvider`, which asks a *metric-catalog* question ("which `metric::*` families does this computation have?"), not a has-results question. It reads the meta snapshot table while the surrounding schema work reads analytics — see [dual-datasource.md](dual-datasource.md) on keeping such a read out of the other datasource's transaction. Unlike the eval-summaries-based resolution above, `RunMetricSnapshotRepository.findLatestComputationId` (the meta repo method behind this lookup) and the inline latest-computation subquery of the `test_suite_runs` query entity's `metric_names` field both tiebreak same-millisecond computations with `computed_at_ms DESC, computation_id DESC` — see [`test_suite_runs` query entity](test-suite-runs-query-entity.md) — since one `Clock` read per computation makes same-millisecond recomputations possible and an unordered tie would let this lookup and `metric_names` disagree.

Export decides explicit-`computation` existence the same way, via `EvalSummaryRepository.existsByRunIdAndComputationId`.
