# Dataset Entity (DatasetSchemaProvider, disabledTestCaseIds, dataset.id vs suite.id, Visibility)

`Dataset` is the central owner of `testCaseSchema` and the test-case table. A `TestSuite` binds to at most one dataset via a NULLABLE `datasetId` with RESTRICT FK; multiple suites may share a PUBLIC dataset, but a PRIVATE dataset is owned by exactly one suite. Schema changes happen on the dataset; the suite never owns or mutates `testCaseSchema` after the migration. A suite with `datasetId=null` is "unbound" — retrievable and updatable, but cannot trigger a run.

- **`DatasetSchemaProvider`** (`service.domain`) — a cross-cutting injectable `@Component` that returns `List<FieldDefinitionDto>` for a given `datasetId`. Introduced to break the would-be circular dependency between `DatasetService` (mutates schema) and `TestSuiteService` (validates suite bindings against schema). Both services inject the provider; the provider has no other dependencies. Throws `EntityNotFoundException` on dataset miss. Callers pre-check `suite.getDatasetId() != null` and pass `List.of()` for unbound suites.
- **`dataset.id = source_suite.id` is a migration starting point, NOT an invariant.** The V1.22 migration creates one dataset per suite with `dataset.id := suite.id` for backfill simplicity. After the migration, users may consolidate (rebind multiple suites to a single dataset) via the dataset endpoints. Production code MUST NOT rely on the id equality — always resolve `suite.getDatasetId()` explicitly.
- **`disabledTestCaseIds`** (`test_suites.disabled_test_case_ids` JSONB array of UUIDs, default `[]`) is a denormalized exclude list. Snapshot-phase query uses `WHERE NOT (id = ANY(:ids::uuid[]))` to filter; stale ids are tolerated by set-membership semantics. The list is capped at `ValidationConstants.MAX_DISABLED_TC_IDS` (10000).
- **Bulk-patch whitelist** (`BulkPatchFields`) is `{testCaseName, data}` — the legacy `enabled` flag was removed with the dataset move. `TestCaseService.bulkPatch` serializes `data` Map → JSON before calling `PostgresTestCaseRepository.updateFieldsByIds` (jOOQ DSL, `isDistinctFrom` for no-op accounting).
- **Visibility** (`datasets.visibility VARCHAR(16) NOT NULL CHECK IN ('PUBLIC','PRIVATE')`) controls catalogue membership and binding semantics:
  - PUBLIC datasets appear in `GET /api/v1/datasets` and can be bound to many suites; FK RESTRICT blocks deletion while suites reference them. Filtering by `visibility` is NOT a query option — `PostgresDatasetRepository.findAll` applies `WHERE visibility = 'PUBLIC'` server-side.
  - PRIVATE datasets are hidden from the list endpoint (still retrievable by id) and are bound to **at most one** suite. Atomic create-and-bind: `POST /datasets {visibility:PRIVATE, bindToSuiteId}` inserts the dataset and rebinds the target suite in one transaction. PRIVATE delete unbinds the (single) bound suite then drops dataset + test cases.
  - PUBLIC↔PRIVATE transitions go through `PATCH /api/v1/datasets/{id}/visibility` (not PUT — PUT silently ignores `visibility`). PUBLIC→PRIVATE requires exactly one bound suite (returns 409 `PRIVATE_TRANSITION_INVALID_BINDING_COUNT` otherwise); PRIVATE→PUBLIC always succeeds.
  - Rebinding a suite off a PRIVATE dataset is forbidden (PUT `/test-suites/{id}` and the PRIVATE create-and-bind path both reject with 409 `PRIVATE_DATASET_REBIND_FORBIDDEN`).
  - **PL/pgSQL constraint trigger `tg_test_suites_private_binding_guard`** (V1.22) enforces single-binding for PRIVATE datasets at the DB level. It `SELECT … FOR UPDATE`s the target dataset row and raises `ERRCODE='P0001'` with message `'PRIVATE_DATASET_ALREADY_BOUND'` when a second suite tries to bind. `DefaultExceptionHandler.handleDataAccessException` inspects `SQLState=='P0001'` and maps to HTTP 409. The standard 23505 → UNIQUE_CONSTRAINT_VIOLATION mapping is untouched.
