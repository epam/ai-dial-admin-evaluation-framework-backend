# TransactionTimestampContext + Aspect

Ensures consistent timestamps within a transaction — all entities saved in the same `@Transactional` call share the same `createdAt`/`updatedAt`. `TransactionTimestampAspect` (`service.infrastructure.transaction.timestamp`) initializes the timestamp via AOP `@Before` on `@Transactional` methods and cleans up via `TransactionSynchronization.afterCompletion`. Inject `TransactionTimestampContext` (`data.db.transaction.timestamp`) and call `getTimestamp()` in repositories.

**Repository update-method signatures:** state-transition update methods on meta repositories (e.g. `updateToRunning`, `updateToFailed`, `updateSuiteSnapshot`, `updateNumberOfTestCases`) take `updatedAt` (and `completedAt`, `startedAt`, etc.) as explicit parameters rather than reading `TransactionTimestampContext` internally. Callers inside `@Transactional` methods pass `transactionTimestampContext.getTimestamp()`; callers using programmatic `TransactionTemplate` or direct test invocations pass `clock.millis()` / a test timestamp. This keeps repository methods pure and callable from tests that don't open a transaction.

**Programmatic transactions (`TransactionTemplate`):** the aspect only fires on `@Transactional`-annotated methods. If you add code inside a `TransactionTemplate` callback that calls a repository method still reading `transactionTimestampContext.getTimestamp()` internally, call `transactionTimestampContext.initializeIfAbsent()` first — otherwise `getTimestamp()` throws `IllegalStateException: Timestamp not initialized`. Prefer the explicit-parameter pattern above over `initializeIfAbsent()`.
