## Why

The eval job generates random UUID strings as trace IDs — completely unrelated to OpenTelemetry — so the `traceId` stored in `TestCaseRunResult` cannot be correlated with DIAL Core logs or a tracing backend (Jaeger/Tempo). Additionally, try-it-out sends no trace context to DIAL Core and returns no trace ID to the caller. Adding full Micrometer Tracing + OTel integration fixes both gaps and enables end-to-end distributed tracing across the DIAL platform.

## What Changes

- Add `io.micrometer:micrometer-tracing-bridge-otel` dependency; let Spring Boot BOM manage compatible OTel SDK versions
- Wire OTel context propagation through the two async boundaries: `@Async` thread pool (`testSuiteRunExecutor`) and the virtual thread executor inside `InProcessEvaluationExecutor`
- Replace `UUID.randomUUID()` trace ID generation in `EvaluationWorker` with a proper OTel child span per test case; store the real 32-char hex trace ID in `TestCaseRunResult.traceId`
- Remove manual `X-Correlation-Id: <uuid>` header from eval worker outgoing requests; replace with `traceparent` propagation via a `ClientHttpRequestInterceptor` on both DIAL Core `RestClient` beans
- Add `traceparent` / `tracestate` to the evaluation run header blacklist so template-injected values cannot override OTel propagation headers
- Remove `X-Correlation-Id` from the header blacklist (no longer generated by the worker)
- Add OTel child span in `TryItOutService` for each invocation; propagate `traceparent` to DIAL Core; **BREAKING** add `traceId` field to `TryItOutResponseDto`
- Install the Spring-autoconfigured `OpenTelemetry` bean into the existing Log4J appender so trace/span IDs appear in log output
- Add `management.tracing.*` and `management.otlp.tracing.*` configuration properties

## Capabilities

### New Capabilities
- none

### Modified Capabilities
- `observability-and-logging`: X-Correlation-Id on incoming requests is now derived from OTel (`Span.current()` now returns a real span, not all-zeros); OTel context is propagated through all async boundaries; `traceparent` replaces the manual `X-Correlation-Id` on outgoing DIAL Core calls
- `eval-execution-engine`: `TestCaseRunResult.traceId` is now the 32-char hex OTel trace ID from a child span (was: random UUID with dashes); eval worker no longer manually sets `X-Correlation-Id`; `traceparent` injected automatically
- `try-it-out`: Response gains a `traceId` field (32-char hex OTel trace ID of the invocation span); `traceparent` propagated to DIAL Core on all try-it-out calls

## Impact

- **`build.gradle`**: add `micrometer-tracing-bridge-otel`; align `opentelemetry-log4j-appender` version with Spring Boot BOM
- **`AsyncConfiguration`**: add `ContextPropagatingTaskDecorator` to `testSuiteRunExecutor`
- **`InProcessEvaluationExecutor`**: wrap virtual thread executor with `Context.taskWrapping()`
- **`EvaluationWorker`**: inject `io.micrometer.tracing.Tracer`; create child span per test case; use span trace ID; remove manual `X-Correlation-Id`
- **`DialCoreClientConfiguration`** + **`DialCoreDeploymentInvokerConfiguration`**: add OTel `traceparent` propagation interceptor to both RestClients
- **`TryItOutService`**: inject `Tracer`; wrap each invocation in a child span; return trace ID
- **`TryItOutResponseDto`**: add `traceId` field (String, nullable)
- **`application.yml`**: update header blacklist; add tracing and OTLP config
- **New `OtelAppenderInitializer`** (or similar): `@EventListener(ApplicationReadyEvent)` installs the Spring `OpenTelemetry` bean into `OpenTelemetryAppender`
- **OpenAPI examples** for try-it-out responses must be updated to include `traceId`
