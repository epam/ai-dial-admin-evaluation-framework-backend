## Why

Today `TestSuite` owns both the test case **shape** (`testCaseSchema`) and the **data** (test cases are FK'd to a suite). Test cases cannot be reused across suites — they can only be cloned, after which the copies drift independently. There is no way to maintain a single, governable corpus of test inputs and have edits propagate to every suite that consumes them.

Introducing a `Dataset` entity establishes a centralized, governable container for test case data and shape. Test suites become consumers of a dataset rather than owners of cases; an edit to a test case in the dataset is observed by every suite that references it. The dataset is the foundation for upcoming reuse, governance, and (eventually) cross-environment portability of evaluation corpora.

## What Changes

- Introduce a new `Dataset` entity (id, name, description, `testCaseSchema`, validity flags, optimistic-concurrency `version`, `createdBy`, timestamps) with global name uniqueness on `LOWER(name)`.
- **BREAKING**: Move `testCaseSchema` ownership from `TestSuite` to `Dataset`. Suites no longer carry a schema.
- **BREAKING**: Re-root `TestCase` from `TestSuite` to `Dataset`. The FK becomes `test_cases.dataset_id` (cascade delete) instead of `test_cases.test_suite_id`. The composite uniqueness constraint becomes `(dataset_id, LOWER(test_case_name))`.
- **BREAKING**: Add `TestSuite.datasetId` (NOT NULL FK to `datasets.id`, `ON DELETE RESTRICT`). Each suite must reference exactly one dataset; many suites may share one dataset.
- **BREAKING**: Remove `TestCase.requestTemplateOverride`, `TestCase.inputBindingsOverride`, and `TestCase.enabled` entirely. Per-suite case exclusion is moved to `TestSuite.disabledTestCaseIds` (JSONB array of UUIDs, default `[]`) — a denormalized exclude list, no junction table at this stage.
- **BREAKING**: Relocate all test case endpoints from `/api/v1/test-suites/{suiteId}/test-cases/*` to `/api/v1/datasets/{datasetId}/test-cases/*` (CRUD, bulk PATCH, CSV/ZIP import/preview, CSV export). Drop the `includeEnabled` export query param. Drop the `is_enabled` column from CSV import/export.
- Add a new `DatasetController` (`/api/v1/datasets`) exposing list/get/create/update/delete plus revalidation-task subresources.
- **BREAKING**: Remove `/api/v1/test-suites/{id}/revalidation-tasks*` subroutes. All revalidation-task reads move to `/api/v1/datasets/{id}/revalidation-tasks*`.
- **BREAKING**: Suite delete response drops the `deletedTestCases` count (test cases no longer live under a suite).
- **BREAKING**: `TestSuiteCloneRequestDto` drops the `testCaseSchema` override; clone references the source suite's dataset by default. Test-case copying inside `TestSuiteCloneService` is removed.
- Extend the existing async `RevalidationTask` to be **dataset-rooted**: a single task is spawned per dataset PUT that mutates `testCaseSchema`. It runs two sequential phases with asymmetric failure handling — (1) coerce + revalidate every test case in the dataset, **fail-fast** (any exception aborts the task as today); (2) re-validate every dependent suite's bindings, response columns, and metric definitions (`SuiteValidationService` + `TestSuiteMetricDefinitionService.revalidateAllForSuite`), **per-suite resilient** (an exception in one suite's revalidation is logged with full stacktrace and the loop continues to the next suite). The task ends `COMPLETED` even when individual suites failed Phase 2; per-suite failures are visible in logs only. Counters retain their existing shape and reflect the test-case phase only; structured per-suite outcomes and suite-phase progress tracking are deferred.
- Existing `revalidation_tasks` rows are migrated by renaming `test_suite_id → dataset_id` and retargeting the FK to `datasets(id)` (data preserved because dataset IDs equal source suite IDs). **In-flight rows** (status `PENDING` or `RUNNING` at deploy time) are explicitly transitioned to `FAILED` by the migration with a structured error message ("Aborted by introduce-dataset-entity migration: …"); operators see the abort in task listings and can re-trigger revalidation against the new dataset endpoint. The choice to fail rather than silently fall through is to avoid surprises from a v1 RevalidationService picking up a row whose semantics it no longer understands.
- **BREAKING**: `RevalidationTaskDto.testSuiteId` → renamed to `datasetId`. FK on `revalidation_tasks` retargeted from `test_suite_id` to `dataset_id` (`ON DELETE CASCADE`).
- **BREAKING**: Add `datasetRef` to `SuiteSnapshotDto` to capture the dataset (id + version + name) at run-snapshot time. Bump `SuiteSnapshotDto.CURRENT_VERSION` from `"1"` to `"2"`. `testCaseSchema` continues to be embedded in the snapshot but is sourced from the dataset rather than the suite. `test_case_run_inputs` schema is unchanged (override columns kept nullable for historical-run readability).
- DB: new `datasets` table; structural ALTERs on `test_suites`, `test_cases`, and `revalidation_tasks`. New Flyway migration under `src/main/resources/db/migration/meta/POSTGRES/`. `./gradlew generateJooq` re-run and generated sources committed.
- DB: **data migration runs inline in the same Flyway file** as the DDL. The structural key is `dataset.id = source_suite.id` for every existing suite — this lets the `test_cases.test_suite_id → dataset_id` rename preserve data verbatim, and makes `test_suites.dataset_id` a self-reference column populated via `SET dataset_id = id`. Pre-existing `test_cases.is_enabled = false` rows are translated into `test_suites.disabled_test_case_ids` JSONB arrays **before** the `is_enabled` column is dropped, preserving per-suite case-exclusion behavior. Pre-existing `test_cases.request_template_override` and `input_bindings_override` values are dropped with the columns (acknowledged data loss, per the locked-in scoping decision). Detailed step ordering is in `design.md`.
- Post-migration shape: one dataset per source suite, sharing the same UUID. Dataset `name` is the source suite's name prefixed with the literal string `DATASET_` (e.g. suite `CustomerSupport` → dataset `DATASET_CustomerSupport`) so post-migration listings make the dataset/suite split visually unambiguous. Consolidation — rebinding multiple suites to share a single dataset — is a user-driven follow-on workflow; no automated deduplication.

**Out of scope (separate OpenSpec changes):**
- File-reference path-scheme reform for `@ef/suites/{suiteId}/...` strings embedded in `TestCase.data`. Current scheme is preserved for now and tracked as a known follow-up.
- Splitting `RevalidationTask` into dataset-rooted and suite-rooted variants, adding suite-phase progress counters, or surfacing structured per-suite failures in the task DTO. Per-suite resilience runtime (an exception in one suite's revalidation is logged and the loop continues) is implemented; structured reporting of those failures is deferred — operators inspect logs for v1. Single task row per dataset edit, test-case counters only.
- Dataset consolidation UX (bulk rebind, merge-dataset). Migration produces a 1:1 dataset-per-suite shape; consolidation is left to users via the new dataset CRUD endpoints.
- Cross-spec text harmonization for `tsmd-validation`, `request-template`, `test-suite-metric-definitions`, `response-columns`, `eval-execution-engine`, `eval-summary-export` — deferred to follow-up change `realign-spec-references-to-dataset`.

## Capabilities

### New Capabilities
- `datasets`: Lifecycle and identity of the Dataset entity — CRUD, name uniqueness, optimistic concurrency via `version` + ETag/If-Match, ownership of `testCaseSchema`, validity flags, and the deletion contract (RESTRICT when referenced by any suite).

### Modified Capabilities
- `test-cases`: Test cases are re-rooted under datasets. Endpoints relocate to `/api/v1/datasets/{datasetId}/test-cases/*`. The `requestTemplateOverride`, `inputBindingsOverride`, and `enabled` fields are removed. Name uniqueness becomes `(dataset_id, LOWER(name))`. CSV import/export move with the endpoints; the `is_enabled` column and `includeEnabled` query param are dropped.
- `test-suites`: Suites gain `datasetId` (required) and `disabledTestCaseIds` (default `[]`). The `testCaseSchema` field is removed from suite request/response DTOs. Delete response drops the test-case count. Suite revalidation-task subroutes are removed.
- `test-suite-clone`: Cloned suite references the source suite's dataset by default. Test-case copying and per-case file-reference rewriting under `TestSuiteCloneService` are removed. The `testCaseSchema` override is dropped from `TestSuiteCloneRequestDto`.
- `suite-run-snapshot`: `SuiteSnapshotDto` gains a `datasetRef` (id, version, name). Snapshot version bumps to `"2"`; `"1"` remains readable for in-flight runs. `testCaseSchema` continues to be embedded, sourced from the dataset at snapshot time. Snapshot-phase test case fetch filters by `dataset_id` excluding `suite.disabledTestCaseIds`.
