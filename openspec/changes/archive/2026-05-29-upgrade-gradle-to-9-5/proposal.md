## Why

The project is pinned to Gradle 8.14.4. Gradle 9.x is the current stable line; it ships Configuration Cache + Isolated Projects improvements, full JDK 21 toolchain support, faster incremental builds, and removes many long-deprecated APIs. Staying on 8.x means losing CVE fixes shipped in the 9.x line and accumulating deprecation warnings that will turn into hard errors when we are eventually forced to upgrade under time pressure. Bumping now — while plugins (`io.freefair.lombok 9.2.0`, `org.springframework.boot 3.5.14`) already advertise Gradle 9 compatibility — is the low-risk window.

## What Changes

- Update Gradle wrapper from **8.14.4 → 9.5** (`gradle/wrapper/gradle-wrapper.properties` `distributionUrl`, `gradle-wrapper.jar` regenerated by `./gradlew wrapper --gradle-version 9.5`).
- Update `AGENTS.md` Quick Reference table and `openspec/config.yaml` tech-stack line to read `Build: Gradle 9.5`.
- Fix any Gradle 9 deprecation warnings surfaced by `--warning-mode all` in `build.gradle` — typical hits in scripts of this shape:
  - Removed `convention` plugin API: any `project.convention(...)` calls (none expected; verify).
  - Removed `archiveBaseName`/`archiveVersion` legacy properties (none expected).
  - `Property.set(Provider)` strictness on `JavaCompile` task wiring.
  - Removed `JavaPluginConvention` references (we already use `java { toolchain { ... } }`).
- Re-verify the `generateJooq` task (which uses script-classpath `io.zonky.test:embedded-postgres`, `org.flywaydb:flyway-core`, `org.jooq:jooq-codegen`) still runs under Gradle 9.5 with embedded Groovy 4.
- Re-verify checkstyle plugin (10.26.1), `io.freefair.lombok` 9.2.0, and `org.springframework.boot` 3.5.14 plugins continue to apply cleanly; bump only if their advertised compatibility matrix forbids Gradle 9.5.
- Update GitLab CI (`.gitlab-ci.yml`) and Dockerfile if they reference a specific Gradle image tag.

No source-code, schema, API, or runtime-config changes. No new packages. No spec-level requirement changes — feature contracts are untouched.

## Capabilities

### New Capabilities
- `build-tooling`: declares the project's build-tooling baseline (Gradle wrapper version, distribution type, JDK toolchain) as a single testable spec, so future tooling bumps have an explicit requirement to amend instead of being silent file edits. This is a deliberately narrow capability — it does NOT cover application behavior, only the contract between the project and its build system.

### Modified Capabilities
- _(none — no application-feature spec changes its behavior)_

## Impact

- **Build files**: `gradle/wrapper/gradle-wrapper.properties`, `gradle/wrapper/gradle-wrapper.jar`, `gradlew`, `gradlew.bat` (all regenerated by the wrapper task); `build.gradle` (only if a Gradle 9 deprecation requires a code fix).
- **Docs / tooling metadata**: `AGENTS.md` Quick Reference row, `openspec/config.yaml` `# Tech Stack` block.
- **CI**: `.gitlab-ci.yml` if pinned to a `gradle:8` image tag; `Dockerfile` if it bundles a specific Gradle distribution (we currently use the wrapper, so this is likely a no-op).
- **Local developer setup**: any developer using `gradle` directly (not `./gradlew`) on JDK 21 must update; the wrapper bumps automatically on next invocation.
- **Risk**: low — Gradle 9.5 keeps the Groovy build script DSL, all current plugins advertise 9.x support, and our build does not depend on any of the APIs Gradle 9 removed. Rollback is a one-line `distributionUrl` revert.
- **Verification**: `./gradlew --warning-mode all clean build` must complete green; `./gradlew generateJooq` must still produce the same outputs (diff `src/main/java-generated/` after regen).
