## Context

Metric values are produced per test case during a run's metric-evaluation phase and persisted in the analytics table `test_case_eval_summaries` (`metric_values` JSONB = `{metricName: {outputField: numeric}}`), tagged with a `computation_id`. The only existing aggregation, `EvalSummaryService.aggregate()` / `PostgresEvalSummaryRepository.aggregate()`, is on-demand and limited to AVG/MIN/MAX/COUNT — it cannot produce median or percentiles, which the Single-Run dashboard's `avg / med / p10 / p90 / min / max` toggle and "Overall score" card require.

The experimental Query DSL (`com.epam.aidial.evaluation.experimental.query`) already:
- supports `avg`, `min`, `max`, `percentile_cont`, `percentile_disc` aggregate functions;
- registers `eval_summaries` as a queryable analytics entity whose **detailed schema** flattens `metric_values` into numeric `metric:<name>:<field>` columns (resolved via `JsonbFieldResolver`, the JSONB-numeric path pattern);
- serializes a `StructuredQuery` to/from JSON end-to-end.

The one missing DSL feature is `ParamExpr`: it exists in the sealed `Expr` model but `ExprTranslator` rejects it ("not yet implemented"). This change implements it and builds the metric-score feature on top.

This is a cross-cutting change: a DSL capability extension, an analytics data model addition, a new run phase, and a new API surface.

## Goals / Non-Goals

**Goals:**
- Define the per-metric statistics (AVG/P10/P90/MIN/MAX) **in code** as self-contained `StructuredQuery` objects (`BuiltInMetricStatistics`). The `overall` definition is a per-suite property (`test_suites.overall_score`), snapshotted per run.
- Compute statistics (AVG, P10, P90, MIN, MAX) per numeric metric output field automatically at run-end, plus a DSL-computed run-level `overall` resolved from the suite snapshot (custom per-suite expression, or a single-metric default), into a new `metric_score_result` analytics table keyed by the run's `computation_id`.
- Implement `ParamExpr` in the DSL via a single substitution pre-pass (`QueryParameterResolver`), and make the function catalog registry-driven (adding the `mean` reduction), without changing behaviour for existing entity repositories or the public `/queries/execute` endpoint.
- Expose computed results to the frontend only via the unified Query DSL entity `metric_score_results` (no dedicated read endpoint). Statistics are code-defined — no management API.

**Non-Goals:**
- Standalone "recompute scores only" endpoint (deferred; storage is designed to enable it later with zero rework).
- Per-test-case overall score and the pass/fail "Cases passed" threshold (per-case concern, not a run-level aggregate).
- Weighted / group-selectable `overall` (needs arithmetic functions; a richer per-suite "score config" compiled to a `StructuredQuery` — today `overall_score` stores the raw expression) and prev/base run comparison deltas (frontend concern, satisfied by per-run queryability).
- Exposing `ParamExpr` on the public `POST /api/v1/queries/execute` endpoint (stays paramless).

## Decisions

### D1. ParamExpr via a single substitution pre-pass (not threaded through translation)
A `Map<String,Expr>` binds each param name to a concrete `Expr`. A dedicated **`QueryParameterResolver`** rewrites the `StructuredQuery` into a **parameter-free copy before translation**: each `ParamExpr` is replaced with its bound `Expr`, recursively (a bound `FieldExpr` becomes a column incl. JSONB `metric:<name>:<field>` paths; a bound `ValueExpr` becomes a jOOQ bind value once translated). Unbound param → `ValidationException` (HTTP 400); param→param bindings and cyclic binding chains are forbidden (HTTP 400). The translator/builder/executor/repository are **parameter-agnostic** — no `Map<String,Expr> params` argument is threaded through them.
- **Why a pre-pass, not threading:** substitution is context-free (it needs only the name→`Expr` map, nothing from the field-binding/SQL layer), so isolating it in one recursive pass keeps the hot translation path clean and puts all param logic — and validation — in a single place. `ParamExpr` can appear only in `select` expressions, `filter`, and `having`, so the walker is small and complete.
- **Invocation:** `QueryParameterResolver.resolve(query, params)` runs once at the `StructuredQueryService.execute(query, params)` entry; the resolved query is dispatched to the (paramless) repository. An empty map is a no-op (identity); the public paramless endpoint thus leaves any `param` in place, which `ExprTranslator` rejects with a defensive 400.
- **Alternative considered & rejected:** thread an optional `Map<String,Expr> params` through `ExprTranslator.toField`/`FilterTranslator`/`StructuredQueryBuilder`/`StructuredQueryExecutor`/`StructuredQueryRepository` and substitute at the bottom of the call chain. Rejected — it spread a `params` argument across ~8 method signatures for a context-free transform; the pre-pass achieves the same behavior (byte-identical SQL, regression-tested) without polluting the translation layer.

### D2. Statistic queries are full, self-contained `StructuredQuery` objects built in code
Each built-in statistic is a complete `StructuredQuery` — aggregate select **and** the run-scoping filter (`test_suite_run_id eq :runId AND computation_id eq :computationId`) — with `:runId`, `:computationId` as `ParamExpr`, plus `:metricField` (per-metric leaf stats), and the percentile fraction baked as a literal `ValueExpr`. The default run-level `overall` is the single metric's `avg(:metricField)`; a custom per-suite `overall` is a self-contained expression over the configured metric columns (D5). These objects are **constructed in code** (`BuiltInMetricStatistics`, package `experimental.query.service.metricscore`); the per-suite `overall_score`/default lives per D5.
- **Why:** the catalog is a fixed, code-owned set (no management API, no per-row editing), so defining the queries as typed objects is compile-checked, while the filter/params stay data-driven for a future recalculation (bind params → execute). `runId`/`computationId` remain *params* so each query is a reusable template, never bound to a specific run.
- **Alternative considered:** persist the statistics in a configuration table loaded at run time. Rejected — for a fixed code-owned catalog that adds a table, a migration, generated jOOQ, and a model/mapper/repository with no payoff (the rows would never be edited or managed).

### D3. Only computed results are a table (analytics); statistics are code
`metric_score_result` (computed) lives in **analytics** alongside `eval_summaries`. The per-metric statistic queries are code-defined (D2) and the `overall` definition is a per-suite property on `test_suites` (D5).
- **Why:** results are computed analytics data, co-located with the `eval_summaries` they aggregate. The statistics are a fixed code catalog, so they need no datasource.
- The result repository uses `@Qualifier("analyticsDsl")`, written append-only via the `PostgresEvalSummaryRepository.saveAll` batch pattern through `MetricScoreService.saveAll` (`@Transactional("analyticsTransactionManager")`).

### D7. Phase 3 executes the code-defined DSL query; layering kept intact via an inverted trigger interface
Phase 3 executes each code-defined per-metric statistic's `StructuredQuery` through `StructuredQueryService.execute(query, params)` (binding `runId`/`computationId`/`metricField` via `ParamExpr`, D1) once per metric field, and separately executes the run-level `overall` (from the suite snapshot, D5) — this is the feature's original premise ("use the query DSL for metric statistics"), so the queries and `ParamExpr` are live, not vestigial. The per-metric statistics are uniformly leaf queries (all reference `:metricField`) provided by `BuiltInMetricStatistics.perMetric()`; `overall` is a distinct run-level step driven by `MetricScoreComputationContext.overallExpression` (the snapshot's `overall_score`, or the code-defined `BuiltInMetricStatistics.defaultOverall()` when null). The default overall is `avg(:metricField)` bound to the single field (computed only for a single-metric run); a non-null custom `overall_score` is a self-contained JSON expression parsed and run with only the run-scoping params (dormant today; no API sets it).
- The computation must touch `experimental.query.service` (the DSL), but the run job (`TestSuiteEvaluationJob`) is stable `service` and cannot move. **Resolution (chosen): dependency inversion** — the executor (`MetricScoreComputationExecutor`) lives in `experimental.query.service.metricscore`, where its use of `StructuredQueryService` is intra-layer; it implements a one-method `MetricScoreComputation` interface declared in `service.domain.job`. The job depends only on that interface (its `MetricScoreComputationContext` also stays in `service`), so there is **no `service → experimental.query.service` bytecode edge** and `LayeredArchitectureTest` is left **unchanged** (no rule relaxed). `experimentalService → service`/`data` (the executor reading repos and the interface/context) is already permitted by the guard.
- **Trade-off:** one thin trigger interface in `service` is the seam. Accepted as the minimal, boundary-preserving inversion; preferred over relaxing the architecture guard.
- **Alternatives considered & rejected:** (a) relax `LayeredArchitectureTest` to allow `service → experimentalService` — rejected to keep the experimental boundary enforced; (b) decouple the trigger via a Spring `ApplicationEvent` — works with zero interface but adds indirection and synchronous-ordering concerns around the COMPLETED transition; (c) a dedicated raw-jOOQ `MetricScoreAggregationRepository` bypassing the DSL — rejected because it left `ParamExpr` and the stored `expression` unused, defeating the feature's purpose.

### D4. Phase 3 in the run job, reusing Phase 2's computation_id
A new `MetricScoreComputationExecutor` (`@Component` in `experimental.query.service.metricscore`, implementing the `service`-layer `MetricScoreComputation` interface — see D7) runs as Phase 3 in `TestSuiteEvaluationJob`, after metric evaluation (Phase 2). It reuses the **same** `computation_id` produced for Phase 2, so results join the run's computation. It discovers numeric metric output fields from `RunMetricSnapshot.outputSchema`, then for each code-defined statistic binds `:metricField` per field (per-metric stats), and additionally runs the `overall` step (default = the single field's `avg(:metricField)`; D5), executes via `StructuredQueryService`, reads the single aliased `value`, and batch-writes results.
- **Why reuse computation_id:** readers resolve `latest` via the existing `ComputationResolver`; a mismatched id would orphan the scores.
- **Failure handling:** Phase 3 is **non-fatal** — any failure logs and the run still transitions to `COMPLETED` (scores are regenerable). Per-`(def × field)` execution catches `ValidationException` (e.g. JSONB numeric-cast failure surfaced as HTTP 400 by `StructuredQueryExecutor`) and continues, so one bad metric field doesn't abort the whole computation. Honors the run's `cancellationSignal`.

### D5. `overall` is a per-suite definition, snapshotted, computed through the DSL
`overall` is **per-test-suite** configuration. The suite stores a nullable `test_suites.overall_score` JSONB column (a `StructuredQuery` expression); `SuiteSnapshotBuilder` captures it **verbatim** into the suite snapshot (new `overallScore` field on `SuiteSnapshotDto`, backward-compatible — no version bump, legacy/null → default). Phase 3 reads it from the snapshot via `MetricScoreComputationContext.overallExpression` (threaded by `TestSuiteEvaluationJob`, which already holds the resolved snapshot) — the executor needs no meta/snapshot access. Computation flows **through the Query DSL**, written as a single `metric_score_result` row (`metric_score_name = metric_name = overall`).
- **Default behavior (single-metric guard):** when the suite has no custom `overall_score` (snapshot value null), the executor uses the **code-defined default** (`BuiltInMetricStatistics.defaultOverall()` = `avg(:metricField)`), computed **only when the run resolves to exactly one numeric metric field** — `overall` is then that single metric's average, and the executor binds `:metricField` to that field. With more than one field the default is ambiguous (averaging disparate metrics is meaningless until the user picks which to include) → **no `overall` row**.
- **Custom (future):** a non-null `overall_score` is a self-contained expression referencing the real configured metric columns, run with only the run-scoping params (no executor-built placeholders), regardless of metric count. This is deferred: the dynamic `metric:<tsmd>:<field>` JSONB columns are not yet authorable through the query schema, so authored custom expressions cannot translate end-to-end yet. The executor branch and snapshot field are in place as the hook.
- **Why the default is code-defined, not a pre-resolved suite value:** the single-metric semantics depend on the run's metric count, known only at Phase 3 — so the snapshot pins the *config* (null = default, non-null = explicit), not a pre-resolved expression. Suites are not DB-seeded with the default; `overall_score` stores only a custom override.
- **Why `overall` is per-suite, not a built-in statistic:** `overall` is conceptually suite-specific (which metrics, eventually weights), unlike the generic per-metric statistics that apply to every metric of every run. Putting it on the suite + snapshot lets each run compute `overall` per the suite's config at run time, exactly like template/bindings/metrics are snapshotted, and seeds the future per-suite metric-selection work.
- **Not yet editable:** setting `overall_score` is **not** exposed on the suite API in this version (it is dropped from `TestSuiteRequestDto`/`ResponseDto` and the mapper's DTO wiring); the column + `SuiteSnapshotDto.overallScore` field + `MetricScoreComputationContext.overallExpression` + the executor's non-null branch remain as the dormant future hook (the executor "reads the snapshot value; if empty, runs the default"). A non-null `overall_score` is a JSON expression parsed at run time. A richer "score config" (modes/weights) + compiler is deferred.
- **Extension window:** a weighted/selective `overall` is authored as a richer per-suite `overall_score` expression once arithmetic functions (`add/subtract/multiply/divide`, optional `weighted_mean`) are added as `QueryFunction` beans (D8) — no engine changes, just new function components.

### D8. Function catalog is registry-driven (`QueryFunction` SPI), not a hardcoded switch
`ExprTranslator`'s former name→jOOQ `switch` is replaced by a `QueryFunctionRegistry` that collects `QueryFunction` beans by name (mirrors the bean-collection pattern of `StructuredQueryService`/`QueryEntityRegistry`). Each built-in (`lower/upper/length/trim/abs/width_bucket/count/sum/avg/min/max/percentile_cont/percentile_disc`) is a bean (`BuiltInQueryFunctions`); `mean` is added as `MeanFunction`. A `FunctionContext` exposes the recursive `toField`, param substitution, bindings, and args. Unknown name → `ValidationException`.
- **Why:** the user requirement — adding a function later must be "drop in a `@Component` and the engine uses it," with no central edits. Makes the weighted-`overall` extension (D5) purely additive.
- **Trade-off:** more classes than a switch; accepted for the extensibility payoff and testability (each function is unit-testable in isolation). Existing render tests act as a migration regression guard.

### D6. API shape
- Read: **only** via the unified Query DSL entity `metric_score_results` (`POST /api/v1/queries/execute`) — no dedicated metric-score-results REST endpoint. The generic engine is computation-agnostic, so the entity's repo resolves the `computation_id eq "latest"` sentinel: `MetricScoreLatestComputationDefaulter`, for a single-run query (`test_suite_run_id eq <uuid>`), pulls the single `computation_id` value out of the filter and — when it is `"latest"` — calls `ComputationResolver.resolve("latest", runId)` (the single authority for "latest", shared with the eval-summary path) and swaps the resolved id back in before translation, so `"latest"` is never UUID-parsed. Explicit `computation_id` (eq `<uuid>`/`in`) and an omitted `computation_id` (spans all computations) pass straight through.
- Statistics: **code-defined**, no management API. `BuiltInMetricStatistics` exposes `perMetric()` + `defaultOverall()`, consumed by the Phase-3 executor.
- `MetricScoreService` exposes only `saveAll` (the Phase-3 executor's write path); `metric_name` is stored as the frontend-friendly `<metricGroup>.<outputField>` (DSL token `metric:<tsmd>:<field>` stays internal).
- `MetricScoreConstants` holds the reserved param names, `value` alias, entity, and run-scoping field names; reuse `EvalSummaryExportColumnConstants` for metric-field tokens.

## Risks / Trade-offs

- **Threading `params` through the DSL breaks existing entity queries** → add overloads defaulting to `Map.of()`; add a regression unit test asserting paramless queries produce byte-identical SQL; existing `test_suites`/`eval_summaries` repos forward the empty map.
- **Percentile/AVG over JSONB-extracted numeric may be unstable in aggregate mode** (`percentile_cont … WITHIN GROUP` over a `JsonbFieldResolver` numeric path) → verified structurally during exploration; per-`(def × field)` fault isolation contains runtime cast errors. Fallback: compute P10/P90 engine-side from a ROW-mode query that selects raw `metric:<name>:<field>` values + percentile in Java — a localized change behind the seed/engine seam.
- **computation_id reuse depends on hoisting it out of `buildMetricEvaluationContext`** → if missed, Phase 3 writes under a new id and scores won't resolve as `latest`. Covered by a functional test asserting result `computation_id` equals the run's.
- **Code-defined statistic queries drifting from the wire contract / `MetricScoreConstants`** → `BuiltInMetricStatisticsTest` asserts each built-in query is an aggregate `value` query over `eval_summaries` referencing the expected params; typed objects are compile-checked (no JSON literals to drift).
- **Append-only with `ON CONFLICT DO NOTHING`** means a same-computation re-insert is silently skipped (fine for v1: each run computes once). A future recompute feature will require upsert/replace semantics — noted, not built.
- **Non-fatal Phase 3** means a run can be `COMPLETED` with missing scores → surfaced via logs (exception as last SLF4J arg) and the absence of result rows; acceptable since scores are regenerable.

## Migration Plan

1. The per-metric statistic queries are code-defined (`BuiltInMetricStatistics`). The only metric-score meta migration is `V1.23__AddOverallScoreToTestSuites.sql` (nullable `test_suites.overall_score` JSONB). The computed-results table is `V1.10__CreateMetricScoreResultTable.sql` under `db/migration/analytics/POSTGRES/` (PK `id` + unique `(test_suite_run_id, computation_id, metric_score_name, metric_name)`); it carries no audit/computation timestamps — the result joins its computation via `computation_id`, and "latest" is resolved from `run_metric_snapshots`.
2. Run `./gradlew generateJooq`; commit the generated `MetricScoreResult*` sources under `src/main/java-generated/.../jooq/analytics/`.
3. Ship DSL `ParamExpr` support (D1) and the analytics result layer before wiring Phase 3 (D4).
4. **Rollback:** drop the result table / revert migrations; Phase 3 is additive and non-fatal, so reverting the executor leaves runs functioning. The `ParamExpr` translator change is backward compatible (empty-param default).
5. Update `docs/database-schema.md`, `openspec/specs/README.md`, and note `ParamExpr` support in `AGENTS.md`. No new config property expected.
