## Why

The only aggregation over evaluation results today is `EvalSummaryService.aggregate()` — computed on-demand and limited to AVG/MIN/MAX/COUNT, so it **cannot** produce median or percentiles, which the Single-Run dashboard requires (its `avg / med / p10 / p90 / min / max` toggle and the per-run "Overall score" card). We need richer, stable, per-run aggregated metric statistics, and a way to let users define custom scores — reusing the existing experimental Query DSL, which already supports `percentile_cont`/`percentile_disc` and can aggregate over the `eval_summaries` entity's flattened `metric:<name>:<field>` JSONB columns.

## What Changes

- Introduce **code-defined metric-score statistics**: reusable Query-DSL queries describing an aggregated metric statistic, constructed as typed `StructuredQuery` objects in `BuiltInMetricStatistics` (no database table).
  - The predefined per-metric stats (`AVG`, `P10`, `P90`, `MIN`, `MAX`) are defined in code and applied to every run, evaluated once per numeric metric output field.
  - The run-level **`overall`** is **per-test-suite** configuration, stored on the suite (`test_suites.overall_score`) and snapshotted per run (see below).
- Each statistic is a **full, self-contained `StructuredQuery`** (aggregate select + run-scoping filter) with `:runId`, `:computationId` plus `:metricField` (per-metric leaf stats) as **`ParamExpr` params** (a reusable template, never a hardcoded run id). The default `overall` is the single metric's `avg(:metricField)`. This keeps a future *independent score recalculation* fully data-driven.
- Implement **`ParamExpr` support** in the Query DSL (currently rejected by the translator) via a **single substitution pre-pass** (`QueryParameterResolver`): a `Map<String,Expr>` binding; the resolver rewrites the query into a parameter-free copy (replacing each `param` with its bound `Expr`, recursively) before translation, so the translator/builder stay parameter-agnostic. The public `POST /api/v1/queries/execute` endpoint stays **paramless** by design.
- Make the DSL **function catalog registry-driven** (`QueryFunction` SPI + `QueryFunctionRegistry`) so the engine is no longer a hardcoded `switch`: every built-in becomes a bean, and adding a function later means dropping in a new `@Component` — no edits to the translator. Add one new function now, **`mean`**, a reduction over an `ArrayExpr` (folds `(e₁+…+eₙ)/n`), enabling `overall` to be computed through the DSL.
- Add a **Phase 3** to the test-suite-run job (`TestSuiteEvaluationJob`), after metric evaluation, that takes the code-defined per-metric statistics, enumerates the run's numeric metric output fields (from `RunMetricSnapshot.outputSchema`), and **executes each statistic's `StructuredQuery` via `StructuredQueryService`** over the run's eval summaries for the run's existing `computation_id`, persisting results (`:metricField` → one execution per metric field). It additionally runs the run-level `overall` (resolved from the suite snapshot, threaded via `MetricScoreComputationContext.overallExpression`); the default binds `:metricField` to the run's single metric field. The executor lives in `experimental.query.service.metricscore` (so its use of the DSL is intra-layer) and implements a one-method `MetricScoreComputation` interface in the stable `service` layer; the run job triggers Phase 3 through that interface, so no `service → experimental.query.service` dependency is introduced and `LayeredArchitectureTest` is unchanged. Score-computation failure is **non-fatal** to the run.
- Make `overall` a **per-test-suite** property: add a nullable `test_suites.overall_score` JSONB column (a `StructuredQuery` expression) captured verbatim into the suite snapshot, so each run computes `overall` per the suite's config at run time. **Setting a custom value is not exposed via the API yet** (reserved extension point) — the column stays null and `overall` always uses the built-in default, computed **through the DSL** as the single metric's average (`avg(:metricField)`) and **only for single-metric runs**; with more than one metric field the default yields no `overall` (deferred to future per-suite metric selection). The Phase-3 executor already resolves the expression from the snapshot and would run a non-null self-contained custom one if present, so enabling per-suite custom later is additive.
- Add a new analytics table **`metric_score_result`** (append-only per computation). Results are exposed to the frontend **only** via the unified Query DSL entity `metric_score_results` (no dedicated REST endpoint); a single-run query requests the latest computation with `computation_id eq "latest"`, resolved to a concrete id by the existing `ComputationResolver` before translation (omitting `computation_id` spans all computations).
- The per-metric statistics are **code-defined** (`BuiltInMetricStatistics`) and not editable through any management API. The Phase-3 computation reads them directly from code.

**Non-goals (v1):** any HTTP API to author/list/delete the per-metric statistics (code-defined); a richer per-suite "score config" UI/compiler beyond storing the raw `overall_score` expression; standalone "recompute scores only" endpoint (storage is designed to enable it later with zero rework); per-test-case overall score + pass/fail "Cases passed" threshold; weighted/group-selectable overall; prev/base run comparison deltas (a frontend concern satisfied by results being queryable per run).

## Capabilities

### New Capabilities
- `metric-score-statistics`: code-defined Query-DSL per-metric statistics (`BuiltInMetricStatistics`), a per-suite `overall` definition reserved on the test suite (`overall_score`) and snapshotted per run, automatic Phase-3 computation at run-end into `metric_score_result` (per-metric stats + the DSL-computed default `overall`), and read-back via the `metric_score_results` Query DSL entity (`computation_id eq "latest"` resolves to the run's latest computation). (No dedicated read endpoint, no management API; `overall` API exposure deferred — default-only for now.)

### Modified Capabilities
- `structured-query-model`: implement `ParamExpr` via expression-substitution parameter binding (previously an explicitly-rejected feature); add an `execute(query, params)` path while keeping the public execute endpoint paramless; make the function catalog **registry-driven** (`QueryFunction` SPI) and add the `mean` array-reduction function.

## Impact

- **Database:** the per-metric statistics are code-defined in `BuiltInMetricStatistics` (no configuration table). `test_suites` gains a nullable `overall_score` JSONB column (`db/migration/meta/POSTGRES/V1.23__AddOverallScoreToTestSuites.sql`); `metric_score_result` (computed) is created in **analytics** (`db/migration/analytics/POSTGRES/V1.10__CreateMetricScoreResultTable.sql`). Requires `./gradlew generateJooq` + committing the generated `metric_score_result` sources under `src/main/java-generated/.../jooq/analytics/`. Update `docs/database-schema.md`.
- **Query DSL** (`com.epam.aidial.evaluation.experimental.query`): new `QueryParameterResolver` (in `service.translate`) resolves `param` expressions in a single pre-pass at the `StructuredQueryService.execute(query, params)` entry; `ExprTranslator`, `FilterTranslator`, `StructuredQueryBuilder`, `StructuredQueryExecutor`, `StructuredQueryRepository` stay parameter-agnostic (no threaded `params`). New `service.translate.function` package: `QueryFunction` SPI, `QueryFunctionRegistry`, `FunctionContext`, `BuiltInQueryFunctions` (one bean per built-in), and `MeanFunction`.
- **Run flow** (`service.domain.job`): new `MetricScoreComputationExecutor` + Phase-3 hook in `TestSuiteEvaluationJob`; hoist the Phase-2 `computationId`/`computedAtMs` so Phase 3 reuses them.
- **New analytics layer artifacts:** model `MetricScoreResult`, its RecordMapper, and repository (`@Qualifier("analyticsDsl")`, `@Transactional("analyticsTransactionManager")`); reuse `PostgresEvalSummaryRepository.saveAll` batch pattern and `ComputationResolver`.
- **Write path:** `MetricScoreService.saveAll` persists the Phase-3 output. No dedicated read controller/DTO/mapper.
- **Read API (unified Query DSL only):** results are exposed as the `metric_score_results` queryable entity (schema provider + `StructuredQueryRepository` on `analyticsDsl`), readable/aggregatable via `POST /api/v1/queries/execute`. The entity's repo resolves the `computation_id eq "latest"` sentinel (`MetricScoreLatestComputationDefaulter` + `ComputationResolver`) for a single-run query, swapping in the concrete latest id before translation; `computation_id eq <uuid>`/`in` and an omitted `computation_id` (all computations) pass through. The generic engine itself stays computation-agnostic.
- **New constants:** `MetricScoreConstants` (types, reserved param names, stat names, `value` alias, entity); reuse `EvalSummaryExportColumnConstants` for metric-field tokens.
- **No new config properties expected** (revisit only if a Phase-3 enable/timeout flag is added → then update `docs/configuration.md`).
- **Docs/specs:** update `openspec/specs/README.md` (new `metric-score-statistics` spec), and note in `AGENTS.md` that `ParamExpr` is now supported and `/queries/execute` stays paramless.
