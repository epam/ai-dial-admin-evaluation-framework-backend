## Context

`TestSuiteRunService.createRun` is the existing model for "create a run and dispatch async work": it runs guard checks, saves a `TestSuiteRun` (status `PENDING`) inside a single `@Transactional("metaTransactionManager")` method, and registers a `TransactionSynchronizationManager` `afterCommit` callback that only fires once that transaction has actually committed — the callback registers a cancellation signal and calls `TestSuiteEvaluationJob.executeRunAsync(runId, token)` asynchronously. Deferring dispatch to `afterCommit` matters: the async job thread reads the run by id on its own connection, and if dispatch happened before commit, it could race a not-yet-visible row.

`TestSuiteEvaluationJob.executeRunAsync` drives three phases: snapshot (writes `TestCaseRunInput` rows + `suite_snapshot`), Phase 1 (`EvaluationExecutor` — actual deployment invocation, writes `TestCaseRunResult`), Phase 2 (`MetricEvaluationExecutor` — calls the metric provider, writes `RunMetricSnapshot` + `EvalSummary`), Phase 3 (`computeMetricScores` — pure SQL aggregation over `EvalSummary`/`RunMetricSnapshot`, writes `MetricScoreResult`, non-fatal on failure). Critically, `resolveSnapshot(run)` (used by Phase 3's `computeMetricScores`) already falls back to synthesizing a snapshot live from the current `TestSuite`+`Dataset` whenever `run.getSuiteSnapshot()` is null — this is the existing "legacy run" code path, and it means a run that never went through the snapshot phase is already handled correctly by unmodified Phase 3 code.

`AnalyticsResultService.batchCreate` (`POST /api/v1/analytics/test-case-results`) is the existing precedent for writing `TestCaseRunResult` rows without any deployment invocation: it loads the (already-existing) `TestSuiteRun` inside an `@Transactional("analyticsTransactionManager")` method, validates the batch, maps `TestCaseRunResultItemDto` → `TestCaseRunResult` via `TestCaseRunResultMapper`, and calls `TestCaseRunResultRepository.saveAll`. It does not run response-column extraction — callers must pre-populate `extractedColumns`/`extractionWarnings`. `ResponseColumnExtractor.extract(responseColumns, responseBody)` is the existing, reusable extraction component (JSONata evaluation + type reconciliation), otherwise only invoked from the live Phase-1 path.

This project's dual-datasource constraint (`docs/patterns/dual-datasource.md`) is explicit: the two transaction managers do not federate, so a single Spring `@Transactional` cannot atomically span both a `TestSuiteRun` write (meta) and a `TestCaseRunResult` write (analytics). Any design here must accept that and make the analytics-side write recoverable rather than pretend it's atomic with the meta-side write.

## Goals / Non-Goals

**Goals:**
- One HTTP request creates a `TestSuiteRun`, persists a batch of caller-supplied eval results as `TestCaseRunResult` rows (with server-side response-column extraction), and asynchronously runs Phase 2 (metric evaluation) + Phase 3 (score computation) against them.
- The import item shape mirrors exactly what a live Phase 1 invocation produces (minus the DB-internal ids/timestamps assigned at persistence time) — see Decision 4 (revised). This lets the same payload work whether Phase 1 ran inside EF or was produced "somewhere else" entirely.
- Reuse existing guard/validation/extraction/mapping components wherever the shape matches; only add what's genuinely new (in-batch duplicate detection, a Phase-2/3-only job method).
- Keep the meta-write (run) and analytics-write (results) failure modes recoverable without a 2-phase commit: if the analytics write fails after the run is committed, the run is explicitly marked `FAILED` rather than left orphaned in `PENDING`.

**Non-Goals:**
- Re-running or backfilling response-column extraction for results imported via the existing `AnalyticsResultService.batchCreate` endpoint — out of scope.
- Any new "run kind" concept in the data model. Nothing downstream needs to branch on whether a run was imported vs. executed (`executeRunAsync`'s `skipDeploymentPhase` flag is passed explicitly by the caller, not derived by inspecting the run; `cancelRun`/`deleteRun` only ever check `status`) — a `run_source` column was considered and rejected as unnecessary.
- CSV/bulk-file import of eval results. This change accepts a JSON batch (mirroring `BatchWriteRequestDto`'s shape); file-based import is a separate concern if ever needed. (Revised post-archive: this Non-Goal was superseded by Decision 7, which switched the endpoint to CSV/multipart — see Decision 7 for the full rationale.)
- Any change to the CSV import path's own test-case data validation (`TestCaseValidationService`/`SchemaTypeCoercer`) or to `TestCase.data` already stored in the DB for other flows — both remain fully unchanged. (Revised post-implementation: this change *does* validate caller-supplied `testCaseData` against the dataset's schema at import time via `SchemaValidationService`/`DatasetSchemaProvider` — see Decision 4's "Schema validation" addendum below — since the initial "no validation, just trust it" framing here was superseded.)

## Decisions

### 1. Single endpoint, two sequential transactions, dispatch deferred to `afterCommit`

`POST /api/v1/test-suites/{testSuiteId}/runs/import` maps to `TestSuiteRunService.importResultsAndEvaluate(UUID testSuiteId, String testRunName, InputStream csv, long contentLength, char delimiter)`, annotated `@Transactional("metaTransactionManager")`. Its transactional body does **only meta-side work**:
- Suite guards, same style as `createRun`: not-found, unbound-dataset, config-invalid (`!testSuite.isValid()`).
- CSV parsing via `evalResultsCsvImportService.parse(testSuite.getDatasetId(), csv, contentLength, delimiter)`, producing `List<TestCaseRunResult>` stubs (see Decision 7 / task 15 for the full parse → inline-validation → schema-validation flow inside the parser).
- Structural batch validation that needs no DB read, via `evalResultsImportService.validateBatch(results)`: non-empty batch, batch size vs. `analyticsProperties.getBatch().getMaxItems()`, no duplicate `(testCaseId-or-name, runIndex)` within the batch, `completedAt >= startedAt` per item. (Schema validation and `testCaseData` checks are handled by `parse`, not `validateBatch` — see Decision 2 and Decision 4.)
- **No `TestCase`/dataset lookup at all** (revised — see Decision 4). `testCaseId`/`testCaseName` are caller-trusted identity labels, not resolved against `TestCaseRepository`.
- Concurrency guards (`countByStatuses`, `countByTestSuiteIdAndStatuses`) and run-name uniqueness handling — identical to `createRun`.
- Saves the `TestSuiteRun` (`status=PENDING`, `runConfig="{}"`, `numberOfTestCases=results.size()`).
- Registers a `TransactionSynchronizationManager.registerSynchronization` `afterCommit` callback — **the only place analytics-side work happens** — carrying the run and the validated `List<TestCaseRunResult>`.

The `afterCommit` callback (runs only once the run row is durably committed):
1. Calls `EvalResultsImportService.persistResults(UUID testSuiteId, TestSuiteRun run, List<TestCaseRunResult> items)` — a **new sibling service**, `@Transactional("analyticsTransactionManager")` — which for each `TestCaseRunResult` stub: fills in run-context fields (`id = UUID.randomUUID()`, `testSuiteRunId`, `testSuiteId`, `createdAtMs`) via `.toBuilder()` and persists `extractedColumns`/`extractionWarnings` verbatim from the caller-supplied CSV stubs (defaulting to `{}`/`[]` when absent), then batches via `TestCaseRunResultRepository.saveAll`. No `ResponseColumnExtractor.extract` call is made — the caller pre-computes and supplies extracted columns via the optional `extractedColumns`/`extractionWarnings` CSV columns (consistent with the existing `AnalyticsResultService.batchCreate` precedent). (Revised post-implementation: the initial design had `persistResults` deserializing `responseColumnsJson` and calling `ResponseColumnExtractor.extract` per item; this was superseded when Decision 7 switched to CSV with optional caller-supplied extraction columns — see Decision 3, revised.)
2. If that throws, calls `testSuiteRunRepository.updateToFailed(...)` directly (a plain repository call, auto-committed on its own connection — no ambient transaction is active at this point since `afterCommit` runs outside the meta transaction's scope) and notifies SSE, then stops — **no dispatch**.
3. On success, registers the cancellation signal and calls `TestSuiteEvaluationJob.executeRunAsync(runId, null, true)` directly — same `RejectedExecutionException` → `updateToFailed` handling `createRun` uses for its own dispatch, duplicated rather than shared (see Decision 5).

**Why this shape, not a single self-contained method or a new orchestrator class**: Spring's `@Transactional` is proxy-based and does nothing on same-class self-invocation (`this.otherAnnotatedMethod()` bypasses the proxy entirely). Wrapping the *whole* flow in one `@Transactional("metaTransactionManager")` method that also calls out to the analytics write mid-transaction would nest the analytics write inside the still-open meta transaction, and — worse — if dispatch happened before the meta transaction commits, the async job thread could race a not-yet-visible run row (exactly the reason `createRun` already defers to `afterCommit`). Extending the *same, already-established* `afterCommit` pattern with one extra step (the analytics persist) reuses a pattern already proven correct in this codebase, avoids introducing a new orchestrator class purely to dodge self-invocation, and keeps the failure-compensation logic (mark `FAILED` on analytics-write failure) exactly where `createRun`'s own failure compensation already lives.

**Alternative considered**: a separate `createImportRun` step (meta tx) + separate `EvalResultsImportService.persistResults` call + separate `triggerEvaluation` step, orchestrated by the controller calling three service methods in sequence. Rejected per explicit user feedback during planning — the goal is one HTTP request, and three backend calls behind one endpoint is unnecessary ceremony once the `afterCommit`-callback shape achieves the same transactional safety in one call.

### 2. New sibling service `EvalResultsImportService`, not a method on `TestSuiteRunService`

The analytics-side write (extraction + mapping + `saveAll`) lives in its own `@Service` class rather than as another method on `TestSuiteRunService`, for two reasons: (a) it needs `@Transactional("analyticsTransactionManager")`, a different qualifier than the rest of `TestSuiteRunService`'s methods, and putting mixed-datasource `@Transactional` methods on one class is exactly the kind of thing `docs/patterns/dual-datasource.md`'s "cross-datasource service calls" rule warns about; (b) calling it from the `afterCommit` callback goes through its own Spring proxy normally (it's a different bean), sidestepping the self-invocation problem entirely — no special wiring needed.

**Revised (folded `EvalResultsImportRunService.validateBatch` in — see Decision 5/11, further revised below)**: `EvalResultsImportService` now also owns `validateBatch`/`testCaseIdentity` — plain (non-`@Transactional`) methods that validate the batch (structural checks: empty batch, max-batch-size, in-batch-duplicate, `completedAt >= startedAt`, missing identity) before any run is created. Dataset-schema validation is **not** part of `validateBatch` — it moved into `EvalResultsCsvParser.parse` (see Decision 15 / task 15 below), which validates each row's `testCaseData` against the dataset schema inline during CSV parsing, before the parsed `List<TestCaseRunResult>` is ever handed to `validateBatch` or the service layer. This does not reintroduce the mixed-datasource-transactional-method problem this decision originally guarded against: `validateBatch` carries no transaction annotation of its own, so when `TestSuiteRunService.importResultsAndEvaluate` calls it, it simply runs inside that caller's already-open `metaTransactionManager` transaction — `persistResults` remains the only method on this class actually annotated `@Transactional("analyticsTransactionManager")`. The class now has two responsibilities (pre-persistence structural validation, called synchronously before the run is saved; and result persistence, called later from `afterCommit` in its own transaction) rather than one, which is a mild domain-boundary trade-off accepted in exchange for not introducing a third service purely to host a handful of plain validation methods.

### 3. Response-column extraction happens at import time, not deferred to Phase 2/3 (Revised — superseded by Decision 7; see also the caller-supplied extraction note below)

`ResponseColumnExtractor.extract(responseColumns, responseBody)` is called once per item inside `EvalResultsImportService.persistResults`, using the suite's `responseColumns` (same `JsonbMapper.mapResponseColumns` deserialization `SuiteSnapshotBuilder` already uses). This means the `skipDeploymentPhase=true` branch of `executeRunAsync` needs zero extraction-aware logic — it just runs Phase 2 + Phase 3 exactly as the live-run branch already does, over rows that already look exactly like Phase-1 output.

**Revised (post-archive, Decision 7 / task 15)**: `persistResults` does NOT call `ResponseColumnExtractor.extract`. The switch to CSV import introduced `extractedColumns` and `extractionWarnings` as optional reserved CSV columns — the caller pre-computes and supplies them; `persistResults` persists them verbatim (defaulting to `{}`/`[]` when absent). This is consistent with the existing `AnalyticsResultService.batchCreate` precedent (callers pre-populate `extractedColumns`/`extractionWarnings`). The `skipDeploymentPhase=true` path of `executeRunAsync` still needs no extraction-aware logic — Phase 2/3 operate on whatever extracted columns were persisted, exactly as designed in this decision.

### 4. `testCaseData` is caller-supplied and trusted, not resolved from an existing `TestCase` row (revised post-implementation)

The initial implementation deliberately excluded `testCaseData` from `EvalResultsImportItemDto` and resolved it from an existing `TestCase` row in the suite's bound dataset instead (via `TestCaseRepository`, requiring `testCaseId`/`testCaseName` to match a real row — 404 otherwise). The stated rationale was "dataset-schema validation is free": the data was already validated by `TestCaseValidationService`/`SchemaTypeCoercer` at CSV-import time.

This was revised based on two observations from real usage:
1. **Consistency with what Phase 1 actually produces.** A live run's Phase 1 (`EvaluationWorker.buildResult`) stamps `testCaseData` onto every `TestCaseRunResult` from the snapshot it already has (`TestCaseRunInput.testCaseData`) — it never re-validates that snapshot against the dataset at Phase-1 time either. The import item should be exactly what Phase 1 produces, minus the DB-internal ids (`id`/`testSuiteRunId`/`testSuiteId`/`createdAtMs`) assigned at persistence time — not a bespoke shape that requires the caller to already have test cases registered in EF's dataset.
2. **The suite-clone replay scenario.** Take results produced against suite A, clone suite A, and import those results into the clone to run a fresh evaluation there. Per the `test-suite-clone` spec, cloning a suite bound to a **PRIVATE** dataset clones the dataset too, with **new UUIDs per test case** (`testCaseName`/`data` copied, id not) — cloning on a **PUBLIC** dataset keeps the same dataset (ids unchanged). Requiring `testCaseId` to resolve against a dataset row would silently break the PRIVATE-dataset-clone case, since the id you have is for a test case that doesn't exist under that id from the clone's perspective. Only `testCaseName` survives as a stable cross-clone identifier.

**Revised design**: `EvalResultsImportItemDto` gains a required `testCaseData` field (`@NotNull`, validated as a JSON object — mirroring `AnalyticsResultService.batchCreate`'s own check). `testCaseId`/`testCaseName` keep their existing optional-id/name-fallback shape (unchanged) but are **never looked up** — no `TestCaseRepository` dependency remains in the import path at all. Whichever of `testCaseId`/`testCaseName` is supplied is stored as a pure identifying label, exactly how `AnalyticsResultService.batchCreate` already treats `TestCaseRunResultItemDto.testCaseId`/`testCaseData` (fully trusted, no existence check) — except that endpoint requires `testCaseId`; this one keeps the id-optional/name-fallback flexibility for the clone-replay case above.

**DB constraint this interacts with (no schema change — confirmed)**: `test_case_run_results.test_case_id` is `VARCHAR(36) NOT NULL` (`V1.1__CreateTestCaseRunResultsTable.sql:5`). Rather than migrating the column to nullable, when the caller supplies only `testCaseName`, `TestCaseRunResultMapper`'s import overload synthesizes `UUID.randomUUID()` for the persisted `testCaseId` column via a MapStruct expression. This is safe and semantically honest: `test_case_id` has no FK to `test_cases` (analytics and meta are separate datasources; there never was a real cross-DB FK), so a synthesized id is just an opaque per-row identifier, not a claim that a matching `TestCase` row exists — which is exactly the point of dropping resolution. The unique constraint `(test_suite_run_id, test_case_id, run_index, created_at_ms)` is trivially satisfied either way; in-batch duplicate detection (`validateBatch`/`testCaseIdentity`, prefer id else name) is unaffected and still catches a caller submitting the same logical test case twice within one request.

**Schema validation (revised post-implementation, further revised — task 15)**: `testCaseData` IS validated against the dataset schema at import time, but that validation now runs inside `EvalResultsCsvParser.parse` (not `EvalResultsImportService.validateBatch`). The parser calls `SchemaValidationService.validate(dataMap, schemaMap)` for each row after building `testCaseDataNode`, collecting schema violations into the per-row error list alongside JSON-parse and enum errors, with the same all-or-nothing semantics — a schema violation on any row rejects the entire batch (HTTP 400) with a `row N: testCaseData validation failed: …` message. Moving schema validation into `parse` eliminates the `SchemaValidationService`/`DatasetSchemaProvider` dependencies from `EvalResultsImportService` (they belonged to the CSV-parsing concern, not the persistence concern) and ensures that the `List<TestCaseRunResult>` handed to `validateBatch` is already schema-valid.

**Further revised (task 15)**: `EvalResultsImportItemDto` was removed entirely (see Decision 7, task 15 below). `testCaseId`/`testCaseName`/`testCaseData` are now fields on `TestCaseRunResult` directly, written by `EvalResultsCsvParser.parse`; the synthesized `UUID.randomUUID()` when only `testCaseName` is supplied is now done inline in the parser (`testCaseId` field defaulted to `UUID.randomUUID()` when the CSV cell is blank). The `TestCaseRunResultMapper` import overload (`toEntity(EvalResultsImportItemDto, ...)`) was removed; `EvalResultsImportService.persistResults` fills in run-context fields (`id`, `testSuiteRunId`, `testSuiteId`, `createdAtMs`) via `TestCaseRunResult.toBuilder()` directly, with no mapper involvement. The existing `toEntity(TestCaseRunResultItemDto, ...)` overload used by `AnalyticsResultService` is untouched.

### 5. `executeImportedRunAsync` was merged into `executeRunAsync` behind a `skipDeploymentPhase` flag (revised post-implementation)

The initial implementation added a separate `executeImportedRunAsync(UUID runId)` method, explicitly rejecting a parameterized `executeRunAsync` on the grounds that a `token` parameter with no meaning for import runs would make the method harder to read. Once both methods existed side by side, that argument didn't hold up: `executeRunAsync` and `executeImportedRunAsync` shared the cancellation check, `updateToRunning`, Phase 2, Phase 3, the terminal-status transition, `notifySse`, and the top-level catch/finally verbatim — only the snapshot phase + inconsistent-snapshot guard + Phase 1 (`buildContext`/`evaluationExecutor`) differed. That's a real duplication cost, and a `null` token for a boolean-gated branch that never reads it is a small, well-contained readability cost by comparison.

`executeImportedRunAsync` was removed. `executeRunAsync(UUID runId, String token, boolean skipDeploymentPhase)` now wraps exactly the snapshot-phase call and the inconsistent-snapshot-guard-plus-Phase-1 block in `if (!skipDeploymentPhase) { ... }`; everything else is unconditional, unchanged from before. `buildMetricEvaluationContext` and `computeMetricScores` remain reused **unmodified**, as originally designed (see Context — both already work against a run with no snapshot/no `TestCaseRunInput` rows).

This merge is scoped to `TestSuiteEvaluationJob` only. `TestSuiteRunService.createRun` and `importResultsAndEvaluate` were briefly unified behind shared private helpers (`loadSuiteForRun`, `enforceConcurrencyLimits`, `resolveRunName`, `saveRunOrThrow`, `dispatchEvaluation`, `markRunFailed`) in the same pass, then deliberately reverted per user feedback: the two methods' guard/validation logic differs enough (zero-runnable-count + `numberOfRuns`/execution-settings validation for live runs vs. batch/test-case-resolution for imports) that routing both through shared helpers made each method harder to read in isolation, for a modest line-count saving. `createRun` and `importResultsAndEvaluate` stay two separate, self-contained methods — each still ends its own `afterCommit` body with a direct call to `evaluationJob.executeRunAsync(runId, token, skipDeploymentPhase)` (`false`/real token for `createRun`, `true`/`null` token for `importResultsAndEvaluate`), which is the one thing they actually share: the job-level entry point, not service-level plumbing.

**Further revised (task 13, superseding the "not shared" framing above for two narrow helpers)**: after `EvalResultsImportRunService` was folded back out of existence (see Decision 6, further revised below), the two methods' concurrency-limit checks (`globalActive`/`suiteActive` against `TooManyRunsException`) and run-name-resolution/save logic were found to be byte-identical modulo the `runConfig` JSON payload (`createRun`'s serialized `RunConfigDto` vs. import's fixed `"{}"`) and the caller-supplied `numberOfTestCases`. Those two blocks — and only those two — were extracted into shared private helpers `enforceConcurrencyLimits(UUID testSuiteId)` and `createAndSaveRun(UUID testSuiteId, String requestedTestRunName, int numberOfTestCases, String runConfigJson)`, called by both `createRun` and `importResultsAndEvaluate`. This is deliberately narrower than the fully-reverted attempt above: the suite not-found/unbound/invalid guard chain — whose error messages differ per method ("Cannot start a run" vs. "Cannot import eval results") — stays inline in each method, unshared, exactly as the revert above intended for guard logic. Only the two verbatim-duplicate blocks moved.

### 6. Timestamps via `System.currentTimeMillis()` throughout — `Clock` removed (revised post-implementation)

The initial implementation injected a `Clock` into `TestSuiteRunService` for the new import-failure path (`failImportRun`'s `updateToFailed` call), while leaving `createRun`'s own pre-existing `RejectedExecutionException` handler on `System.currentTimeMillis()` — a stated "pre-existing tech debt, out of scope to fix here" stance. In practice, adding `Clock` for one method on a class whose sibling method keeps `System.currentTimeMillis()` created exactly the drift that stance was meant to avoid, and a later pass (task 4.5/10 work) briefly let `Clock` leak into `createRun`'s handler as a side effect.

**Revised**: the "new code injects `Clock`" framing no longer applies, because the compensating-failure logic that motivated it moved out of `TestSuiteRunService` entirely — see Decision 5's `EvalResultsImportRunService` extraction (`validateBatch`, `createAndSaveRun`, `markRunFailed`, moved from `TestSuiteRunService`'s `importResultsAndEvaluate`/`failImportRun`). `EvalResultsImportRunService.markRunFailed` uses `System.currentTimeMillis()` directly, for the same reason `createRun`'s handler always has: it's a single, non-critical-path timestamp on a failure branch, not business logic that benefits from `Clock`-based determinism in tests (the unit test asserts via a timestamp range check, not an exact stubbed value). `TestSuiteRunService` itself no longer has a `Clock` field/constructor parameter at all — both remaining `System.currentTimeMillis()` call sites (`createRun`'s handler, unchanged) and `EvalResultsImportRunService.markRunFailed`'s (new) now use the same, consistent, non-injected timestamp approach. (Further revised — task 13: `EvalResultsImportRunService` deleted; `markRunFailed` moved back to `TestSuiteRunService` as a private method — see "Further revised" note below.)

**Also in this pass**: the copy-pasted register-signal → `executeRunAsync` → on-rejection-compensate shape that both `createRun` and `importResultsAndEvaluate`'s `afterCommit` bodies duplicated was de-duplicated into one private `TestSuiteRunService.dispatchEvaluation(UUID runId, String token, boolean skipDeploymentPhase, Runnable onRejected)` helper — registers the cancellation signal, calls `evaluationJob.executeRunAsync(...)`, and on `RejectedExecutionException` removes the signal and invokes the caller-supplied `onRejected` compensation (each method keeps its own: `createRun`'s inline `RESOURCE_LIMIT` message with no SSE notify vs. import's `evalResultsImportRunService.markRunFailed` with SSE notify); any other exception also removes the signal before rethrowing. This is narrower than Decision 5's already-reverted shared-helper attempt (`loadSuiteForRun`/`enforceConcurrencyLimits`/etc.) — it only touches the one piece of logic the two methods' `afterCommit` bodies actually share verbatim (the job-dispatch mechanics), not their guard/validation/save logic, which stays separate per that decision's rationale.

**Further revised (task 13)**: `EvalResultsImportRunService` was deleted entirely; its `markRunFailed` was moved back onto `TestSuiteRunService` as a private method, unchanged internally (still `System.currentTimeMillis()`, still notifies SSE) — `TestSuiteRunService` still has no `Clock` field; both `System.currentTimeMillis()` call sites (`createRun`'s inline rejection handler and the moved-back private `markRunFailed`) live on the same class again, consistently non-injected. `dispatchEvaluation`'s `onRejected` callback in `importResultsAndEvaluate` now calls the private `markRunFailed` directly instead of delegating to a separate service bean.

### 7. Request format switched from JSON body to CSV/multipart (post-archive rewrite)

The endpoint originally accepted a JSON body (`EvalResultsImportRequestDto` wrapping `List<EvalResultsImportItemDto>`), explicitly scoped as a Non-Goal to keep file-based import separate (see Non-Goals above: "CSV/bulk-file import of eval results ... file-based import is a separate concern if ever needed"). That separateness didn't hold up once used: producing a large JSON array by hand (or from another tool's export) is far more awkward than a CSV file, and this project already has an established, proven CSV/multipart import pattern (`TestCaseController`/`CsvImportService`) that the endpoint could reuse the shape of. This decision retires the Non-Goal and switches the endpoint's request format to CSV over `multipart/form-data`, in place of (not alongside) the JSON body.

**Column layout.** A fixed set of 15 reserved, flat-named columns covers all fields of the imported result: `testCaseId`, `testCaseName`, `runIndex`, `testCaseData`, `requestBody`, `responseBody`, `responseStatusCode`, `executionStatus`, `startedAt`, `completedAt`, `traceId`, `retryCount`, `logDetails`, `extractedColumns`, `extractionWarnings`. Every column is reserved — `testCaseData` is a required JSON-object column that the caller supplies verbatim (the CSV parser reads it as a JSON string and validates it against the dataset schema); `extractedColumns` and `extractionWarnings` are optional pre-computed JSON columns that the caller may supply (defaulting to `{}` and `[]` when absent). There is no mechanism by which a non-reserved CSV header maps to a `testCaseData` field: `resolveColumnBindings` maps any header not in `RESERVED_COLUMNS` to `"unknown"`, and `parseRecord`'s default branch drops the value silently. `CsvCellParser`/`SchemaTypeCoercer` are not used. Reserved names are not prefixed/namespaced.

**Type handling of the reserved columns.** `requestBody`/`responseBody`/`logDetails` cells are parsed as JSON (object/array/primitive) when non-blank, blank → `null`; malformed JSON in one of these cells is a validation error identifying the row. `executionStatus` must parse as an `ExecutionStatus` enum name; `runIndex`/`startedAt`/`completedAt`/`retryCount` must parse as integers/longs. `testCaseData` is a required JSON-object cell — the parser validates it is a JSON object and runs `SchemaValidationService.validate` against the dataset schema when one is configured. `extractedColumns`/`extractionWarnings` are optional JSON cells parsed by the same `parseOptionalJsonToString` helper as the other JSON columns; when absent or blank they default to `{}`/`[]` in the built `TestCaseRunResult` stub. No dataset-schema-driven type coercion (via `CsvCellParser`/`SchemaTypeCoercer`) is performed for any column.

**New component, not an extension of `CsvImportService`.** A new `EvalResultsCsvParser` (`service.domain.analytics`) owns CSV parsing for this endpoint, structured like `CsvImportService` (Apache Commons CSV, streaming) but not literally sharing its code: `CsvImportService` is coupled to `TestCase`/dataset persistence (import modes, conflict strategies, schema auto-detection/merge) that has no analog here — this endpoint has no import mode, no conflict strategy, and never writes to `test_cases`. `CsvDelimiterParser` is reused (generic utility); `CsvCellParser`/`SchemaTypeCoercer` are not reused, since the CSV layout here is entirely reserved-column (no dataset-schema-driven field typing).

**Validation remains all-or-nothing, unchanged from the JSON contract.** The parsed `List<TestCaseRunResult>` still goes through the existing `EvalResultsImportService.validateBatch` (structural + in-batch-duplicate checks) unmodified — schema validation now runs inside `EvalResultsCsvParser.parse` before the list is handed to `validateBatch` — a single violation anywhere in the batch rejects the whole request and creates no run, exactly as the JSON body already guaranteed. This was a deliberate choice over adopting the test-cases CSV import's partial-success model (`CsvImportResultDto`-style, invalid rows warned but valid rows persisted): imported results feed directly into metric scoring, so a partially-valid batch would silently produce misleading aggregate scores over an incomplete/inconsistent result set — a materially different risk profile than test-case *data* import, where an invalid row just means one fewer test case to run later.
**Bean Validation without `@Valid @RequestBody` (revised — task 15)**: The original implementation built `EvalResultsImportItemDto`/`ExecutionInfoRequestDto` instances in the CSV parser and validated them via `jakarta.validation.Validator.validate(item)` per row. This approach was replaced when the intermediate DTO was removed (task 15): `parse` now builds `TestCaseRunResult` stubs directly and validates fields with explicit inline checks in `parseRecord` — `runIndex` null/`< 0`/`> 99999`, `testCaseName` length `> 255`, `executionStatus` null, `startedAt` null, `completedAt` null. These checks cover exactly the same constraints the DTO annotations declared, without the indirection. Schema validation (Decision 4, above) replaces the DTO's `@NotNull testCaseData` + `isObject()` check. The `Validator` dependency was removed from `EvalResultsCsvParser` entirely. The first manual (non-MVC-bound) use of `jakarta.validation.Validator` described in this decision no longer applies to this codebase.

**Batch-size bound stays in-memory, unchanged from the JSON contract's own bound.** The JSON body already fully materialized the entire `results` array in memory before validating/persisting, bounded by `analytics.results.batch.max-items` (default 10000). The CSV parser preserves that same bound — it stream-parses CSV rows via Apache Commons CSV's iterator (never loading the raw file into memory at once) but still materializes the *parsed* `List<TestCaseRunResult>` up to the existing item-count cap before validation, since `validateBatch`'s in-batch-duplicate and schema checks are batch-level operations that need to see every item, not a row-by-row streaming validation. This was chosen over true two-pass streaming (a first structural pass without materializing row data, a second pass to parse+persist) as unnecessary complexity for a batch already capped at ~10k items — the same complexity/benefit trade-off `CsvImportService.preview`'s own bounded-sample-in-memory approach already accepts at a similar scale.

**`persistResults` writes are chunked, unlike the original JSON-path implementation.** The original `EvalResultsImportService.persistResults` called `resultRepository.saveAll(entities)` once, unchunked, for the whole batch — acceptable when the batch's realistic size was bounded by how large a JSON body a client would hand-construct. Since CSV files more plausibly arrive at the full `max-items` cap, `persistResults` now chunks its `saveAll` calls (reusing a batch-size property, mirroring `CsvImportService.importCsv`'s own chunked-insert loop) to keep any single JDBC batch bounded, per this project's "use pagination/batch/streaming for bulk operations" convention (`AGENTS.md`). This is the only behavior change to the previously-implemented validation/persistence/mapping/job-dispatch code — `validateBatch` (whose signature changed from `List<EvalResultsImportItemDto>` to `List<TestCaseRunResult>` in task 15) and `TestSuiteEvaluationJob.executeRunAsync(..., skipDeploymentPhase=true)` are otherwise unchanged by this rewrite. (Revised by task 15: `TestCaseRunResultMapper` import overload deleted; `validateBatch` parameter type updated to `List<TestCaseRunResult>`.)

**New configuration, reusing the existing item-count cap.** A new `analytics.results.csv-import.max-file-size` property (`DataSize`, default `10MB`, mirroring `csv.import.max-file-size`'s shape) bounds the uploaded file size — a concern the JSON body's `analytics.results.batch.max-request-size-bytes` (enforced via `MaxRequestBodyFilter` on the JSON-body content type) doesn't apply to multipart uploads. The existing `analytics.results.batch.max-items` continues to bound item count; no new property was added for that, since the CSV parser enforces it the same way the JSON body's `@NotEmpty @Valid List<...>` binding + `validateBatch`'s explicit check already did.

**No preview endpoint, no ZIP support.** Test-cases CSV import offers both a `/import/preview` dry-run and ZIP-archive support (for `FILE`-typed schema fields materialized alongside the CSV). Neither is added here: a preview endpoint would need to re-derive metric-evaluation-relevant guarantees (schema validation, batch-level duplicate detection) without actually persisting anything, which is a non-trivial amount of new surface for a first cut; and eval-results import has no file-materialization use case analogous to `FILE`-typed test-case fields — `requestBody`/`responseBody`/`testCaseData` are inline JSON/text cells, not references to uploaded files. Both can be added later, additively, if needed.

## Risks / Trade-offs

- **[Risk]** Analytics write succeeds but the process crashes before the async job dispatch line executes → run stays `PENDING` forever with results already attached, never evaluated. **Mitigation**: this is the same class of risk `createRun` already accepts for the executor-rejection case: `TestSuiteRunRepository.failOrphanedRuns` (used elsewhere for orphan cleanup) can be extended to cover `PENDING` import runs with no progress, or an operator can re-trigger by re-importing — out of scope to solve differently here since it mirrors an existing accepted risk shape, not a new one.
- **[Risk]** Since `testCaseId`/`testCaseName` are never looked up against `test_cases`, a caller can reference a `testCaseId`/`testCaseName` that doesn't exist anywhere in EF at all. **Accepted**: this is the same trust boundary `AnalyticsResultService.batchCreate` already operates under (never validated `testCaseId` against `TestCaseRepository` either) — the caller is responsible for pairing a response with data that's actually relevant to the test case identity they provide. **Note**: `testCaseData` schema validation (Decision 4, revised) does catch structural mismatches, so callers cannot submit data that violates the dataset schema.
- **[Risk]** A large batch (near `analyticsProperties.getBatch().getMaxItems()`) does per-item `SchemaValidationService.validate` calls inside `EvalResultsCsvParser.parse` (which runs inside the meta transaction) — O(n) with no batching optimization. Dropping `TestCase` resolution (Decision 4) and dropping server-side `ResponseColumnExtractor.extract` calls (Decision 3, revised / Decision 7) removed the per-item meta-DB lookups and JSONata evaluation that used to also run inside the meta transaction, so this risk is now smaller than originally scoped. **Mitigation**: acceptable at the same batch-size cap `AnalyticsResultService.batchCreate` already tolerates for its own per-item validation loop; can be revisited if the cap is later raised significantly.
- **[Trade-off]** No schema/migration changes and no `run_source` column, per the "Non-Goals" decision — a UI cannot currently distinguish an imported run from an executed one by querying the API. Accepted: nothing in the pipeline needs the distinction, and if reporting needs it later, the run's `suiteSnapshot IS NULL AND status != 'PENDING'`-ish signal (or simply: it was dispatched with `skipDeploymentPhase=true`) is inferable without a dedicated column, though not queryable directly — a future need can add the column then, additively.
- **[Trade-off]** A `testCaseId`-less item gets a synthesized `UUID.randomUUID()` (Decision 4) rather than a `NULL` column — confirmed with the user as the preferred option over a `test_case_id` nullability migration. Consequence: re-importing "the same" logical test case's result twice (e.g. once by name into suite A, once by name into a clone of A) produces two rows with *different* synthetic `test_case_id` values — there is no way to detect "these two rows are about the same logical test case" from `test_case_id` alone across separate import calls; `test_case_name` remains the only cross-call correlating field in that situation.

## Migration Plan

No database schema changes. No feature flag or phased rollout is needed since this is a purely additive endpoint with no impact on existing run-creation or evaluation paths — Phase 2 (`MetricEvaluationExecutor`) and Phase 3 (`MetricScoreComputation`) are reused unmodified and are already exercised by every existing live run.
