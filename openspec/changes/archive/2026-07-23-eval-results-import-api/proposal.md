## Why

Today, getting metric scores for a test suite requires running the full evaluation pipeline: snapshot → Phase 1 (actual deployment invocation) → Phase 2 (metric evaluation) → Phase 3 (score computation). There is no way to bring in test-case data and *already-produced* model responses (from an external run, a different system, or historical data) and have EF score them — the only path today is to re-invoke a deployment through EF to get a `TestSuiteRun` populated. Users who already have response data (e.g. exported from another tool, or produced by a system EF cannot invoke directly) need a way to import it and get the same metric evaluation and score computation EF already provides for live runs.

## What Changes

- Add a single endpoint, `POST /api/v1/test-suites/{testSuiteId}/runs/import`, that accepts a batch of already-produced eval results (raw response bodies, one per test case) for an existing, dataset-bound suite. In one request it creates a `TestSuiteRun`, persists the imported results as `TestCaseRunResult` rows, and asynchronously triggers Phase 2 (metric evaluation) + Phase 3 (score computation) — Phase 1 (deployment invocation) is skipped entirely, replaced by the caller-supplied responses.
- **Request format switched from a JSON body to a CSV file upload (`multipart/form-data`)**, matching the existing test-cases CSV import UX (`TestCaseController`/`CsvImportService`): the endpoint now `consumes = MULTIPART_FORM_DATA_VALUE`, accepting a `file` part (CSV), an optional `testRunName` form field, and an optional `delimiter` form field (single ASCII character, default comma). The CSV is parsed and the batch is validated and persisted synchronously within the request — same all-or-nothing semantics as the JSON body it replaces, just parsed from CSV rows instead of JSON array items. `EvalResultsImportRequestDto` (the JSON envelope) and `EvalResultsImportItemDto` are both removed (task 15); `EvalResultsCsvParser.parse` produces `List<TestCaseRunResult>` stubs directly, consumed by the existing validation/persistence code. `ExecutionInfoRequestDto` is retained (still referenced by `TestCaseRunResultItemDto` in the live-run path).
- CSV columns: a fixed set of reserved, flat-named columns (`testCaseId`, `testCaseName`, `runIndex`, `requestBody`, `responseBody`, `responseStatusCode`, `executionStatus`, `startedAt`, `completedAt`, `traceId`, `retryCount`, `logDetails`) plus one column per dataset test-case-schema field (flattened `testCaseData`, exactly like the existing test-cases CSV import's non-reserved-column handling — typed/coerced via the dataset schema, JSON-parsed for OBJECT/ARRAY fields). `requestBody`/`responseBody`/`logDetails` cells are parsed as JSON when present; `executionStatus` must be a valid `ExecutionStatus` name.
- Response-column (JSONata) extraction, previously only performed inline during live Phase 1 execution, is invoked directly against the imported response bodies at import time via the existing `ResponseColumnExtractor` — unchanged by the CSV switch.
- New validation: each imported item is caller-supplied and trusted for identity — `testCaseId`/`testCaseName`/`testCaseData` are never looked up or resolved against any existing `TestCase` row (no `TestCaseRepository` dependency in the import path); no two imported items may share the same test-case identity and `runIndex`; `completedAt >= startedAt` per item; batch-size cap; standard run guards (suite not-found/unbound/invalid, concurrency limits, run-name uniqueness). Unchanged by the CSV switch — these checks still run against the parsed `List<TestCaseRunResult>` (task 15: `EvalResultsImportItemDto` removed; parser produces `List<TestCaseRunResult>` directly), all-or-nothing, before any run is created.
- Test-case *data* schema validation IS performed by the endpoint, at import time, directly against the suite's bound dataset schema — via `SchemaValidationService`/`DatasetSchemaProvider` inside `EvalResultsImportService.validateBatch` — unchanged by the CSV switch (the CSV parser produces the same `testCaseData` `JsonNode` shape a JSON body item used to carry).
- No schema/migration changes: the endpoint reuses the existing `TestSuiteRun` and `TestCaseRunResult` tables/columns as-is (a `run_source`/kind column was considered and deliberately rejected — nothing in the pipeline needs to branch on it, since the new Phase-2/3-only job method is invoked directly rather than dispatched by inspecting the run).

## Capabilities

### New Capabilities
- `eval-results-import`: Importing already-produced eval results (raw model responses) for an existing test suite's test cases, and running metric evaluation + score computation against the imported data without invoking a deployment.

### Modified Capabilities
(none — this is a new, additive capability; no existing spec's requirements change)

## Impact

- **API**: one endpoint on the existing test-suite-run resource, `POST /api/v1/test-suites/{testSuiteId}/runs/import`, `consumes = multipart/form-data` (`file` part + optional `testRunName`/`delimiter` form fields), returning `202 Accepted` with a `TestSuiteRunResponseDto` (status `PENDING`, transitioning to `RUNNING`/`COMPLETED`/`FAILED` asynchronously like a normal run).
- **DTOs** (`service.domain.dto.analytics`): `EvalResultsImportItemDto` and `EvalResultsImportRequestDto` removed entirely (task 15 / Decision 7); `ExecutionInfoRequestDto` retained (still referenced by `TestCaseRunResultItemDto` in the live-run path).
- **New service code**: `EvalResultsCsvParser` (new, `service.domain.analytics`) — streams the uploaded CSV via Apache Commons CSV (mirroring `CsvImportService`'s approach), parses each row directly into a `TestCaseRunResult` stub bounded by the existing `analytics.results.batch.max-items` cap, and validates required fields with explicit inline checks in `parseRecord` (no intermediate DTO, no `jakarta.validation.Validator` dependency — see note below). (Revised by task 15: DTO and Bean Validation removed; see design.md Decision 7)
- **Changed service code**: `TestSuiteRunService.importResultsAndEvaluate` signature changes from `(UUID testSuiteId, EvalResultsImportRequestDto request)` to accepting the raw multipart upload (CSV stream, content length, delimiter, optional run name) instead of a parsed request DTO; `EvalResultsImportService.persistResults` chunks its `TestCaseRunResultRepository.saveAll` calls (was a single unchunked call) per AGENTS.md's bulk-write convention. `TestSuiteEvaluationJob`'s existing `executeRunAsync(runId, token, skipDeploymentPhase)` entry point, `TestCaseRunResultMapper`'s import overload, and `EvalResultsImportService.validateBatch` are unchanged by the CSV switch.
- **New configuration**: `analytics.results.csv-import.max-file-size` (`AnalyticsResultsProperties`, `DataSize`, mirroring `csv.import.max-file-size`) — the item-count cap continues to reuse the existing `analytics.results.batch.max-items`.
- **No DB schema changes.**
- **OpenAPI**: the two `*-request-*.json` examples under `openapi/examples/` (JSON body) are retired; the endpoint description documents the CSV column contract instead, matching `TestCaseController.importCsv`'s style. Response examples (202/409) are unchanged.
- **Testing**: new unit tests for `EvalResultsCsvParser` (column mapping, reserved columns, JSON-cell parsing for `requestBody`/`responseBody`/`logDetails`, enum/type errors, file-size/item-count caps, inline constraint checks for `runIndex`/`executionStatus`/`startedAt`/`completedAt`/`testCaseName` length, schema validation surfacing); existing unit tests for `EvalResultsImportService`/`TestSuiteRunService` updated for the chunked persistence and the new service call shape; `EvalResultsImportFunctionalTests` rewritten to submit multipart CSV requests (reusing the `ByteArrayResource`-based multipart-upload helper pattern from `CsvImportModeFunctionalTests`) instead of JSON bodies, preserving existing scenario coverage.
