## Context

The EF backend's Phase 1 execution engine (request resolution, deployment invocation, retries, streaming/SSE handling, response-column extraction, multi-turn turn loop) was already extracted into a separate, DB-free Gradle subproject, `evaluation-runner-core` (root package `com.epam.aidial.evaluation.runner`), contributed to the EF backend via Spring Boot autoconfiguration. It exists specifically so a standalone runner could reuse the exact same execution logic without depending on the EF backend's database.

There is currently no such standalone runner. Teams evaluating an application deployed to an environment with no EF instance running alongside it have no way to reuse the "standard" test suites already defined on an existing EF instance, short of standing up a second EF deployment next to the target application purely to run one evaluation. This design adds that standalone runner as a CLI.

Two REST capabilities already exist on the EF backend that this CLI depends on unchanged:
- `POST /api/v1/test-suites/{id}/clone` (deep-copies suite config + TSMDs + a private test-case dataset).
- `POST /api/v1/test-suites/{id}/runs/import` (imports already-produced `TestCaseRunResult`-shaped rows from CSV, skips Phase 1, and automatically dispatches Phase 2/3 metric evaluation — no separate trigger needed).

And one extension point in `evaluation-runner-core` is used exactly as designed: `ResultBatchWriter` is documented as "DB-free by contract so a standalone runner can supply an alternate implementation (e.g. in-memory, CSV)" — this CLI supplies the first such alternate implementation.

## Goals / Non-Goals

**Goals:**
- Provide a standalone, runnable CLI (`eval-cli`, new Gradle subproject) that clones standard test suites from a **source** EF instance, fetches their configuration and test cases, executes them against a CLI-configured deployment on a **target** environment using `evaluation-runner-core`'s existing concurrent batch execution path, and imports the results back into the source EF's clone via its existing import API.
- Reuse `evaluation-runner-core`'s `TestCaseRunnerFactory` / `TestCaseRunner.submit(List<TestCaseRunInput>)` / `awaitCompletion()` as the batch dispatch entry point — the same one `InProcessEvaluationExecutor` uses for DB-backed runs — so concurrency, rate limiting, cancellation plumbing, synthetic ERROR-row handling on worker failure, and per-task auth-token propagation are inherited for free, not reimplemented.
- Make the four steps (clone, fetch, run, import) usable independently as separate CLI subcommands, plus an `evaluate` subcommand chaining all four, since a user may want to re-run just one step (e.g. re-import after fixing a target deployment issue).
- Keep the CLI a pure consumer: zero changes to the EF backend's existing production code or REST contracts, and zero changes to `evaluation-runner-core`'s production code.

**Non-Goals:**
- OIDC client-credentials authentication (client id/secret → token exchange) for the source EF. A static, pre-obtained bearer token (`EVAL_TOKEN` env var) is used instead, explicitly as a temporary measure. The target environment authenticates via a static `Api-Key` header sourced from the `DIAL_CORE_API_KEY` env var, which is the intended long-term mechanism (mirrors the EF backend's own DIAL Core file-operations auth), not a temporary placeholder.
- Cancellation/Ctrl-C handling — `EvaluationContext.cancellationSignal` is wired (required by `TestCaseRunner`'s constructor contract) but the CLI never flips it in this change.
- Concurrent *`evaluate` invocations* against overlapping suites, or any notion of resuming a partially-completed evaluation run beyond re-running an individual subcommand.
- Any new database schema, migration, or persistent storage — the module is DB-free by design, matching `evaluation-runner-core`.

## Decisions

### New Gradle subproject, not a package inside the root app or inside `evaluation-runner-core`
`eval-cli` is its own subproject (`settings.gradle` gains `include 'eval-cli'`), modeled on `evaluation-runner-core/build.gradle` (Java 25 toolchain, checkstyle, spotless/palantir formatting, the same `commons-logging`/`spring-boot-starter-logging` exclusions). It depends on `evaluation-runner-core` (`implementation project(':evaluation-runner-core')`) but never on the EF backend's own `src/main` — enforced by a new ArchUnit test, `CliModuleConstraintsTest`, mirroring `RunnerModuleConstraintsTest`. Alternatives considered: adding a CLI entry point inside the root app (rejected — the root app already boots a full JDBC/security/web stack that a CLI shouldn't need to carry, and it would blur the "one-way dependency" rule that keeps `evaluation-runner-core` DB-free); adding CLI commands inside `evaluation-runner-core` itself (rejected — that module's charter is the execution engine only, not a delivery mechanism, and picocli/CSV/HTTP-client dependencies don't belong in a library other consumers embed).

### `TestCaseRunner`/`TestCaseRunnerFactory` as the execution entry point, not raw `EvaluationWorker.execute`
`EvaluationWorker.execute(TestCaseRunInput, EvaluationContext, int, List<ResponseColumnDefinitionDto>)` executes exactly one test case — its Javadoc says so directly, and there is no batch overload. `TestCaseRunner` (constructed per run by `TestCaseRunnerFactory.create(context, responseColumns, resultsWriter)`) is the actual batch entry point: `submit(List<TestCaseRunInput>)` dispatches all test cases concurrently on virtual threads bounded by a semaphore sized from `context.getConcurrencyLevel()`, respects an optional token-bucket rate limit (`context.getRateLimitRps()`), propagates the auth token onto each worker thread automatically via `TokenPropagationHelper.withTokenRunnable`, turns any per-case worker exception into a synthetic `ExecutionStatus.ERROR` row instead of losing it, and honors `context.getCancellationSignal()`. `awaitCompletion()` blocks until all submitted tasks finish (or the cancellation grace period elapses). This is the exact same path `InProcessEvaluationExecutor` uses for DB-backed runs, so using it here gives the CLI correctness parity with the EF backend's own execution behavior for free. `RunOrchestrationService` therefore does not implement its own thread pool, retry loop, or token propagation — it only builds the `EvaluationContext` and `List<TestCaseRunInput>`, then delegates.

### CSV `ResultBatchWriter` implementation, thread-safe by construction
`CsvResultBatchWriter` (in a new `csv` package) implements `evaluation-runner-core`'s `ResultBatchWriter` interface, writing rows via Apache Commons CSV (`CSVPrinter`) in a column set/order the EF backend's `runs/import` endpoint accepts (`EvalResultsCsvParser` resolves columns by header name, not position): `testCaseName, runIndex, testCaseData, requestBody, responseBody, responseStatusCode, executionStatus, startedAt, completedAt, traceId, retryCount, logDetails, extractedColumns, extractionWarnings`. Because `TestCaseRunner` calls `resultsWriter.addResults(...)` concurrently from multiple virtual threads, `addResults` synchronizes around the shared `CSVPrinter` to prevent interleaved/corrupted rows. `testCaseData` is a **required** JSON-object column on the import contract (`EvalResultsCsvParser.parseRequiredJsonObject`, validated against the destination dataset's schema when one is configured) — an earlier draft of this design incorrectly assumed it was unaccepted; a `null` value on the result is written as `"{}"` rather than a blank cell, since a blank cell fails import validation. `testCaseId` is deliberately **omitted**: the IDs eval-cli reads come from the *source* suite's bound dataset, but the destination clone's dataset isn't guaranteed to be the same one (a clone of a suite bound to a PRIVATE dataset gets a freshly cloned dataset with new test case IDs), so those source-side IDs wouldn't correspond to anything at the destination. This is safe because `EvalResultsImportService.validateBatch`/`testCaseIdentity` never resolves `testCaseId` against any dataset — it's used only for in-batch duplicate detection, falling back to `testCaseName` (always supplied here) when `testCaseId` is absent; the contract only requires one of the two, never both. `extractedColumns`/`extractionWarnings` ARE included — a second earlier-draft mistake in the same category as `testCaseData`: extraction (`ResponseColumnExtractor.extract(responseColumns, responseBody)`) happens *exclusively* inside `EvaluationWorker.buildResult` during Phase 1; server-side Phase 2 (`InProcessMetricEvaluationExecutor`/`MetricEvaluationWorker`) only ever reads the already-persisted value verbatim, never re-extracts — so for an import, skipping Phase 1 means extraction never happens anywhere, on either `test_case_run_results` or the copied `test_case_eval_summaries.extracted_columns`. Since eval-cli's own `RunOrchestrationService` already runs Phase 1 locally (the shared `TestCaseRunner`/`EvaluationWorker`), every `TestCaseRunResult` handed to this writer already carries real extraction output — omitting it from the CSV silently threw that away, breaking any metric whose binding reads an extracted column for an imported run. `turnIndex`/`totalTurns` remain omitted — they are not part of `EvalResultsCsvParser.RESERVED_COLUMNS` at all.

### `SuiteContractValidator`: pre-flight check of `endpointRef`/`requestTemplate`, not a target-deployment cross-check
`RunOrchestrationService.run` calls `SuiteContractValidator.validate(bundle.getSuite())` before building the `EvaluationContext`, failing fast with an `IllegalStateException` if `endpointRef` is missing, `endpointRef.method` is missing, `requestTemplate` is missing, or `requestTemplate.urlTemplate` is blank — the exact fields `EvaluationWorker` actually reads to build the outbound request (see the "actual suite fields used to hit application" analysis: `endpointRef.method` + `requestTemplate` + `inputBindings`, nothing else on `endpointRef` is read at runtime). A request-body-vs-`endpointRef.requestBodySchema` content-type mismatch is logged as a warning, not a hard failure, mirroring the source EF's own `SuiteValidationService.validateDeploymentSuite` (which treats the same mismatch as a soft warning, not an HTTP 400). This is **not** a cross-check against the target deployment's actual contract — the target is only ever a CLI parameter (`--deployment-id`), the source suite's config carries no reference to it, and DIAL Core's `GET /v1/deployments` exposes only a coarse `interfaces` category (no HTTP method/path/schema) — there is nothing to auto-discover the target's real contract against today. This only catches a suite left in an invalid state on the source EF, or drift between `fetch` and `run` time, before it surfaces as a confusing null-method failure mid-run.

### Supplying `"dialCoreTryOutRestClient"` from the CLI module, targeting the target environment
`DialCoreDeploymentInvoker` (in `evaluation-runner-core`) consumes a `RestClient` bean qualified `"dialCoreTryOutRestClient"` by name only — it doesn't care which module declares it. Today the EF backend supplies it (`DialCoreDeploymentInvokerConfiguration`, deliberately kept in the EF backend rather than moved into the shared module, to avoid a shared-module → EF-backend compile dependency). `eval-cli` supplies its own instance the same way (same `JdkClientHttpRequestFactory`/timeout construction, same interceptor composition), bound to `evaluation-runner-core`'s existing `DialCoreProperties` (`dial.components.core.*`) — which the CLI configures to point at the **target** environment's DIAL Core host. One CLI process/Spring context therefore targets exactly one target environment per invocation, which matches the CLI's single-run-at-a-time usage model.

### Own `ObjectMapper`/`JsonMapper`, `dialFileRestClient`, and complete `test-suite-run.*`/`sse-event-processing.*` bindings
Because `spring.main.web-application-type=none`, Spring Boot's Jackson autoconfiguration never activates, so `eval-cli` cannot rely on it the way the EF backend (a web app) does — it declares its own `JsonMapperConfiguration` (`com.epam.aidial.evaluation.cli.config`), mirroring the EF backend's settings (case-insensitive enums, tolerant deserialization, `NON_NULL` inclusion) and reusing the shared `HttpMethodSerializer`/`HttpMethodDeserializer` (moved from the EF backend into `evaluation-runner-core`'s `runner.util.jackson`, since `EndpointContractDto` — the type that needs them — already lives there and both consumers need parity). `TargetDialCoreClientConfiguration` also supplies `"dialFileRestClient"` (in addition to `"dialCoreTryOutRestClient"`), bound to the **target** DIAL Core host with the same `Api-Key` interceptor — file references encountered while executing a test case resolve against the target, not the source; if that's wrong for a given deployment (files uploaded on the source only), this bean needs reworking to use `eval.source`'s DIAL Core credentials instead. `evaluation-runner-core`'s `EvaluationWorker`/SSE parsing also unconditionally require `test-suite-run.*` (`execution`/`retry`/`run-inputs`) and `sse-event-processing.max-total-duration-ms` to bind at context startup even though `eval-cli`'s actual per-run values come from `cli.run.*`; `application.yml` supplies permissive defaults for these (only `execution.header-blacklist` is actually read at runtime, to strip headers — including `Api-Key` — that a test case's own request template cannot override).

### Source EF REST contract DTOs live in `evaluation-runner-core`, not as local mirrors
`eval-cli` cannot depend on the EF backend's `src/main` (see the ArchUnit rule above). Rather than maintaining hand-kept local copies of the EF backend's response contracts, the top-level envelope DTOs it needs (`TestSuiteResponseDto`, `TestSuiteCloneRequestDto`, `TestCaseResponseDto`, `PageResponseDto<T>`, and the full `TestSuiteRunResponseDto` family — `RunConfigDto`/`ExecutionSettingsDto`/`RetryPolicyDto`/`SuiteSnapshotDto`/`DatasetReferenceDto`/`FieldDefinitionDto`/`RunErrorDetailsDto`) were consolidated into `evaluation-runner-core`'s `runner.dto` and are now consumed directly by both the EF backend and `eval-cli`, eliminating the drift risk entirely for those types (a compile-time dependency, not a "manually kept in sync" comment). The one deliberate exception is `client/source/dto/TestSuiteUpdateResultDto` — a `{suite}`-only subset of the canonical `runner.dto.TestSuiteUpdateResultDto`, kept local because `eval-cli` never needs the sibling `revalidationTask` field (the clone endpoint's contract guarantees it is always null) and unknown-JSON-property tolerance handles its absence safely.

### Suite selection by explicit ID list, not a dynamic filter query
`--suites` is a required, explicit list of source EF test-suite UUIDs (no configuration/env-var fallback), not a name pattern or filter expression resolved at runtime. This makes the "standard suites" set an explicit, reviewable per-invocation choice rather than something that silently changes as suites are added/renamed on the source EF.

### Clone idempotency: reuse an existing `<name>_<suffix>` clone as the destination
For each selected source suite ID, `CloneService` resolves the source suite's name, checks whether `<name>_<suffix>` already exists on the source EF (by exact-name lookup), and if so reuses that existing suite's ID as the destination for fetch/run/import without re-cloning. Only if no such suite exists does it call the clone endpoint. Either way, the result is a `sourceId -> destinationCloneId` mapping that the rest of the flow treats identically regardless of which branch was taken — this keeps repeated `evaluate` invocations idempotent with respect to suite creation while still re-running fetch/run/import each time. `CloneService` does not read `EvalCliProperties` at all: `resolveClone(sourceSuiteId, cloneSuffix)`/`resolveClones(sourceSuiteIds, cloneSuffix)` take both as explicit parameters, resolved by each command from its required `--suites`/`--clone-suffix` picocli options (via the shared `SuitesOption`/`CloneSuffixOption` mixins — both simple required-option wrappers with no configuration fallback, matching `--deployment-id`).

### Source: static bearer token env var; Target: static API key env var — both env-var-only, no CLI flag or file
The source EF client authenticates via a static, pre-obtained bearer token read from CLI configuration (`eval.source.token`, env var `EVAL_TOKEN`) — explicitly temporary, behind a one-method `CliTokenProvider`-style swap point pending future OIDC client-credentials support. The target DIAL Core client authenticates via an `Api-Key` header instead (mirroring the EF backend's own `DialFileClientConfiguration`), since a standalone CLI process has no signed-in user session to source a JWT from. Both secrets are deliberately **env-var-only** — no CLI flag, no file-based delivery: in this tool's primary deployment context (a CI job), the platform's own secret-store → env-var injection already gets automatic log redaction and leaves no on-disk artifact, so a plain env var is the more idiomatic choice, not a compromise. The target API key is bound by a small local `TargetProperties` (`dial.components.core.api-key`, env var `DIAL_CORE_API_KEY`) — placed under the same `dial.components.core` prefix as `evaluation-runner-core`'s own `DialCoreProperties` (host/timeouts); Spring allows multiple `@ConfigurationProperties` classes on one prefix as long as field sets don't overlap. `EvaluationContextFactory` reads `TargetProperties.getApiKey()` directly (a fixed value for the process's lifetime — no runtime mutation layer, unlike an earlier draft of this design which had a `--api-key-file`/`--api-url`-driven mutable-provider indirection that this simplifies away). The target base URL (`dial.components.core.base-url`, env var `DIAL_CORE_URL`) is likewise env-var-only now — there is no `--api-url` CLI override.

### Picocli subcommands over a single fixed pipeline
`clone`, `fetch`, `run`, `import` are independent picocli subcommands (via `picocli-spring-boot-starter`, which auto-registers `@Command` beans and wires `CommandLine.IFactory` to the Spring context), plus an `evaluate` subcommand (originally named `pipeline`, renamed since it names the domain action — "run a full evaluation" — rather than the implementation detail of how it's built) that chains all four. `fetch` persists its output (suite config + test cases) as JSON under a configurable `cli.workDir` so `run` can be invoked later/standalone against previously fetched data, not only as part of `evaluate`. Alternative considered: a single fixed end-to-end command (rejected — it removes the ability to re-run just the `import` step after fixing a target-side issue without re-running the whole evaluation).

## Risks / Trade-offs

- **[Risk]** The locally-declared source-EF DTOs can silently drift from the EF backend's actual response contract if that contract changes without a corresponding CLI update. → **Mitigation**: class-level Javadoc comments flag the duplication explicitly; contract-shape tests (`MockRestServiceServer` fixtures built from real DTO JSON) catch deserialization breakage early, and a future improvement could publish a shared DTO artifact.
- **[Risk]** Static bearer tokens require manual acquisition/rotation by the operator and will expire mid-run for long evaluations. → **Mitigation**: explicitly scoped as temporary; documented in the CLI's README with a note that OIDC client-credentials support is a known follow-up.
- **[Risk]** `TestCaseRunner`'s concurrency and rate-limit settings, if misconfigured too high, could overwhelm the target deployment. → **Mitigation**: `cli.run.concurrency-level` and `cli.run.rate-limit-rps` are explicit, documented config with conservative defaults (concurrency 4, unbounded rate limit only if explicitly set).
- **[Trade-off]** No cancellation/Ctrl-C wiring in this change means a long-running `run` invocation must be killed at the process level (no graceful in-flight drain). Accepted for this change; `EvaluationContext.cancellationSignal` remains available for a future pass to wire to a shutdown hook.
- **[Trade-off]** Reusing an existing `<name>_<suffix>` clone rather than always creating a fresh one means results from successive `evaluate` runs accumulate as separate imported runs against the same suite rather than fresh suites per run — this is the intended behavior (mirrors how a human would re-run an evaluation against the same destination suite) but should be called out to users comparing historical runs.
