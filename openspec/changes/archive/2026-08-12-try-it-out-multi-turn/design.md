## Context

Try-it-out (`TryItOutService.tryWithTestCase`, `ResolvedRequestService.resolveRequest`) resolves a test case's shared `data` exactly once, invokes the deployment once, and returns a single `TryItOutResponseDto`. It never reads `TestCase.multiTurnData`, so previewing a multi-turn test case today silently produces a "turn 1 only, shared-fields-only" result — no error, no real turn loop, no `$history` accumulation.

Real suite runs already solve this exact problem via `evaluation-runner-core`'s Phase 1 engine:
- `runner.job.TurnLoopExecutor.buildTurnPlan` decides turn count N: if `multiTurnData == null` → N=1 from shared `data`; otherwise `runner.job.PerTurnBindingDetector.referencesPerTurnField(bindings, schema)` checks whether any effective binding targets a schema field flagged `perTurn=true` — if none does, it collapses to N=1 (shared data only) even though `multiTurnData` has multiple entries; otherwise N = `multiTurnData.length` and each turn's effective data = `mergeSharedAndTurn(shared, turn[i])` (per-turn wins on collision).
- Each turn is resolved via `runner.service.RequestResolver.resolveForRun(template, bindings, turnData, frameBindings)`, where `frameBindings` is the *previous* turn's extracted response columns (turn 0 uses an empty frame) — this is what makes `$append($history, [...])` work in request templates, entirely author-driven via JSONata, with no hardcoded chat-completions handling.
- `runner.service.ResponseColumnExtractor.extract(responseColumns, responseBody, requestBodyJson)` is a pure function (no run/snapshot dependency) that computes the next turn's `frameBindings` from the current turn's response.
- `TestSuite.responseColumns` (`data.db.model.TestSuite`) is a live field on the suite row — `TurnLoopExecutor` reads it via a frozen run snapshot only because runs need reproducibility, not because the field is otherwise unavailable. `TryItOutService`/`ResolvedRequestService` already load the full `TestSuite`, so `suite.getResponseColumns()` is available directly, no snapshot needed.
- MCP_TOOL suites are barred from multi-turn entirely: `openspec/specs/multi-turn-test-case/spec.md` ("MCP suites reject multi-turn datasets") rejects run creation for an MCP suite bound to a dataset containing any multi-turn case, HTTP 409 `INVALID_OPERATION`.

This design extends try-it-out to reuse these exact components for the test-case flow, rather than inventing a parallel turn-loop implementation.

## Goals / Non-Goals

**Goals:**
- `tryWithTestCase` executes every turn of a multi-turn test case sequentially, threading `frameBindings` between turns exactly as `TurnLoopExecutor` does, so `$history`-style templates behave identically to a real run.
- `TryItOutResponseDto` returns only the last executed turn's `resolvedRequest`/`response`/`durationMs`/`traceId` — the exact same shape as today's single-turn response, no new fields.
- Single-turn test cases (no `multiTurnData`, or `multiTurnData` present but no per-turn binding — the N=1 collapse case) produce a byte-identical response to today.
- Turn failures fail fast, matching `TurnLoopExecutor`'s behavior.
- MCP_TOOL + multi-turn test case is rejected at try-it-out the same way it's rejected at run creation.

**Non-Goals:**
- `tryWithVariables` (suite-level, no bound test case) is unchanged — there is no `multiTurnData` source without a persisted `TestCase`.
- No persistence of try-it-out turn results — this stays a stateless preview, unlike real runs which write `TestCaseRunResult` rows.
- No change to `TurnLoopExecutor`, `PerTurnBindingDetector`, `RequestResolver`, or `ResponseColumnExtractor` themselves — try-it-out is purely a new caller of existing, unmodified components.
- No change to the MCP try-it-out flow beyond the new rejection guard — MCP arguments are still resolved as a single call.

## Decisions

**Turn planning lives in `ResolvedRequestService`, not `TryItOutService`.** `ResolvedRequestService` already owns the suite/test-case loading and JSONB deserialization (`requestTemplate`, `inputBindings`, `data`) inside its own `@Transactional(readOnly = true)` boundary. Turn planning needs the same loads plus `multiTurnData`, `responseColumns`, and the dataset's current schema (for `PerTurnBindingDetector`) — keeping it in this service avoids a second suite/test-case fetch and keeps DB access inside one transaction. `TryItOutService` gets a plan (template, bindings, response columns, per-turn merged data maps) and drives the turn loop itself, since the loop's HTTP invocation (`invokeAndBuildResponse`) must happen *outside* the DB transaction — same "load in a transaction, invoke after it closes" split the current single-turn flow already uses (see `try-it-out` spec, Scenario: Successful try-it-out with test case, which calls out this trade-off explicitly).

**Turn count/merge decision is delegated to `PerTurnBindingDetector`, not reimplemented.** Reusing it guarantees try-it-out's "will this run as 1 turn or N turns" answer never drifts from what a real run would decide for the same suite/test case — a second bespoke implementation would be a maintenance hazard (two places to keep in sync on every future change to per-turn semantics).

**Response returns only the last executed turn — no `turns[]` list, no new fields at all.** Originally considered exposing every turn as a `turns[]` list alongside the existing top-level result. Dropped after review: for the common case — a request template that accumulates history via `$append($history, [...])` — the last turn's `resolvedRequest` already contains every prior turn's messages, so a separate per-turn payload mostly just duplicated data already visible in the final turn. Returning only the last turn keeps `TryItOutResponseDto` byte-identical in shape to today's single-turn response for every case, multi-turn or not — no client-visible change beyond "the loop actually runs now instead of stopping after turn 0". The trade-off (accepted): for a turn that failed after some turns succeeded, or a suite whose JSONata doesn't fold prior turns into the request body, there's no way to inspect intermediate turns' individual `response`/`durationMs`/`traceId` through this endpoint — only the final (or failing) turn is visible.

**Fail-fast on turn failure.** Matches `TurnLoopExecutor.execute`'s existing behavior for real runs — a failed turn has no valid response to extract `frameBindings` from, so continuing would require inventing behavior (empty frame? repeat last frame?) that has no analogue in production runs and would make the preview diverge from what a real run would actually do at that point. The failed turn becomes the returned `resolvedRequest`/`response` (so its error is visible exactly where a caller already looks). This fail-fast detection only catches non-2xx status and `RequestBodyEvaluationException`; a transport-level exception (timeout, connection refused, unreachable deployment) during a turn's invocation is not caught at all and propagates as a plain error response, exactly as it did pre-change for the single-turn path. Converting `DialCoreDeploymentInvoker`'s thrown exceptions into a catchable `TurnOutcome`-like result would be required to close that gap, and is out of scope here. The same uncaught-exception gap also applies to `validateResolutionResult(resolved)`, called inside `runTurnSequence`'s try block right after `resolveForRun`: for turns after the first it can throw plain `ValidationException` (null resolved URL) or `TryItOutValidationException` (unresolved REQUIRED template variables), and `runTurnSequence`'s catch clause only catches `RequestBodyEvaluationException` — neither validation exception is caught, so it propagates uncaught, surfacing as a plain error response, exactly like the transport-exception gap above.

**MCP guard reuses the existing run-creation rejection, not a new bespoke check.** The `multi-turn-test-case` spec already defines "MCP suites reject multi-turn datasets" as HTTP 409 `INVALID_OPERATION`. Implementation should locate whatever component enforces this at run creation (likely a guard checked in the run-creation service) and reuse/extract it rather than re-deriving the MCP+multi-turn condition in `TryItOutService` — exact reuse point is an implementation task, not a design decision, since the check itself (`suiteType == MCP_TOOL && multiTurnData present`) is trivial but the *error construction* (exception type, code) should match existing precedent exactly.

**`tryWithVariables` is explicitly out of scope**, confirmed with the user: `multiTurnData` is a `TestCase`-only concept: there's no per-turn variables array in the current `TryItOutWithVariablesRequestDto`, and inventing one would be new API surface the user did not ask for.

## Risks / Trade-offs

- **[Risk]** Looping turns sequentially inside `tryWithTestCase` means try-it-out's total latency for a multi-turn case is the sum of all turn latencies (previously a single request). → **Mitigation**: this mirrors real run behavior exactly (also sequential), and try-it-out already has its own configurable read timeout (`dial.components.core.try-out.read-timeout-ms`) applied per-invocation; no new timeout concept needed. Document this latency characteristic in the OpenAPI description.
- **[Risk]** Reusing `PerTurnBindingDetector` requires the dataset's *current* schema, whereas real runs use a frozen snapshot schema. If a user edits the dataset schema between authoring a multi-turn case and trying it out, the turn-count decision could differ from what a subsequent real run would use if the schema is edited again before the run. → **Mitigation**: this is inherent to try-it-out being a preview of current state (the existing single-turn flow has the identical property — it already resolves against the *current* suite config, not a snapshot). Acceptable, not a regression.
- **[Risk]** `ResponseColumnExtractor.extract` assumes well-formed `responseColumns` definitions; a suite with no `responseColumns` configured (empty/null) means `frameBindings` for turn 2+ is always empty, so any `$history`-style template silently gets no history. → **Mitigation**: this is identical to real-run behavior (same extractor, same input) — not a new failure mode introduced by this change. No suppression/warning beyond what already exists for runs.
- **[Trade-off]** Not persisting turn results means a user can't diff a try-it-out multi-turn preview against a later real run's stored `TestCaseRunResult` rows through the API — only through manual comparison. Accepted: try-it-out has never persisted anything; adding persistence here would be a scope expansion beyond "preview" that the user didn't ask for.

## Resolved Questions

- **Exact class/method that enforces "MCP + multi-turn → 409 `INVALID_OPERATION`" at run creation, to reuse/mirror for try-it-out**: `TestSuiteRunService` (lines 92-97) throws `InvalidOperationException` when `suiteType == MCP_TOOL && testCaseService.datasetHasMultiTurnCases(datasetId)`. `TryItOutService.tryWithTestCase` mirrors this with a coarse presence check (`testCase.getMultiTurnData() != null`) rather than reusing `datasetHasMultiTurnCases` directly, since try-it-out already has the single `TestCase` in hand and doesn't need a dataset-wide scan.
- **Whether `ResolvedRequestService.resolveRequest` should be folded into the new turn-planning method or kept as-is**: Kept unchanged as its own method. `ResolvedRequestController.getResolvedRequest` (the separate preview/GET endpoint) also calls it, and that endpoint is out of scope for multi-turn support. `TryItOutService.tryWithTestCase` also still calls `resolveRequest` directly for the N<=1 single-turn path (byte-identical behavior, including graceful warning downgrade); only N>1 goes through the new `planTurns`/`runTurnSequence` path.
- **Whether to expose intermediate turns in the response**: initially implemented as additive fields, then removed after review. For the common case (a JSONata template that folds prior turns into the request body via `$append($history, [...])`), the last turn's `resolvedRequest` already contains the full accumulated conversation, so the separate per-turn payload was largely duplicating data already visible in the final turn. `TryItOutResponseDto` now stays exactly as it was before this change — no new fields.
