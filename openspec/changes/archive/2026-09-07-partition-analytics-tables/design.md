## Context

`test_case_run_results` and `test_case_eval_summaries` are the per-test-case-row fan-out tables in the analytics DB (rows = cases × runs × turns × requests) and are the two tables at risk from unbounded growth. Both already carry `PRIMARY KEY (created_at_ms, id)` and unique constraints trailing in `created_at_ms` — added specifically in anticipation of this work (`V1.1`, `V1.5`, `V1.17`, `V1.18` migration comments). Cursor pagination (`PostgresTestCaseRunResultRepository.findAll`, `PostgresEvalSummaryRepository.findAllInternal`) already orders by `created_at_ms DESC, id DESC` and filters by `created_at_ms = runCreatedAtMs` when the caller knows a specific run's timestamp. This design realizes native PostgreSQL declarative partitioning on top of that existing shape.

`test_case_eval_scores` is a 1:1 sibling of `test_case_eval_summaries` (one score/passed row per summary row, joined only by `eval_summary_id`) and therefore scales with exactly the same volume, even though it started without a time column of its own. It is included in this design as a partitioned table, paired to its parent's partition lifecycle, rather than being left unpartitioned with an ad-hoc row-level cleanup mechanism (an earlier draft of this design took that approach and was found to have a real bug — see D5).

Constraints: analytics DB only (meta untouched), no REST/DTO changes, cursor pagination semantics preserved, JDBC-only via jOOQ typed DSL (no JPA), Flyway-delivered schema changes, `@ConfigurationProperties` defaults in `application.yml` only, `@LogExecution` on all Spring components, exceptions passed as the last SLF4J arg.

Decisions already confirmed with the change owner (not open questions): single in-Flyway migration (no separate pre-validation runbook step), retention off by default (`retention-months=0`), cutover/month bounds computed dynamically from `now()` at migration time rather than a pinned literal date, `test_case_eval_scores` is partitioned in lockstep with `test_case_eval_summaries` using an accurate (join-based) backfill of its new `created_at_ms` column rather than a cheap sentinel value, so the JOIN predicate can also match on `created_at_ms` and preserve today's join-elimination optimization.

## Goals / Non-Goals

**Goals:**
- Partition `test_case_run_results` and `test_case_eval_summaries` by `created_at_ms`, monthly, with zero data movement (attach the existing table as a partition).
- Partition `test_case_eval_scores` by the same monthly boundaries, via a new `created_at_ms` column backfilled accurately from its parent summary row, so its partitions are removed automatically in lockstep with `test_case_eval_summaries`'s — no separate row-level cleanup mechanism.
- Preserve every existing constraint, index, and query shape — cursor pagination, `ON CONFLICT` upsert, `findAll`/`findAllForExport` — with no unintended Java-visible change beyond the parameter/JOIN changes explicitly listed in this design.
- Provide a scheduled job that keeps future partitions available ahead of writes (across all three tables) and can drop/detach expired partitions on an opt-in retention window, removing `test_case_eval_summaries` and `test_case_eval_scores` partitions for the same period together.
- Keep jOOQ codegen emitting exactly one `Table` class per partitioned parent, as today.
- Restore partition pruning on the one hot query (`findLatestComputationId`) that would otherwise silently regress to a cross-partition scan.

**Non-Goals:**
- Partitioning `run_metric_snapshots` or `metric_score_result` — neither has a partition-key-compatible PK/unique-constraint shape, and neither has `test_case_run_results`-level volume (`metric_score_result` in particular scales with statistics × metric fields per run, not with test-case-row count — verified against `MetricScoreComputationExecutor`). Deferred indefinitely; row-level `DELETE` remains their retention path if ever needed.
- Any REST API, DTO, or pagination-contract change.
- Automatic historical re-partitioning of the pre-cutover data finer than one `_p_legacy` bucket per table (an operator-run offline split is a separate, out-of-scope exercise if ever needed).
- Fixing the pruning gap on `findById`, or on `RunComparisonService`'s cross-run queries — both are documented, accepted follow-ups (no `created_at_ms` naturally in scope there without a REST contract change or extra plumbing).

## Decisions

### D1. Partition key: raw `created_at_ms` BIGINT, not a generated `timestamptz` column
Partitioning directly on the existing BIGINT epoch-millis column requires zero new columns, so nothing in the PK, unique constraints, `SELECT *`, or `ON CONFLICT (...)` inference list changes. Alternative considered: add a generated `created_at timestamptz` column as the partition key for more readable DDL bounds — rejected because Postgres requires the partition key to be part of every unique constraint, which would force a new column into two already-established unique constraints and change the jOOQ-generated `Keys`/`Tables` shape for no functional benefit. Cost accepted: partition bounds are opaque integers in DDL; mitigated by a `COMMENT ON TABLE` recording the human-readable UTC month on each partition, and centralizing all bound arithmetic in one Java class (`MonthlyPartitionBounds`) and one SQL expression pattern.

### D2. Granularity: monthly
Matches the proposal's stated default and the realistic write rate (one evaluation run produces a bounded burst of rows). Weekly would multiply partition count and maintenance-job overhead for no read-path benefit at current/projected volumes; hash partitioning was rejected because the workload is time-skewed (recent runs are read far more than old ones) and time-range partitioning is what makes retention a metadata operation.

### D3. Migration: single Flyway migration, ATTACH-based for the two pre-shaped tables; ATTACH-plus-backfill for `test_case_eval_scores`
`V1.20__PartitionAnalyticsHighVolumeTables.sql`, one script, one `cutover`/month-bounds computation shared by all three tables (computed once so every table's partitions land on identical boundaries).

**For `test_case_run_results` and `test_case_eval_summaries`** (no data copy):
1. Rename the existing table to `<table>_p_legacy`; rename its PK, unique constraint/index, and both secondary indexes to `_p_legacy`-suffixed names.
2. `CREATE TABLE <table> (LIKE <table>_p_legacy INCLUDING DEFAULTS INCLUDING COMMENTS) PARTITION BY RANGE (created_at_ms)`.
3. Recreate the PK, unique constraint/index, and both secondary indexes on the new (empty) parent under their **original** names — instant, and inherited by every partition attached or created afterward.
4. On the legacy table: `ADD CONSTRAINT ck_..._upper CHECK (created_at_ms < <cutover>) NOT VALID` then `VALIDATE CONSTRAINT` (keeps the heavy scan under `SHARE UPDATE EXCLUSIVE`; lets the subsequent `ATTACH` skip its own validation scan).
5. `ALTER TABLE <table> ATTACH PARTITION <table>_p_legacy FOR VALUES FROM (MINVALUE) TO (<cutover>)`.
6. Create partitions for the current month + `look-ahead-months`, then `CREATE TABLE <table>_p_default PARTITION OF <table> DEFAULT`.

**For `test_case_eval_scores`** (real backfill required — this table did not start with a time column):
1. `DELETE FROM test_case_eval_scores WHERE eval_summary_id NOT IN (SELECT id FROM test_case_eval_summaries)` — defensive removal of any orphaned score row with no matching summary (should not occur in practice; scores are documented as regenerable, so this is a safe no-op in the expected case).
2. `ALTER TABLE test_case_eval_scores ADD COLUMN created_at_ms BIGINT` (nullable initially).
3. `UPDATE test_case_eval_scores s SET created_at_ms = e.created_at_ms FROM test_case_eval_summaries e WHERE s.eval_summary_id = e.id` — a real, one-time table rewrite proportional to row count, the dominant cost of this migration (see Risks).
4. `ALTER TABLE test_case_eval_scores ALTER COLUMN created_at_ms SET NOT NULL`.
5. `ALTER TABLE test_case_eval_scores DROP CONSTRAINT test_case_eval_scores_pkey` (the old single-column PK).
6. Rename to `test_case_eval_scores_p_legacy`; pre-build the new composite unique index `(created_at_ms, eval_summary_id)` on it directly (`CREATE UNIQUE INDEX CONCURRENTLY` where the surrounding transaction context allows, else a plain `CREATE UNIQUE INDEX`) so the subsequent `ATTACH` doesn't need to build it under an exclusive lock.
7. `CREATE TABLE test_case_eval_scores (LIKE test_case_eval_scores_p_legacy INCLUDING DEFAULTS INCLUDING COMMENTS) PARTITION BY RANGE (created_at_ms)`; add the composite PK `(created_at_ms, eval_summary_id)` on the new parent.
8. Same `CHECK`/`VALIDATE`/`ATTACH` sequence as the other two tables, reusing the same `cutover` value.
9. Create partitions for the current month + `look-ahead-months` (same months as `test_case_eval_summaries`), then the `_p_default` partition.

`cutover` and month bounds are computed from `now()` inside a `DO $$ ... $$ / EXECUTE format(...)` block, so the migration text (and its Flyway checksum) is identical across environments regardless of when it runs. The whole migration is wrapped in per-table `relkind = 'p'` guards so it is a no-op if a given table is already partitioned (safe to re-run, safe if partitioning is pre-applied outside Flyway in an exceptional deployment). Table/index names are unqualified (no hardcoded schema), since the schema name differs between real deployments (`postgres.analytics.datasource.schema`, defaults `public`) and jOOQ's embedded-Postgres codegen run (`analytics`).

**Bug found and fixed via functional testing (DST-sensitive month arithmetic)**: the first implementation computed `v_cutover_ts`/`v_month_start` as `timestamptz` values and advanced them with `+ (i || ' months')::interval`. Postgres applies a calendar-unit interval to a `timestamptz` using the **connection's session timezone**, not pure UTC — so on a connection whose session timezone isn't UTC (observed in the functional-test environment, where the default connection timezone follows the host/JDBC client's timezone rather than `Etc/UTC`), adding months across a DST transition in that timezone silently shifted the computed boundary by an hour (caught by a functional test asserting exact partition bounds two months out — the November/December boundary landed exactly on a US DST transition and was off by 3600 seconds). Fixed by doing all month arithmetic on naive (`timestamp without time zone`) values — which have no attached zone and therefore no DST rule to apply — and converting to `timestamptz` only at the single point of extracting an epoch-millis value via `naive_value AT TIME ZONE 'UTC'` (unambiguous and DST-free, since UTC itself has no DST). This is a durable fix, not environment-specific: it removes the session-timezone dependency entirely rather than working around one observed timezone's DST schedule.

Alternative considered: `INSERT INTO ... SELECT` batched backfill into a freshly partitioned table for all three tables — rejected as strictly more expensive than ATTACH for the two tables that don't need a backfill; for `test_case_eval_scores`, which *does* need a real data-touching step regardless, ATTACH is still preferred over a full `INSERT ... SELECT` rebuild because the `UPDATE ... FROM` backfill only rewrites the column being added, not the whole row set into a new table (no double storage during migration).

Alternative considered: a cheap sentinel-value backfill for `test_case_eval_scores` (e.g. `created_at_ms = 0` for all legacy rows, no join) instead of the accurate join-based backfill — rejected (confirmed with the change owner) because it would force the JOIN predicate to stay `eval_summary_id`-only (a sentinel value can never match the real parent timestamp), permanently losing the join-elimination optimization and any chance of partition-wise joins for the life of the legacy data.

Alternative considered: pull the `NOT VALID`/`VALIDATE` step out of Flyway into a pre-migration runbook step, so Flyway's own step is metadata-only — rejected for this change (confirmed with the change owner): the project already accepts lock-conscious-but-in-Flyway DDL as precedent (`V1.13`, `V1.17`, `V1.18` comments), a split runbook would leave `flyway_schema_history` and the live schema divergent across environments during the gap, and the proposal already accepts an offline/maintenance-window activity, which is what pays for the ACCESS EXCLUSIVE lock duration of the validation scans and the `test_case_eval_scores` backfill.

### D4. Constraints/indexes
| Object | Columns | Contains `created_at_ms`? | Pre-existing or new? |
|---|---|---|---|
| `test_case_run_results_pkey` | `(created_at_ms, id)` | yes, leading | pre-existing |
| `uq_results_run_case_index` | `(test_suite_run_id, test_case_id, run_index, request_index, turn_index, created_at_ms)` | yes, trailing | pre-existing |
| `test_case_eval_summaries_pkey` | `(created_at_ms, id)` | yes, leading | pre-existing |
| `uq_eval_summaries_natural_key` | `(test_suite_run_id, test_case_id, run_index, request_index, turn_index, computation_id, created_at_ms)` | yes, trailing | pre-existing |
| `test_case_eval_scores_pkey` | `(created_at_ms, eval_summary_id)` | yes, leading | **new** — replaces the old single-column `(eval_summary_id)` PK; this is the one constraint in this design that isn't already partition-key-shaped, which is why `test_case_eval_scores` needs the backfill the other two tables don't |

`uq_eval_summaries_natural_key` is a bare `CREATE UNIQUE INDEX` (not a table constraint) — recreated as a unique index on the parent under its original name (supported for partitioned tables). `uq_results_run_case_index` stays a table constraint. `ON CONFLICT (...) DO NOTHING` in `PostgresTestCaseRunResultRepository.saveAll` is unaffected: index inference against a partitioned unique constraint works identically. `PostgresTestCaseEvalScoreRepository.saveAll`'s `ON CONFLICT` arbiter changes from `(eval_summary_id)` to `(created_at_ms, eval_summary_id)` to match the new composite PK (see D5a). All secondary indexes become *partitioned indexes*, created once on each parent and auto-materialized on every current and future partition — the maintenance job never creates indexes itself.

### D5. Partition maintenance: dedicated scheduled job, modeled on `TestCaseRunInputsRetentionJob`
New components:
- `data.db.analytics.repository.AnalyticsPartitionRepository` (interface) / `data.db.analytics.repository.partition.PostgresAnalyticsPartitionRepository` (implementation) — all raw DDL/introspection (`listPartitions` via `pg_inherits`/`pg_class`/`pg_get_expr`, `createRangePartition`, `dropPartition`, `detachPartition`, `countRows`). jOOQ has no partition-DDL API, so this repository uses `analyticsJdbcTemplate` directly — an intentional, narrow exception alongside the existing `configuration.datasource`/`service.infrastructure.health` exemptions to the JDBC-template fence, justified by DDL having no typed-DSL equivalent. The implementation lives in its own `data.db.analytics.repository.partition` sub-package (not the flat `repository` package where the interface sits) specifically so `JdbcTemplateFenceTest`'s allowed-packages list can exempt only that narrow sub-package, not the whole `data.db.analytics.repository` tree where every other repository must keep using the typed jOOQ DSL. Partition names are built only from constants + `YearMonth` (never user input) but are still validated against `^[a-z0-9_]+$` before use in DDL, as defense in depth.
- `service.infrastructure.partition.AnalyticsPartitionMaintenanceService` — orchestration: `ensureFuturePartitions()`, `dropExpiredPartitions()`, `reportDefaultPartitionUsage()`. Each phase runs in its own `@Transactional("analyticsTransactionManager")` unit so one failed drop cannot roll back successful creates. Ordering is always create-ahead → drop → report, so a failure in the drop phase never leaves the system without a writable partition. `ensureFuturePartitions()` creates matching partitions for all three tables (`test_case_run_results`, `test_case_eval_summaries`, `test_case_eval_scores`) on the same month set; `dropExpiredPartitions()` evaluates `test_case_run_results` independently but removes `test_case_eval_summaries` and `test_case_eval_scores` for a given month **as a pair** (see below).

  **Bug found and fixed via functional testing**: `ensureFuturePartitions()`'s per-month existence check cannot be a name-only lookup (`listPartitions(table).anyMatch(p -> p.name().equals(expectedName))`). The current UTC month has **no dedicated `_p<yyyyMM>` partition at all** for as long as `_p_legacy` remains unpruned — the migration deliberately folds the current month into the wide legacy range (see D3) — so a name-only check would find nothing, conclude the month is "missing," and attempt `CREATE TABLE ... PARTITION OF ... FOR VALUES FROM (...) TO (...)` for a range that **overlaps `_p_legacy`**, which Postgres rejects. This would have broken on the very first real maintenance run after every deployment, not just in tests. The fix: check whether the month's start is contained within any existing **non-DEFAULT** partition's range (`lowerBoundMs <= point < upperBoundMs`, with `null` bounds treated as unbounded), not just an exact name match. The DEFAULT partition is deliberately excluded from "coverage," since falling into it is exactly the condition this method exists to prevent.
- `service.infrastructure.partition.AnalyticsPartitionMaintenanceJob` — `@Component @LogExecution @Slf4j @RequiredArgsConstructor`, `@Scheduled(fixedDelayString = "${analytics.partitioning.maintenance-interval-ms}", initialDelayString = "${analytics.partitioning.initial-delay-ms}")`. Shape mirrors `TestCaseRunInputsRetentionJob` exactly (log start, try/catch per phase, exception passed last to SLF4J). No-ops when `analytics.partitioning.enabled=false`.
- `service.infrastructure.partition.MonthlyPartitionBounds` — pure static helper (no Spring dependency): partition naming, UTC month bound math, look-ahead/expiry calculation. This is the unit-testable core of the feature.
- `constants.AnalyticsPartitioningConstants` — parent table names, `_p`/`_p_default`/`_p_legacy` naming pieces, `yyyyMM` format, drop-cap-per-run.
- `configuration.properties.analytics.AnalyticsPartitioningProperties` — `@Validated @ConfigurationProperties`, no field initializers:

```yaml
analytics:
  partitioning:
    enabled: ${ANALYTICS_PARTITIONING_ENABLED:true}
    look-ahead-months: ${ANALYTICS_PARTITIONING_LOOK_AHEAD_MONTHS:2}
    retention-months: ${ANALYTICS_PARTITIONING_RETENTION_MONTHS:0}   # 0 = never drop
    archive-instead-of-drop: ${ANALYTICS_PARTITIONING_ARCHIVE_INSTEAD_OF_DROP:false}
    maintenance-interval-ms: 86400000
    initial-delay-ms: 60000
```

`retention-months: 0` (retain forever) is the deliberate default, confirmed with the change owner — shipping a release that silently starts deleting analytics history would be unacceptable; operators opt in explicitly.

Safety rules in the service: never drop/detach the DEFAULT partition on any table; never remove a partition whose range contains `now()`; remove only when a partition's *upper* bound is `<= startOfMonth(now) - retention-months`; cap removals per run and log a WARN when the cap is hit.

**Paired removal of `test_case_eval_summaries` and `test_case_eval_scores` partitions.** Because `test_case_eval_scores` is now partitioned on the same monthly boundaries as its parent (see D5a), retention is symmetric and requires no special-cased row-level cleanup: for a given expired month M, `dropExpiredPartitions()` removes `test_case_eval_summaries_pM` and `test_case_eval_scores_pM` **together, using the same mode** — both dropped if `archive-instead-of-drop=false`, both detached if `true` — in the same maintenance cycle. There is no asymmetry to get wrong (an earlier draft of this design instead reaped `test_case_eval_scores` rows via a row-level `DELETE` scoped to the summaries partition, gated to only run on the drop path and never on archive — that mechanism is superseded by this pairing and removed from the design entirely). The scores partition for a month is removed first, then the summaries partition, purely for tidy logical ordering; there is no physical FK to enforce this order, so a crash between the two leaves at worst one extra already-removed partition to reconcile on the next cycle, never data loss on the still-live side.

The per-run removal cap (`AnalyticsPartitioningConstants.MAX_REMOVALS_PER_RUN`) counts one decrement per expired **month** processed, not per physical partition removed — removing a `test_case_eval_summaries`/`test_case_eval_scores` pair for a month consumes one unit of the cap even though it removes two physical partitions, matching how `test_case_run_results` consumes one unit per single physical partition. This keeps the cap's meaning ("how many months of history does this run advance") consistent across all three tables, at the cost of a paired-table run doing up to 2x the physical DDL of an unpaired run for the same cap value — operators sizing the cap for `test_case_eval_summaries`/`test_case_eval_scores` retention should account for that.

### D5a. `test_case_eval_scores` write path and JOIN predicate
Three code paths need updating to support the new composite key, all verified against the current implementation:

1. **Write path**: `TestCaseEvalScoreService.batchCreate` gains a `createdAtMs` parameter (a single value for the whole batch, mirroring how `computedAtMs` is already passed once per batch) alongside the existing per-item DTOs. `InProcessMetricEvaluationExecutor.writeRowScores` passes `context.getRunCreatedAtMs()` through — this value is already computed and used elsewhere in the same executor (e.g. for `test_case_eval_summaries.created_at_ms` itself in `EvalSummaryService.batchCreate`), so no new query is introduced. `PostgresTestCaseEvalScoreRepository.saveAll` sets the new `created_at_ms` column from this value on every inserted row.
2. **Upsert arbiter**: `PostgresTestCaseEvalScoreRepository.saveAll`'s `.onConflict(TEST_CASE_EVAL_SCORES.EVAL_SUMMARY_ID)` becomes `.onConflict(TEST_CASE_EVAL_SCORES.CREATED_AT_MS, TEST_CASE_EVAL_SCORES.EVAL_SUMMARY_ID)`, since Postgres requires the arbiter to match an existing unique constraint/index exactly, and the single-column one no longer exists.
3. **JOIN predicate**: all 5 sites that join `test_case_eval_scores` to `test_case_eval_summaries` — `PostgresEvalSummaryRepository.findById`, `.buildListQuery`, `.buildExportQuery`, `.buildExportWithBodiesQuery`, and `PostgresEvalSummaryEntityResolver.table()` — change from `ON eval_summary_id = test_case_eval_summaries.id` to `ON eval_summary_id = test_case_eval_summaries.id AND created_at_ms = test_case_eval_summaries.created_at_ms`. Because the backfill (D3) populated every legacy row with its *actual* parent timestamp rather than a sentinel, this predicate matches correctly for all existing data, not just new writes. `PostgresEvalSummaryEntityResolver`'s narrowed `SCORES_JOIN` derived table (aliased `"tces_scores"`, used to avoid a `computed_at_ms` naming collision) must add `created_at_ms` to its projected column list to support the extended join condition.

This preserves the join-elimination optimization documented in `PostgresEvalSummaryEntityResolver`'s class Javadoc (Postgres can skip the join for queries that reference neither `score` nor `passed`) — the optimization now rests on the composite key rather than the single-column one, but the join condition still covers a full unique constraint on the child side, which is what the optimization requires. It additionally opens the door to partition-wise join execution, since both sides of the join now filter on the same partition key.

### D6. jOOQ codegen: exclude partition children
`build.gradle`'s analytics `Database.withExcludes(...)` (currently `"flyway_schema_history"`) becomes:

```groovy
.withExcludes("flyway_schema_history|(test_case_run_results|test_case_eval_summaries|test_case_eval_scores)_p(_default|_legacy|\\d{6})")
```

Explicit enumeration of the three parent names (rather than a blanket `.*_p\d{6}`) avoids silently excluding some future, unrelated table that happens to match the pattern. The meta generator is untouched. After `V1.20` exists, `./gradlew generateJooq` must be run and the regenerated `src/main/java-generated/` committed — the expected diff is empty for `test_case_run_results`/`test_case_eval_summaries`'s `Table`/`Keys`/`Indexes` classes (partitioning is transparent to jOOQ's catalog introspection of the parent relation), but a **real, reviewed diff is expected for `test_case_eval_scores`**: its new `created_at_ms` column and composite PK are genuine schema changes that must show up in the generated `Table`/`Keys` classes.

**Verification gate**: this is the one point in the design that must be empirically confirmed before the rest of the implementation proceeds — run `generateJooq` against the new migration locally and confirm the diff is a no-op (or absent) for `test_case_run_results`/`test_case_eval_summaries`, and that `test_case_eval_scores`'s diff contains exactly the expected new column and composite key (nothing else, no leaked partition-child tables), before writing any downstream code that assumes these shapes. If jOOQ instead emits per-partition `Table` classes or drops a parent, the exclude regex needs adjustment before task 2 begins.

### D7. Restoring pruning on `findLatestComputationId`
`PostgresEvalSummaryRepository.findLatestComputationId(UUID runId)` and `existsByRunIdAndComputationId(UUID runId, UUID computationId)` currently query only by `test_suite_run_id`; post-partitioning this becomes a merge-append across every partition. Fix, threading the run's `created_at_ms` (already available at every call site) through as a nullable equality predicate:

1. `EvalSummaryRepository.findLatestComputationId(UUID runId, Long runCreatedAtMs)` / `existsByRunIdAndComputationId(UUID runId, UUID computationId, Long runCreatedAtMs)` — adds `AND created_at_ms = ?` when non-null.
2. `ComputationResolver.resolve(String computation, UUID runId, Long runCreatedAtMs)` — 3-arg signature. 4 in-repo call sites, one more than originally scoped, found during implementation: `EvalSummaryService.resolveComputationId`, `EvalSummaryExportService.resolveContext`, `MetricScoreLatestComputationDefaulter.resolveLatestComputation` (passes `null`, see below), and `RunComparisonService.requireComputation` (also passes `null`, see the expanded note below this list — an initial attempt to thread the run's real `getCreatedAt()` through here broke 16 functional tests).
3. `EvalSummaryService` — already calls `resolveRunCreatedAtMs(runId)` a few lines below each `resolveComputationId(...)` call; hoist it above and pass through. No new query introduced.
4. `EvalSummaryExportService.resolveContext` — `metaSetup.run()` is already loaded before `computationResolver.resolve(...)` is invoked; pass `metaSetup.run().getCreatedAt()`.
5. `MetricScoreLatestComputationDefaulter` (Query DSL path) — passes `null` (preserves current behavior exactly). Injecting a meta-DB repository into this `query.service.repository` component to obtain `created_at_ms` would put a cross-datasource read inside Query DSL resolution, which is a disproportionate cost for a `LIMIT 1` indexed lookup that isn't on a hot loop. Documented as an accepted, deliberate gap in the method's Javadoc.
6. `EvalSummariesSchemaProvider` uses `RunMetricSnapshotRepository.findLatestComputationId` against the (unpartitioned) `run_metric_snapshots` table — unaffected, no change.

Accepted, documented pruning losses that remain out of scope: `findById` on both repositories scans across partitions via the partitioned `idx_results_id`/`idx_eval_summaries_id` — bounded by partition count, not by row count (no REST contract change permitted to fix this); `RunComparisonService`'s `countMatches`/`findUnmatchedIds` (two runs, no single `created_at_ms` in scope) — flagged as a good future follow-up.

`RunComparisonService.requireComputation` *also* passes `null` despite having the calling run's `TestSuiteRunResponseDto.getCreatedAt()` trivially available — an initial implementation attempt threaded it through, which broke 16 `RunComparisonFunctionalTests` cases with 409s instead of 200s. Root cause: `RunComparisonFunctionalTests` seeds its `test_case_eval_summaries` fixtures with a fixed hardcoded `createdAtMs` constant (`1_700_000_000_000L`), completely decoupled from the real (current-time) `test_suite_runs.created_at` that `getCreatedAt()` returns — a test-fixture artifact, not a production data issue (the real write path, `EvalSummaryService.batchCreate`, always sets `created_at_ms = run.getCreatedAt()`, so production rows never drift this way). Fixing it properly would mean auditing and updating every such fixture across that test file, which is unplanned scope beyond this task group; reverted to `null` instead, documented here as an explicit accepted gap for a future, separately-scoped follow-up.

## Risks / Trade-offs

- **[Risk] jOOQ may not cleanly emit the partitioned parent as a single `Table`, or its `withExcludes` matching may behave unexpectedly against `relkind='p'` children.** → Mitigation: D6's verification gate — run and inspect a real `generateJooq` diff before any downstream implementation task depends on the generated classes being unchanged.
- **[Risk] The ACCESS EXCLUSIVE lock held during the migration's constraint/index recreation and `ATTACH` step blocks reads/writes on the busiest tables for the duration of the validation scans.** → **Correction found during implementation**: the `NOT VALID`/`VALIDATE` split does *not* actually reduce the effective lock level in this migration as delivered, because Flyway runs the whole script inside one transaction — a lock acquired by an earlier statement in that transaction (e.g. the `RENAME`/`ADD CONSTRAINT PRIMARY KEY` steps, which take `ACCESS EXCLUSIVE`) is held until the transaction commits, regardless of what lock level a later statement like `VALIDATE CONSTRAINT` would normally request on its own. So the whole per-table block runs under the strongest lock acquired anywhere in it, for its full duration. The split is retained anyway (and documented as such in the migration's header comment) purely so it can be cleanly pulled apart later: a deployment that needs the real non-exclusive-scan benefit would run the `ADD CONSTRAINT ... NOT VALID` + `VALIDATE CONSTRAINT` pair as a separate statement, in its own transaction, *before* this migration runs (the pre-migration runbook alternative already discussed and rejected for this change) — that's the actual mitigation, not something this single-transaction migration provides on its own. Accepted as-is: an offline/maintenance-window activity per the proposal.
- **[Risk] `test_case_eval_scores`'s backfill (`UPDATE ... FROM` joining every row to its parent summary) is a genuine, non-trivial write — the one part of this migration that is not a cheap metadata-only operation, and it is proportional to the same row count as `test_case_eval_summaries` itself.** → Mitigation: this was a deliberate, confirmed trade-off (over a cheap sentinel backfill) made specifically to preserve join-elimination and enable partition-wise joins; it should be sized into the maintenance-window estimate alongside the two ATTACH-based tables' validation scans, and is the dominant cost driver of the whole `V1.20` migration. If a deployment's `test_case_eval_scores` volume makes this backfill too slow for one maintenance window, the same UPDATE can be batched by a range of `eval_summary_id`/`ctid` without changing the end-state schema.
- **[Risk] A write with `created_at_ms` far outside any existing partition falls into `_p_default`, and once enough rows accumulate there, creating the "missing" real partition requires scanning/locking the default partition.** → Mitigation: `reportDefaultPartitionUsage()` logs a WARN with each table's default partition row count every maintenance cycle, so operators notice before it becomes a problem; `created_at_ms` is a run's meta-DB creation timestamp, not user input, so pathological skew is operationally unlikely.
- **[Risk] Threading `runCreatedAtMs` through `ComputationResolver.resolve` touches several call sites across `EvalSummaryService`/`EvalSummaryExportService`.** → Mitigation: verified that every call site already loads the value a few lines away for other purposes; this is parameter hoisting, not a new query or new cross-service dependency.
- **[Trade-off] `run_metric_snapshots` and `metric_score_result` remain unpartitioned.** → Accepted: neither has a compatible key shape without a larger constraint migration, and neither currently has `test_case_run_results`-level volume; revisit if their growth profile changes.

## Migration Plan

1. Land `V1.20__PartitionAnalyticsHighVolumeTables.sql`; verify locally against a copy of production-shaped (but not production) data if available, otherwise against the standard Testcontainers/embedded-Postgres path. Time the `test_case_eval_scores` backfill step specifically, since it is the migration's dominant cost.
2. Run `./gradlew generateJooq`, confirm the D6 diff expectations (no-op for the two pre-shaped tables, an expected real diff for `test_case_eval_scores`), commit `src/main/java-generated/`.
3. Ship `AnalyticsPartitionMaintenanceJob` and properties with `enabled=true`, `retention-months=0` — partitions get created ahead of need from day one for all three tables; nothing is ever dropped or detached until an operator opts in.
4. Land the `findLatestComputationId`/`ComputationResolver` pruning fix, and the `test_case_eval_scores` write-path/JOIN changes (D5a).
5. Deploy behind the standard release process; the migration runs automatically on Flyway's next `migrate()` call during application startup, inside the announced maintenance window sized to cover the backfill.

**Rollback** (documented runbook, not a Flyway `U` migration — the project is forward-only): disable `analytics.partitioning.enabled` first. Same-month rollback (expected case, since monthly partitions hold only post-cutover data): for each of the three tables, `DETACH` every partition including `_p_legacy`, `DROP` the now-empty parent, `RENAME` `_p_legacy` back to the original name/constraints/indexes, drop the `CHECK`, then `INSERT ... SELECT` the detached partitions' rows back in and drop them — metadata-only plus a small copy for `test_case_run_results`/`test_case_eval_summaries`. For `test_case_eval_scores` specifically, also `DROP COLUMN created_at_ms` and restore the original single-column PK/`ON CONFLICT` shape after the table is reassembled, so the rollback fully reverses D5a's write-path/JOIN changes as well as the partitioning itself. Late rollback is the same shape, batched, proportional to post-cutover volume. Either way, follow with a forward Flyway migration that is a no-op when the table is already unpartitioned, so `flyway_schema_history` stays consistent for subsequent deploys.
