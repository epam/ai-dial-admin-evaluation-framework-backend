## Why

The analytics DB's two highest-volume tables — `test_case_run_results` and `test_case_eval_summaries` — plus their 1:1 sibling `test_case_eval_scores`, are append-only and grow monotonically with no archival mechanism. As row counts grow into the tens/hundreds of millions, query latency on cursor-paginated list endpoints and metric aggregations will progressively degrade, and the only removal path today is row-level `DELETE`, which is expensive, WAL-heavy, and depends on autovacuum to reclaim space. Both tables were already deliberately designed for this: their composite `PRIMARY KEY (created_at_ms, id)` and unique constraints trailing in `created_at_ms` exist specifically "for future time-based partitioning" (migration comments in `V1.1`, `V1.5`, `V1.17`, `V1.18`), and cursor pagination already orders/filters by `(created_at_ms, id)`. Addressing this now, before the tables become unwieldy, is significantly cheaper than retrofitting partitioning under production pressure.

## What Changes

- Convert `test_case_run_results`, `test_case_eval_summaries`, and `test_case_eval_scores` (analytics DB) from plain tables to native PostgreSQL declarative RANGE partitioning, monthly, keyed on `created_at_ms`. `test_case_run_results` and `test_case_eval_summaries` are attached as a `_p_legacy` partition with zero data copy (their PK/unique constraints already end in `created_at_ms`); `test_case_eval_scores` gains a new `created_at_ms` column (backfilled from its parent summary row via `UPDATE ... FROM` — a real, one-time table rewrite) and a new composite PK `(created_at_ms, eval_summary_id)` before the same ATTACH treatment. All delivered in one Flyway migration (`V1.20__PartitionAnalyticsHighVolumeTables.sql`) that shares one computed cutover across all three tables and creates partitions for the current + look-ahead months plus a `_p_default` catch-all on each.
- Add a scheduled partition-maintenance job (`AnalyticsPartitionMaintenanceJob`) that proactively creates upcoming monthly partitions ahead of need (for all three tables) and, when a retention window is configured, drops (or detaches, if archival is preferred) partitions past their retention horizon — turning archival into a near-instant metadata operation instead of row-level `DELETE`. Off by default (`retention-months=0`, never drop) until an operator opts in.
- `test_case_eval_scores` partitions are removed **in lockstep** with their parent `test_case_eval_summaries` partition: whichever mode (drop or archive) applies to a `test_case_eval_summaries` partition for a given month applies identically, in the same cycle, to the paired `test_case_eval_scores` partition — no separate row-level cleanup logic, no risk of the two tables diverging.
- Extend the `test_case_eval_scores` write path (`TestCaseEvalScoreService`, `InProcessMetricEvaluationExecutor`, `PostgresTestCaseEvalScoreRepository`) to populate the new `created_at_ms` column from the run's already-available creation timestamp, and update its `ON CONFLICT` upsert arbiter and all 5 JOIN sites (`PostgresEvalSummaryRepository`, `PostgresEvalSummaryEntityResolver`) to match on the new composite key.
- Restore partition pruning on `EvalSummaryRepository.findLatestComputationId` / `existsByRunIdAndComputationId` (used by "latest computation" resolution) by threading the run's already-available `created_at_ms` through `ComputationResolver.resolve` and its callers as an additional equality predicate.
- Adjust jOOQ codegen (`build.gradle`) to exclude partition-child relations (for all three tables) from generation so only the parent tables' `Table` classes exist, as today.
- No REST API or DTO changes. Cursor-based pagination semantics on analytics endpoints are preserved (partition pruning is transparent to clients). Scope is analytics DB only — meta DB is unaffected.
- `run_metric_snapshots` and `metric_score_result` are explicitly **not** partitioned in this change (no PK-compatible time column, and low volume — `metric_score_result` scales with statistics × metric fields per run, not with test-case row count); retention for them, if ever needed, stays row-level `DELETE`.

## Capabilities

### New Capabilities
- `analytics-partitioning`: Native PostgreSQL declarative time-based (monthly) partitioning of `test_case_run_results`, `test_case_eval_summaries`, and `test_case_eval_scores` (the latter paired to its parent's partition lifecycle), including the partition-maintenance job (proactive partition creation, lockstep retention-based drop/detach), configuration properties, and the accompanying jOOQ codegen and pruning-predicate adjustments.

### Modified Capabilities
(none — no existing spec's requirements change in externally observable behavior; the `findLatestComputationId` change is an internal query-shape optimization with an identical result contract)

## Risks

- The `test_case_eval_scores` backfill (`UPDATE ... FROM` joining every row to its parent summary) is a real, non-trivial write proportional to row count — the dominant cost driver of the `V1.20` migration. It must be timed/sized into the maintenance-window estimate alongside the two ATTACH-based tables' validation scans.
- Because Flyway runs the whole migration in a single transaction, the entire per-table block runs under the strongest lock acquired anywhere in it (`ACCESS EXCLUSIVE`, from the rename/constraint steps) for its full duration — production reads/writes on these tables are blocked for the migration window. This is an offline/maintenance-window activity, not a zero-downtime one.
- Rollback is a documented runbook (detach/rename/reattach steps, plus reversing the `test_case_eval_scores` schema change), not a Flyway `U` (down) migration — the project is forward-only.

See design.md's Risks & Trade-offs and Migration Plan sections for full detail.
