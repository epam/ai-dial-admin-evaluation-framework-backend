## Context

EF currently captures the user's JWT at run-creation time and propagates it via `AuthorizationTokenHolder` (ThreadLocal) + `TokenPropagationHelper` to async worker threads. `DialCoreDeploymentInvoker`/`EvaluationWorker`/`DeploymentTurnInvoker`/`McpToolInvoker` read the credential from `EvaluationContext.getCredential()` (populated from `AuthorizationTokenHolder` at dispatch time) and include it in the outbound request header. During long eval runs (minutes to hours), a JWT-kind credential expires, causing 401 failures mid-run.

Additionally, when test case requests include DIAL file references from the EF bucket (e.g., multi-modal inputs), evaluated deployments receive the file URL but cannot access it — DIAL Core has no mechanism to verify EF's authorization and propagate file access to the downstream deployment's per-request key.

DIAL Core's **per-request key (PRK)** mechanism solves both issues: a PRK is generated by DIAL Core when it calls an application, lives for the lifetime of that HTTP connection, carries user identity and cost-attribution data through the full call tree, and enables DIAL Core's auto-sharing mechanism to propagate EF's bucket file access to evaluated deployments.

**Already-generalized infrastructure this design reuses (confirmed against current code, not assumed):**

- `CallerCredential(value, kind)` — `kind` is `BEARER` or `API_KEY`. `headerName()`/`headerValue()` pick `Authorization: Bearer ...` or `Api-Key: ...`. A PRK is simply an `API_KEY`-kind `CallerCredential` — no new credential type needed.
- `AuthorizationHeaderInterceptor` (registered for every request) already captures an inbound `Api-Key` header into `AuthorizationTokenHolder` as an `API_KEY`-kind credential, with the same precedence rules used everywhere else in the app. The new internal endpoint gets this for free.
- `EvaluationContext.credential` is already typed as `CallerCredential`, not a JWT string — `EvaluationWorker`, `DeploymentTurnInvoker` → `DialCoreDeploymentInvoker`, and `McpToolInvoker` all already read `context.getCredential()` and set the outbound header via `credential.headerName()/headerValue()`, agnostic of `BEARER` vs `API_KEY`. **No invoker changes are needed for PRK support.**
- `ApiKeyAuthenticationFilter` + `CoreApiKeyIntrospector` already authenticate an `Api-Key` header by calling `GET /v1/user/info` on DIAL Core (with caching via `ApiKeyCache`), populating `SecurityContextHolder` with the resolved identity/roles. **This already does PRK validation and identity resolution — no new `DialUserInfoClient` is needed.**
- `TestSuiteEvaluationJob.dispatch(UUID runId, CallerCredential credential, boolean skipDeploymentPhase)` is the existing, single dispatch entry point used by the public run-creation path. The new internal endpoint calls the same method with an `API_KEY`-kind credential instead of a `BEARER`-kind one.
- `ActiveRunRegistry` already tracks one `RunHandle` per in-flight run, keyed by `runId`, supporting cancellation and lookup. **No new PRK-keyed store is needed** for duplicate-trigger detection or cancel-on-disconnect.

Because of this, the only genuinely new work is: (1) a mechanism to make EF *receive* a PRK in the first place by being invoked through a DIAL Application Route, and (2) wiring that receiving endpoint into the existing dispatch path instead of inventing parallel PRK-aware machinery.

**Current flow:**
```
EF UI -> EF BE (POST /api/v1/test-suites/{id}/runs)
  -> captures JWT (ThreadLocal, as a BEARER CallerCredential)
  -> dispatches TestSuiteEvaluationJob.dispatch(runId, credential, false) in-process
  -> DialCoreDeploymentInvoker uses the BEARER credential from EvaluationContext
  [JWT expires after N minutes -> 401 on deployment call]
```

**Target flow (DIAL App mode):**
```
EF UI -> EF BE (POST /api/v1/test-suites/{id}/runs)        [unchanged, returns 202 with runId]
  -> creates run record, captures JWT once
  -> spawns virtual thread: POST /v1/deployments/{deploymentName}/route/api/internal/runs/{runId}/execute
       Authorization: <user JWT>  <- used exactly once
           |
       DIAL Core: validates JWT, generates PRK, proxies to EF internal endpoint
           |
       EF internal: POST /api/internal/runs/{runId}/execute
                    Api-Key: <per-request-key>  <- no expiry while connection open
                    (authenticated by the EXISTING ApiKeyAuthenticationFilter/CoreApiKeyIntrospector chain)
  -> controller calls the EXISTING TestSuiteEvaluationJob.dispatch(runId, credential, false)
     with credential = API_KEY-kind CallerCredential(prk)
  -> eval execution uses that credential for all DIAL Core calls (no new branching)
  -> SSE heartbeat (every 30s, 10x margin under DIAL Core's 300s idle timeout) keeps connection alive
  [connection open = PRK valid; eval can run for hours]
```

## Goals / Non-Goals

**Goals:**
- Solve JWT expiry for eval runs of arbitrary duration without token storage or refresh
- Enable DIAL Core's PRK auto-sharing chain for EF bucket files passed as links to evaluated deployments
- Preserve user identity and cost attribution through the full execution call tree
- Zero breaking changes — gradual rollout via `dial-app-proxy.enabled` feature flag
- Dual-mode operation: existing JWT path remains fully functional when flag is off
- Reuse EF's existing credential/auth generalization instead of adding a parallel PRK-specific stack

**Non-Goals:**
- Replacing EF's REST API with a DIAL chat completions interface
- Storing PRKs in Redis or any persistent store (never stored at all — the PRK only ever lives as the in-flight request's `CallerCredential`, exactly like a JWT does today)
- Changing any public API contract (`/api/v1/...` unchanged)
- Output file auto-sharing to user's DIAL bucket (deferred to v2)
- MCP tool integration for LLM-driven eval triggering (separate future concern)
- MetricEvaluationWorker DIAL integration (no DIAL calls today; the same generic `CallerCredential` path is available for future use without additional changes)

## Decisions

### Decision 1: DIAL Application Routes as trigger mechanism

**Alternatives considered:**

| Option | PRK generation | Semantics | SSE | Request format |
|--------|---------------|-----------|-----|----------------|
| Chat Completions | Confirmed | LLM API repurposed | Yes | Forced `messages[]` + `choices/delta` |
| **DIAL App Routes** | Confirmed | Native REST | Yes (HTTP proxy) | EF's own format |
| MCP Endpoints | Forwards caller PRK, doesn't mint a new one | LLM tool-call pattern | No (synchronous) | N/A |

DIAL Application Routes confirmed to generate PRKs in `route_authorization.md`:
> *"We want to pass per request API key to route as we do models/applications on chat completion request."*

Routes are chosen because they offer the same PRK guarantees as chat completions with no protocol overhead. EF's internal endpoint receives a plain HTTP POST with `Api-Key: <prk>` and can respond with any SSE format. No wrapping/unwrapping of OpenAI message formats required.

**DIAL Core route config (to be documented in `docs/configuration.md`):**
```json
{
  "applications": {
    "EF": {
      "displayName": "Evaluation Framework",
      "routes": {
        "run_execute": {
          "paths": ["/api/internal/runs/[^/]+/execute$"],
          "methods": ["POST"],
          "rewritePath": true,
          "upstreams": [{"endpoint": "http://ef-backend:8080"}]
        }
      }
    }
  }
}
```

**Application properties:**
```yaml
dial-app-proxy:
  enabled: true
  deployment-name: EF
  heartbeat-interval-ms: 30000
  trigger-read-timeout-ms: 43200000

config:
  rest:
    security:
      api-key:
        enabled: true
```

Public route URL: `POST /v1/deployments/EF/route/api/internal/runs/{runId}/execute`
EF receives at: `POST http://ef-backend:8080/api/internal/runs/{runId}/execute`
DIAL Core injects: `Api-Key: <per-request-key>`, `X-DIAL-APPLICATION-ID: EF`

The default deployment name is `EF` (configurable via `dial-app-proxy.deployment-name`, for environments that register it under a different name).

### Decision 2: No dedicated PRK store — reuse `CallerCredential` + `ActiveRunRegistry`

The original design for this change proposed a `PerRequestKeyStore` (`ConcurrentHashMap<UUID, String>`, runId → PRK) plus a `RunIdHolder` ThreadLocal so other components (the deployment invoker, `AuthorResolver`) could look up "the PRK for the currently-executing run" independently of the request thread.

That store is unnecessary: `EvalExecuteInternalController` already runs *on* the request thread that has the PRK in `AuthorizationTokenHolder` (via the standard `AuthorizationHeaderInterceptor` + `ApiKeyAuthenticationFilter` chain, identical to how a JWT caller's bearer credential is available on the public endpoint's request thread). It captures that `CallerCredential` once, the same way `TestSuiteRunService.createRun` already does, and hands it directly to `TestSuiteEvaluationJob.dispatch(runId, credential, false)` — the credential then flows through `EvaluationContext.credential` for the run's whole lifetime via the existing propagation path, with zero new state to manage, clean up, or leak across runs.

Duplicate-trigger detection (was: reject if `PerRequestKeyStore` already has an entry for `runId`) and cancel-on-disconnect (was: remove the entry, notify cancellation) are both already served by `ActiveRunRegistry`: checking whether a `RunHandle` is already registered for `runId` gives the 409 check, and `registry.cancel(runId)` is the existing cancellation hook.

| Option | Pros | Cons |
|--------|------|------|
| **Reuse `CallerCredential` + `ActiveRunRegistry`** (chosen) | Zero new stateful components; identical lifecycle guarantees (request-thread-scoped, same as JWT today); nothing to leak on pod restart because there was never anything stored | None identified |
| New in-memory `PerRequestKeyStore` (original design) | N/A | Duplicates `ActiveRunRegistry`'s bookkeeping; introduces a second identity for "is this run already running" that can drift out of sync with the registry |

### Decision 3: SSE heartbeat strategy

DIAL Core `idleTimeout = 300000ms` (5 minutes). EF must send an SSE heartbeat at least every ~30s (10x margin) on the stream it returns from `EvalExecuteInternalController`.

EF already has `TestSuiteRunSseService` (`SseEmitter`-based, filterable by `runIds`/`testSuiteIds`/`statuses`, with `notifyStatusUpdate`/`notifyProgress` called from `TestSuiteEvaluationJob`/`PostgresResultBatchWriter`, and a scheduled heartbeat sweep) backing the existing `GET /api/v1/test-suite-runs/status-stream` endpoint. The internal endpoint's stream reuses the same emitter/notification plumbing (so progress/status events naturally flow onto it with no new wiring in the job/writer classes) but needs a **faster, configurable heartbeat** than the browser-facing stream's default (300000ms is far too slow for DIAL Core's timeout): `dial-app-proxy.heartbeat-interval-ms` (default `30000`) drives a heartbeat specific to emitters created for this internal endpoint. Heartbeat format: `data: {}\n\n` — minimal, no content parsing required.

### Decision 4: `dial-app-proxy.enabled` feature flag

All new components are conditionally wired via `@ConditionalOnProperty(name = "dial-app-proxy.enabled", havingValue = "true")`:
- `DialRouteTriggerClient` bean
- `EvalExecuteInternalController` bean

When `false` (default): existing JWT path is unchanged. `TokenPropagationHelper` + `AuthorizationTokenHolder` are used exactly as before — no DIAL Route trigger is attempted.

`DialAppProperties` itself is unconditional (so it can validate the flag combination at startup regardless of the flag's own value) but is cheap and inert when `enabled=false`.

### Decision 5: PRK validation via the existing DIAL API-Key auth chain

The original design planned a bespoke PRK-verification step (`dial-app-proxy.verify-per-request-key`, calling `GET /v1/user/info` directly) plus a Spring Security `permitAll` carve-out for `/internal/**`, with network isolation as the stated primary defense.

Instead, `/api/internal/**` is added to the **existing** authenticated matcher set (same as `/api/v1/**`), so the request is authenticated by the already-shipped `ApiKeyAuthenticationFilter`/`CoreApiKeyIntrospector` pair before it ever reaches `EvalExecuteInternalController` — which already calls `GET /v1/user/info`, already caches successes, and already resolves roles via the configured role-mapping properties. There is no separate "PRK validation" step to implement or a flag to gate it: an unauthenticated or invalid PRK is rejected by the filter chain with the same `401` any invalid API key gets today.

This makes `config.rest.security.api-key.enabled=true` a **hard prerequisite** for `dial-app-proxy.enabled=true`. `DialAppProperties` fails fast at startup (`@PostConstruct`) if `enabled=true` but API-Key auth is not enabled, mirroring `ApiKeyProperties`'s own fail-fast validation style.

Network isolation (Kubernetes NetworkPolicy / internal service, keeping `/api/internal/**` off public ingress) remains a **recommended** defense-in-depth measure, but authentication no longer depends on it.

| Option | Pros | Cons |
|--------|------|------|
| **Reuse `ApiKeyAuthenticationFilter`/`CoreApiKeyIntrospector`** (chosen) | Zero new auth code; same caching, role-mapping, and failure semantics already relied on elsewhere; one fewer security-sensitive code path to audit | Requires `config.rest.security.api-key.enabled=true` as a precondition (documented, fail-fast) |
| Bespoke `DialUserInfoClient` + `permitAll` bypass (original design) | N/A | Duplicates `CoreApiKeyIntrospector`; a `permitAll` path is a larger security surface to review than reusing the existing authenticated chain |

### Decision 6: File auto-sharing for evaluated deployments

When EF (running with PRK1) constructs a test case request that includes file references from the EF bucket and sends it to an evaluated deployment via DIAL Core, DIAL Core:
1. Checks that EF (PRK1) has access to referenced files — granted via EF's **registered bucket access** in DIAL Core config (deployment-level "directly accessible to the Application")
2. Generates PRK2 for the evaluated deployment
3. Adds referenced files to PRK2's accessible file list (auto-sharing)
4. Evaluated deployment (PRK2) can now fetch those files from DIAL Core file API

**Requirement**: EF must be registered in DIAL Core with its file bucket configured as accessible. File references in test case requests must use standard DIAL file URL format (`files/{bucket}/{path}`) so DIAL Core's attachment scanner can extract and auto-share them.

EF's `DialFileClient` (using the service API key) continues to handle EF-internal file CRUD operations. Only deployment-bound requests go through the PRK path (unchanged by this design's simplification — this is purely DIAL Core-side behavior once EF is registered).

## Risks / Trade-offs

| Risk | Mitigation |
|------|-----------|
| DIAL Core adds max-duration TTL to PRKs in future | Monitor DIAL Core changelog; heartbeat signals active use; engage DIAL team to confirm long-running connection support |
| Connection drop (DIAL Core -> EF) mid-eval | EF detects `IOException` on SSE write, tears the run down via `ActiveRunRegistry.cancel(runId)` and marks it FAILED with a guarded `updateToFailed` (existing cancellation pattern, unchanged) |
| Pod restart mid-eval | Run fails — same failure mode as today's JWT expiry. DB run status preserved; operator can cancel/restart. (No store to lose, since none exists.) |
| N concurrent runs = N open SSE connections | Java virtual threads handle this; SSE connections are I/O-bound and cheap |
| `/api/internal/**` reachable without network isolation | Authentication is enforced by the existing DIAL API-Key chain regardless (not a `permitAll` path); network isolation is an additional, recommended layer, not the only one |
| DIAL Core idle timeout fires (300s) | 30s heartbeat provides 10x margin. If heartbeat interval is misconfigured, connection drops (recoverable via run retry) |
| JWT consumed at trigger time might be near expiry | JWT only needs to be valid for a single HTTP call (DIAL Core validation). The typical case: user just triggered the run -> JWT is fresh |
| `dial-app-proxy.enabled=true` without API-Key auth enabled | `DialAppProperties` fails fast at startup rather than silently exposing an unauthenticated-feeling endpoint |

## Migration Plan

1. **Deploy** with `dial-app-proxy.enabled=false` (default). No behavior change in existing environments.
2. **Ensure `config.rest.security.api-key.enabled=true`** in the target environment (hard prerequisite, enforced by fail-fast validation).
3. **Register EF** as a DIAL deployment named `EF` with an Application Route in DIAL Core config (see `docs/configuration.md`). Configure EF bucket access on the deployment.
4. **Enable** `dial-app-proxy.enabled=true` in a staging/dev environment. Verify eval runs complete without JWT expiry.
5. **Verify** file auto-sharing and SSE heartbeat behavior.
6. **Rollout** to production environments one by one.
7. **Legacy path** (`dial-app-proxy.enabled=false`) remains available indefinitely as rollback.

## Open Questions

1. **DIAL Core max request duration**: Does DIAL Core have a configurable max duration per deployment (distinct from idle timeout)? A hard cap would break long evals regardless of heartbeats. Needs confirmation from DIAL Core team before production deployment.
2. **EF bucket registration in DIAL Core**: The exact format of configuring EF's bucket access on the deployment record. The DIAL team needs to confirm the config field name and format for granting deployment-level file bucket access.
3. **Route URL collision**: The path `/v1/deployments/EF/route/api/internal/runs/{runId}/execute` must not conflict with any global DIAL Core routes or registered Core controller patterns. Verify with DIAL Core route resolution order.
