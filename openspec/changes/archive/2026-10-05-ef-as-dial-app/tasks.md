## 2. DIAL Route Trigger Client

- [x] 2.1 Create `DialRouteTriggerClient` `@Component` (`@ConditionalOnProperty(name = "dial-app-proxy.enabled", havingValue = "true")`, `@LogExecution`) in `client.dialcore` with `triggerEvalRun(UUID runId, CallerCredential jwtCredential)` — calls `POST {dial.url}/v1/deployments/{deploymentName}/route/api/internal/runs/{runId}/execute` with the credential's own `headerName()/headerValue()` (i.e. `Authorization: Bearer <jwt>`), consumes the SSE response stream until EOF/close, runs on a virtual thread
- [x] 2.2 Configure a dedicated `RestClient` for `DialRouteTriggerClient` with a long read timeout (`dial-app-proxy.trigger-read-timeout-ms`) to accommodate long-running eval connections; do NOT share with `dialCoreTryOutRestClient` or `dialCoreRestClient`
- [x] 2.3 `DialRouteTriggerClient.triggerEvalRun(...)` reads the SSE stream in a loop until EOF/stream close, logs the runId when the stream terminates; catches `IOException` on stream read and logs at WARN (normal on connection close or eval cancellation) — it does not need to parse event content (progress/heartbeat events on this leg are purely informational and can be discarded)

## 3. Internal Eval Execute Endpoint and SSE Streaming

- [x] 3.1 Create `EvalExecuteInternalController` `@RestController` (`@ConditionalOnProperty(name = "dial-app-proxy.enabled", havingValue = "true")`, `@LogExecution`) in `web.controller` with `POST /api/internal/runs/{runId}/execute` (no request body). Behind the **existing** Spring Security chain — no special permitAll handling. Flow: load the run (404 if not found); reject with 409 if a run handle is already active for this `runId` (see 3.2); capture `AuthorizationTokenHolder.getCredential()` (already the `API_KEY`-kind PRK, populated by the existing `AuthorizationHeaderInterceptor`); call `testSuiteEvaluationJob.dispatch(runId, credential, false)`; return `ResponseEntity<SseEmitter>` (`Content-Type: text/event-stream`)
- [x] 3.2 Add `ActiveRunRegistry.registerIfAbsent(UUID runId)` (atomic `ConcurrentHashMap.putIfAbsent`-based) returning `Optional<RunHandle>` (empty when a handle is already registered); change `TestSuiteEvaluationJob.dispatch(...)`'s internal registration to use it, and have `dispatch(...)` signal "already active" (e.g. a dedicated unchecked exception) so `EvalExecuteInternalController` can map it to HTTP 409. This closes the same race for the existing public path too (defensive, no observable behavior change there since it never double-dispatches today).
- [x] 3.3 Reuse `TestSuiteRunSseService`'s existing emitter/notification plumbing (the same `SseEmitter` infra backing `GET /api/v1/test-suite-runs/status-stream`) for progress/status events on this stream, but add a configurable heartbeat specific to emitters created for the internal endpoint, driven by `DialAppProperties.heartbeatIntervalMs` (default 30000ms) instead of the browser-facing stream's slower default — e.g. an overload of `TestSuiteRunSseService.createEmitter(...)` or a small sibling method that accepts a heartbeat interval, so DIAL Core's 300s idle timeout always has a 10x margin
- [x] 3.4 On eval terminal state (completed/failed/cancelled, as already signaled via the existing `notifyStatusUpdate` call from `TestSuiteEvaluationJob`), the emitter completes/closes normally (existing `SseEmitter` completion semantics) — no new "final event" payload format is required beyond what `TestSuiteRunSseService` already emits
- [x] 3.5 On `IOException` from the emitter (client/DIAL Core disconnected), cancel the eval via `ActiveRunRegistry.cancel(runId)` (existing cancellation pattern — mirrors `TestSuiteRunService.cancelRun`'s effect, minus the synchronous CANCELLING/CANCELLED status write which the job's own guarded terminal write already handles)

## 4. Security

No `NoSecurityConfiguration` change needed (that configuration already `permitAll`s everything when `mode=none`).
