## Context

EF currently captures the user's JWT at run-creation time and propagates it via `AuthorizationTokenHolder` (ThreadLocal) + `TokenPropagationHelper` to async worker threads. `DialCoreDeploymentInvoker` reads the JWT from `AuthorizationTokenHolder` and includes it in the `Authorization` header for every deployment invocation. During long eval runs (minutes to hours), this JWT expires, causing 401 failures mid-run.

Additionally, when test case requests include DIAL file references from the EF bucket (e.g., multi-modal inputs), evaluated deployments receive the file URL but cannot access it — DIAL Core has no mechanism to verify EF's authorization and propagate file access to the downstream deployment's per-request key.

DIAL Core's **per-request key (PRK)** mechanism solves both issues: a PRK is generated by DIAL Core when it calls an application, lives for the lifetime of that HTTP connection, carries user identity and cost-attribution data through the full call tree, and enables DIAL Core's auto-sharing mechanism to propagate EF's bucket file access to evaluated deployments.

**Current flow:**
```
EF UI → EF BE (POST /api/v1/runs)
  → captures JWT (ThreadLocal)
  → spawns CompletableFuture with TokenPropagationHelper
  → DialCoreDeploymentInvoker uses JWT from ThreadLocal
  [JWT expires after N minutes → 401 on deployment call]
```

**Target flow (DIAL App mode):**
```
EF UI → EF BE (POST /api/v1/runs)
  → creates run record, captures JWT once
  → spawns virtual thread: POST /v1/deployments/ef-eval/route/eval/runs/{runId}/execute
       Authorization: <user JWT>  ← used exactly once
           ↓
       DIAL Core: validates JWT, generates PRK, proxies to EF internal endpoint
           ↓
       EF internal: POST /internal/eval/runs/{runId}/execute
                    Api-Key: <per-request-key>  ← no expiry while connection open
  → eval execution uses PRK for all DIAL Core calls
  → SSE heartbeat keeps connection alive → PRK stays valid
  [connection open = PRK valid; eval can run for hours]
```

## Goals / Non-Goals

**Goals:**
- Solve JWT expiry for eval runs of arbitrary duration without token storage or refresh
- Enable DIAL Core's PRK auto-sharing chain for EF bucket files passed as links to evaluated deployments
- Preserve user identity and cost attribution through the full execution call tree
- Zero breaking changes — gradual rollout via `ef.dial-app.enabled` feature flag
- Dual-mode operation: existing JWT path remains fully functional when flag is off

**Non-Goals:**
- Replacing EF's REST API with a DIAL chat completions interface
- Storing PRKs in Redis or any persistent store (in-memory only)
- Changing any public API contract (`/api/v1/...` unchanged)
- Output file auto-sharing to user's DIAL bucket (deferred to v2)
- MCP tool integration for LLM-driven eval triggering (separate future concern)
- MetricEvaluationWorker DIAL integration (no DIAL calls today; PRK store is available for future use without additional changes)

## Decisions

### Decision 1: DIAL Application Routes as trigger mechanism

**Alternatives considered:**

| Option | PRK generation | Semantics | SSE | Request format |
|--------|---------------|-----------|-----|----------------|
| Chat Completions | ✅ Confirmed | ❌ LLM API repurposed | ✅ | ❌ Forced `messages[]` + `choices/delta` |
| **DIAL App Routes** | ✅ Confirmed | ✅ Native REST | ✅ HTTP proxy | ✅ EF's own format |
| MCP Endpoints | ❌ Forwards caller PRK | ❌ LLM tool-call pattern | ❌ Synchronous | ❌ |

DIAL Application Routes confirmed to generate PRKs in `route_authorization.md`:
> *"We want to pass per request API key to route as we do models/applications on chat completion request."*

Routes are chosen because they offer the same PRK guarantees as chat completions with no protocol overhead. EF's internal endpoint receives a plain HTTP POST with `Api-Key: <prk>` and can respond with any SSE format. No wrapping/unwrapping of OpenAI message formats required.

**DIAL Core route config (to be documented in `docs/configuration.md`):**
```json
{
  "applications": {
    "ef-eval": {
      "displayName": "Evaluation Framework",
      "routes": {
        "eval_run_execute": {
          "paths": ["/eval/runs/[^/]+/execute$"],
          "methods": ["POST"],
          "rewritePath": true,
          "upstreams": [{"endpoint": "http://ef-backend:8080/internal"}],
          "attachmentPaths": {
            "requestBody": []
          }
        }
      }
    }
  }
}
```

Public route URL: `POST /v1/deployments/ef-eval/route/eval/runs/{runId}/execute`
EF receives at: `POST http://ef-backend:8080/internal/eval/runs/{runId}/execute`
DIAL Core injects: `Api-Key: <per-request-key>`, `X-DIAL-APPLICATION-ID: ef-eval`

### Decision 2: In-memory `ConcurrentHashMap<UUID, String>` for PRK store

| Option | Pros | Cons |
|--------|------|------|
| In-memory map | Simple, no deps, auto-cleaned on stream close | Lost on pod restart |
| Redis | Survives pod restarts | Infra dependency, adds latency, PRKs are short-lived anyway |
| DB (encrypted) | Durable | Write latency, DIAL Core invalidates the key on connection drop anyway |

Chosen: **in-memory**. If the pod restarts mid-eval, the run fails — identical behavior to today's JWT expiry failure. The PRK is ephemeral by design (DIAL Core invalidates it when the connection closes), so durability beyond the connection lifetime provides no value.

`PerRequestKeyStore` is a `@Component` with a `ConcurrentHashMap<UUID, String>`. Entry is added when the internal endpoint is called; removed when eval completes, SSE stream closes, or eval is cancelled.

### Decision 3: SSE heartbeat interval

DIAL Core `idleTimeout = 300000ms` (5 minutes). EF sends a heartbeat SSE comment every **30 seconds** (configurable via `ef.dial-app.heartbeat-interval-ms`). This provides 10× margin against the idle timeout. Heartbeat format: `data: {}\n\n` — minimal, no content parsing required.

The same SSE stream carries progress events between heartbeats (no extra connection needed for progress reporting — though EF FE polls the DB for status, so progress events via SSE are informational only and can be safely discarded by the trigger thread).

### Decision 4: `ef.dial-app.enabled` feature flag

All new components are conditionally wired via `@ConditionalOnProperty(name = "ef.dial-app.enabled", havingValue = "true")`:
- `DialRouteTriggerClient` bean
- `EvalExecuteInternalController` bean
- `PerRequestKeyStore` bean
- PRK path in `DialCoreDeploymentInvoker` and `AuthorResolver`

When `false` (default): existing JWT path is unchanged. `TokenPropagationHelper` + `AuthorizationTokenHolder` are used as before.

### Decision 5: PRK validation at internal endpoint (default: verify)

The `/internal/eval/runs/{runId}/execute` endpoint must not be exploitable by arbitrary clients. Two layers of protection:
1. **Network isolation**: the endpoint is only reachable through DIAL Core proxy (Kubernetes NetworkPolicy, internal service, or equivalent). Not exposed on public ingress.
2. **PRK verification**: configurable via `ef.dial-app.verify-per-request-key=true` (default). EF calls `GET /v1/user/info` on DIAL Core with the incoming `Api-Key` value. If DIAL Core returns 200, the key is a valid PRK. If 401, reject with 401.

When `verify-per-request-key=false`: trust the network (appropriate for environments with strict network segmentation). Spring Security permits all on `/internal/**` (no JWT filter chain applied to these paths).

### Decision 6: AuthorResolver in DIAL App mode

`AuthorResolver` has two modes:
- **JWT mode** (existing): extract user claim from JWT via configured `security.jwt.user-claim`
- **PRK mode** (new): `GET /v1/user/info` with PRK → parse `userClaims.<user-claim>` from response

Mode is selected based on: (a) `ef.dial-app.enabled=true` AND (b) a PRK exists in `PerRequestKeyStore` for the current runId. Falls back to JWT mode if PRK unavailable. Falls back to `"anonymous"` if both fail (security mode `none`).

### Decision 7: DialCoreDeploymentInvoker — PRK priority

`DialCoreDeploymentInvoker` currently reads from `AuthorizationTokenHolder.getToken()` for the `Authorization` header. In DIAL App mode, the invoker checks `PerRequestKeyStore.get(runId)` first:
- PRK present → `Api-Key: <prk>` header (no `Authorization` header)
- PRK absent → fall back to `AuthorizationTokenHolder.getToken()` → `Authorization: <jwt>`

`runId` must flow through to the invoker. The existing `EvaluationContext` already carries `runId` and is passed to `EvaluationWorker`, which calls `deploymentInvoker`. The invoker needs access to `PerRequestKeyStore` — inject it conditionally (null when DIAL App mode is off, invocation is PRK-absent path).

### Decision 8: File auto-sharing for evaluated deployments

When EF (running with PRK1) constructs a test case request that includes file references from the EF bucket and sends it to an evaluated deployment via DIAL Core, DIAL Core:
1. Checks that EF (PRK1) has access to referenced files — granted via EF's **registered bucket access** in DIAL Core config (deployment-level "directly accessible to the Application")
2. Generates PRK2 for the evaluated deployment
3. Adds referenced files to PRK2's accessible file list (auto-sharing)
4. Evaluated deployment (PRK2) can now fetch those files from DIAL Core file API

**Requirement**: EF must be registered in DIAL Core with its file bucket configured as accessible. File references in test case requests must use standard DIAL file URL format (`files/{bucket}/{path}`) so DIAL Core's attachment scanner can extract and auto-share them.

EF's `DialFileClient` (using the service API key) continues to handle EF-internal file CRUD operations. Only deployment-bound requests go through the PRK path.

## Risks / Trade-offs

| Risk | Mitigation |
|------|-----------|
| DIAL Core adds max-duration TTL to PRKs in future | Monitor DIAL Core changelog; heartbeat signals active use; engage DIAL team to confirm long-running connection support |
| Connection drop (DIAL Core → EF) mid-eval | EF detects `IOException` on SSE write, cancels eval via existing `AtomicBoolean` cancellation signal, removes PRK from store, marks run FAILED |
| Pod restart loses PRK store | Run fails — same failure mode as today's JWT expiry. DB run status preserved; operator can cancel/restart |
| N concurrent runs = N open SSE connections | Java 21 virtual threads handle this; SSE connections are I/O-bound and cheap |
| Internal endpoint exposed accidentally | Kubernetes NetworkPolicy + Spring Security `permitAll` on `/internal/**` (no JWT filter). Network-level isolation is primary; PRK verification is secondary |
| DIAL Core idle timeout fires (300s) | 30s heartbeat provides 10× margin. If heartbeat interval is misconfigured, connection drops (recoverable via run retry) |
| JWT consumed at trigger time might be near expiry | JWT only needs to be valid for a single HTTP call (DIAL Core validation). The typical case: user just triggered the run → JWT is fresh |

## Migration Plan

1. **Deploy** with `ef.dial-app.enabled=false` (default). No behavior change in existing environments.
2. **Register EF** as a DIAL deployment with Application Route in DIAL Core config (see `docs/configuration.md`). Configure EF bucket access on the deployment.
3. **Enable** `ef.dial-app.enabled=true` in a staging/dev environment. Verify eval runs complete without JWT expiry.
4. **Verify** PRK validation, file auto-sharing, and SSE heartbeat behavior.
5. **Rollout** to production environments one by one.
6. **Legacy path** (`ef.dial-app.enabled=false`) remains available indefinitely as rollback.

## Open Questions

1. **DIAL Core max request duration**: Does DIAL Core have a configurable max duration per deployment (distinct from idle timeout)? A hard cap would break long evals regardless of heartbeats. Needs confirmation from DIAL Core team before production deployment.
2. **EF bucket registration in DIAL Core**: The exact format of configuring EF's bucket access on the deployment record. The DIAL team needs to confirm the config field name and format for granting deployment-level file bucket access.
3. **Route URL collision**: The path `/v1/deployments/ef-eval/route/eval/runs/...` must not conflict with any global DIAL Core routes or registered Core controller patterns. Verify with DIAL Core route resolution order.
