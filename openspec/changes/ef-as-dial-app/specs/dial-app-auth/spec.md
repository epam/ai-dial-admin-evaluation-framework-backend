# DIAL App Auth

## Purpose

Defines EF's integration as a DIAL Application via DIAL Application Routes. Covers the per-request key (PRK) lifecycle, eval execution trigger, SSE keepalive, PRK-based deployment invocation, user identity resolution, and file auto-sharing to evaluated deployments.

Status: **Planned**

## Key Terms

- **per-request key (PRK)**: Ephemeral key generated by DIAL Core per HTTP request to an application or route. Lives for the duration of the request. Carries user identity, trace-id, and cost attribution. Grants access to DIAL models, applications, and auto-shared files.
- **PerRequestKeyStore**: In-memory registry mapping `runId (UUID) → PRK (String)`. Populated when DIAL Core triggers EF's internal eval endpoint; cleared on eval completion or connection close.
- **DialRouteTriggerClient**: EF component that fires eval execution by calling DIAL Core's Application Route, maintaining the SSE connection open to keep the PRK alive.
- **EvalExecuteInternalController**: Internal Spring controller receiving DIAL Core's PRK-injected request; starts async eval and streams SSE back.
- **DIAL App mode**: Operational mode activated by `ef.dial-app.enabled=true`. When active, PRK replaces JWT for deployment invocations and user identity resolution.

## Requirements

### Requirement: Feature flag controls DIAL App mode activation
The system SHALL support a configuration property `ef.dial-app.enabled` (boolean, default `false`) that controls whether the DIAL App integration is active. When `false`, all existing JWT-based flows MUST remain unchanged. When `true`, DIAL App mode components are active. All DIAL App mode beans MUST be conditionally wired via `@ConditionalOnProperty(name = "ef.dial-app.enabled", havingValue = "true")`.

Status: **Planned**

#### Scenario: DIAL App mode disabled by default
- **WHEN** the application starts without `ef.dial-app.enabled` configured
- **THEN** JWT-based eval execution SHALL be used (existing `TokenPropagationHelper` path)
- **AND** no DIAL route trigger is attempted

#### Scenario: DIAL App mode enabled
- **WHEN** `ef.dial-app.enabled=true`
- **THEN** eval runs SHALL be triggered via `DialRouteTriggerClient` (DIAL Application Route)
- **AND** `PerRequestKeyStore`, `EvalExecuteInternalController`, and PRK-aware `DialCoreDeploymentInvoker` beans SHALL be active

### Requirement: Per-request key store
The system SHALL provide a `PerRequestKeyStore` component (`service.domain`) that maintains an in-memory `ConcurrentHashMap<UUID, String>` mapping `runId → PRK`. The store SHALL be thread-safe for concurrent reads and writes. The store SHALL remove the mapping when: (a) eval execution completes (success or failure), (b) the SSE stream closes, or (c) eval is cancelled.

Status: **Planned**

#### Scenario: PRK stored on eval trigger
- **WHEN** `EvalExecuteInternalController` receives a valid request for `runId`
- **THEN** it SHALL call `PerRequestKeyStore.put(runId, prk)` before starting eval execution

#### Scenario: PRK removed on completion
- **WHEN** eval execution completes (any terminal state: completed, failed, cancelled)
- **THEN** `PerRequestKeyStore.remove(runId)` SHALL be called

#### Scenario: PRK absent when store queried with unknown runId
- **WHEN** `PerRequestKeyStore.get(runId)` is called for a runId not in the store
- **THEN** it SHALL return `null` (not throw)

### Requirement: DIAL Route trigger client
The system SHALL provide a `DialRouteTriggerClient` component (`client.dialcore`) that triggers eval execution via the DIAL Application Route. The client SHALL: (a) call `POST /v1/deployments/ef-eval/route/eval/runs/{runId}/execute` on DIAL Core using the user's JWT in the `Authorization` header; (b) maintain the SSE connection open by consuming the SSE stream from DIAL Core until the stream terminates; (c) run on a virtual thread (non-blocking for the REST response).

Status: **Planned**

#### Scenario: Trigger call dispatched asynchronously after run creation
- **WHEN** a new eval run record is created with DIAL App mode enabled
- **THEN** `DialRouteTriggerClient.triggerEvalRun(runId, jwt)` SHALL be called on a virtual thread
- **AND** the run-creation REST response SHALL be returned immediately (before trigger completes)

#### Scenario: Trigger call uses user JWT exactly once
- **WHEN** `DialRouteTriggerClient.triggerEvalRun(runId, jwt)` is called
- **THEN** the `jwt` value SHALL appear only in the `Authorization` header of the outbound DIAL Core call
- **AND** it SHALL NOT be stored, logged, or propagated further

#### Scenario: Trigger connection kept open via SSE consumption
- **WHEN** DIAL Core proxies the SSE stream from EF's internal endpoint back to `DialRouteTriggerClient`
- **THEN** `DialRouteTriggerClient` SHALL consume (read and discard) the SSE stream until `[DONE]` or stream close
- **AND** the HTTP connection SHALL remain open for the duration of eval execution

#### Scenario: Connection drop during eval
- **WHEN** the SSE stream from DIAL Core is interrupted (network error, DIAL Core restart)
- **THEN** `DialRouteTriggerClient` SHALL log a warning with the runId
- **AND** the eval execution in `EvalExecuteInternalController` SHALL detect the write failure and cancel the run

### Requirement: Internal eval execute endpoint
The system SHALL expose `POST /internal/eval/runs/{runId}/execute` (Spring `@RestController`) accessible only via the DIAL Core Application Route proxy. Spring Security SHALL permit all requests to `/internal/**` without JWT validation. The endpoint SHALL: extract the PRK from the `Api-Key` header; optionally validate it (see PRK validation requirement); store it in `PerRequestKeyStore`; start async eval execution; and return a streaming SSE response (`text/event-stream`).

Status: **Planned**

#### Scenario: Endpoint triggers eval execution
- **WHEN** DIAL Core POSTs to `/internal/eval/runs/{runId}/execute` with `Api-Key: <prk>`
- **THEN** the endpoint SHALL store `runId → prk` in `PerRequestKeyStore`
- **AND** start async eval execution for the given `runId`
- **AND** return HTTP 200 with `Content-Type: text/event-stream`

#### Scenario: Run not found
- **WHEN** the `runId` path parameter does not correspond to an existing run
- **THEN** the endpoint SHALL return HTTP 404 and NOT store anything in `PerRequestKeyStore`

#### Scenario: Api-Key header missing
- **WHEN** the request arrives without an `Api-Key` header
- **THEN** the endpoint SHALL return HTTP 401

#### Scenario: Concurrent trigger for same runId rejected
- **WHEN** `EvalExecuteInternalController` receives a trigger for a `runId` that already has a PRK in `PerRequestKeyStore`
- **THEN** it SHALL return HTTP 409 (Conflict)

### Requirement: SSE heartbeat to maintain PRK liveness
The SSE stream returned by `EvalExecuteInternalController` SHALL emit a heartbeat event at a configurable interval (`ef.dial-app.heartbeat-interval-ms`, default `30000`) to prevent DIAL Core's idle connection timeout from firing. The heartbeat format SHALL be `data: {}\n\n`. Progress events (test case count, phase changes) MAY also be emitted on the same stream.

Status: **Planned**

#### Scenario: Heartbeat emitted within idle timeout window
- **WHEN** no eval progress event has been emitted within `heartbeat-interval-ms` milliseconds
- **THEN** a heartbeat SSE event SHALL be emitted on the stream

#### Scenario: Stream terminated on eval completion
- **WHEN** eval execution reaches a terminal state (completed, failed, cancelled)
- **THEN** the SSE stream SHALL emit a final event and then `data: [DONE]\n\n` before closing

### Requirement: PRK-based deployment invocation
When `ef.dial-app.enabled=true` and a PRK is present in `PerRequestKeyStore` for the current `runId`, `DialCoreDeploymentInvoker` SHALL use the PRK as the `Api-Key` header value for all outbound DIAL Core calls (deployment invocations). The `Authorization` header SHALL NOT be set in this case. When no PRK is present (legacy mode or PRK absent), the invoker SHALL fall back to `AuthorizationTokenHolder.getToken()` for the `Authorization` header (unchanged behavior).

Status: **Planned**

#### Scenario: Deployment invocation uses PRK in DIAL App mode
- **WHEN** `DialCoreDeploymentInvoker.invokeWithStreaming(...)` is called during an eval run with a PRK in the store for that `runId`
- **THEN** the outbound HTTP request SHALL include `Api-Key: <prk>` header
- **AND** SHALL NOT include an `Authorization` header

#### Scenario: Deployment invocation falls back to JWT when no PRK
- **WHEN** `DialCoreDeploymentInvoker.invokeWithStreaming(...)` is called and `PerRequestKeyStore.get(runId)` returns `null`
- **THEN** the outbound HTTP request SHALL include `Authorization: <jwt>` header (existing behavior)

### Requirement: PRK validation at internal endpoint
When `ef.dial-app.verify-per-request-key=true` (default), `EvalExecuteInternalController` SHALL verify the incoming `Api-Key` value by calling `GET /v1/user/info` on DIAL Core with that key. If DIAL Core returns HTTP 200, the key is valid and processing continues. If DIAL Core returns any non-2xx status, the endpoint SHALL return HTTP 401.

Status: **Planned**

#### Scenario: Valid PRK accepted
- **WHEN** `ef.dial-app.verify-per-request-key=true`
- **AND** DIAL Core returns HTTP 200 for `GET /v1/user/info` with the incoming key
- **THEN** the endpoint SHALL proceed with eval execution

#### Scenario: Invalid key rejected
- **WHEN** `ef.dial-app.verify-per-request-key=true`
- **AND** DIAL Core returns non-2xx for `GET /v1/user/info` with the incoming key
- **THEN** the endpoint SHALL return HTTP 401

#### Scenario: PRK verification disabled
- **WHEN** `ef.dial-app.verify-per-request-key=false`
- **THEN** the endpoint SHALL skip the `/v1/user/info` call and trust the incoming key

### Requirement: Author resolution via DIAL user info
When `ef.dial-app.enabled=true` and a PRK is available for the current run, `AuthorResolver` SHALL resolve user identity by calling `GET /v1/user/info` on DIAL Core with the PRK in the `Api-Key` header and extracting the configured claim (`security.jwt.user-claim`) from the `userClaims` field of the response. When no PRK is available, the existing JWT-based claim extraction SHALL be used. In both cases, `"anonymous"` SHALL be returned if the identity cannot be resolved (security mode `none` or missing claim).

Status: **Planned**

#### Scenario: Author resolved via PRK in DIAL App mode
- **WHEN** `ef.dial-app.enabled=true`
- **AND** a PRK is in `PerRequestKeyStore` for the current run
- **THEN** `AuthorResolver` SHALL call DIAL Core `/v1/user/info` with the PRK
- **AND** return the value of `userClaims.<user-claim>` from the response

#### Scenario: Author falls back to JWT when PRK unavailable
- **WHEN** `ef.dial-app.enabled=true` but no PRK is available for the current run
- **THEN** `AuthorResolver` SHALL fall back to JWT claim extraction (existing behavior)

#### Scenario: Author is anonymous when identity unavailable
- **WHEN** `/v1/user/info` returns no matching claim or security mode is `none`
- **THEN** `AuthorResolver` SHALL return `"anonymous"`

### Requirement: DIAL Core Application Route registration documentation
The system's `docs/configuration.md` SHALL document the required DIAL Core deployment configuration for EF: the Application Route definition (path pattern, upstream, `rewritePath`), the EF deployment name (`ef-eval`), and the bucket access configuration granting EF's deployment access to the EF file bucket for DIAL Core's file auto-sharing chain.

Status: **Planned**

#### Scenario: Documentation covers DIAL Core config
- **WHEN** an operator reads `docs/configuration.md`
- **THEN** they SHALL find the complete DIAL Core Application Route config block
- **AND** the EF bucket access registration instruction
- **AND** a note that the `/internal/eval/runs/*/execute` endpoint must not be exposed on public ingress

### Requirement: File auto-sharing to evaluated deployments
When EF App (running with PRK1) constructs a test case sub-request to an evaluated deployment that contains DIAL file references (format: `files/{bucket}/{path}`), DIAL Core SHALL automatically check EF's registered bucket access, and if granted, propagate read access to those files in the evaluated deployment's PRK2. EF SHALL use standard DIAL file URL format in test case request bodies to ensure DIAL Core's attachment scanner processes them.

Status: **Planned**

#### Scenario: EF bucket files accessible to evaluated deployment
- **WHEN** EF (PRK1) sends a sub-request to an evaluated deployment containing `files/ef-bucket/suites/{suiteId}/input.csv` in the request body
- **AND** EF's DIAL Core deployment registration grants bucket access to `ef-bucket`
- **THEN** DIAL Core SHALL generate PRK2 for the evaluated deployment
- **AND** PRK2 SHALL have read access to `files/ef-bucket/suites/{suiteId}/input.csv`
- **AND** the evaluated deployment SHALL be able to fetch the file via DIAL Core file API

#### Scenario: File access denied if EF lacks bucket registration
- **WHEN** EF's DIAL Core deployment is NOT configured with bucket access
- **THEN** DIAL Core SHALL reject the sub-request with HTTP 403 (file not accessible)
