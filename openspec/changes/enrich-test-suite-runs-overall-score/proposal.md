## Why

GH #197 moves the run listing onto the `test_suite_runs` query entity, which must show each run's run-level `overall` metric score. The entity resolves on `metaDsl`; the value lives in `metric_score_result` on the **analytics** datasource, with no joinable path — a cross-datasource subquery fails at the database. Client-side resolution is no better: there is no batch metric-score read API, and the `computation_id eq "latest"` sentinel only works for a query pinning a single run, so the FE would need one request per row.

So the value must be attached after the entity's SQL has run, and the pipeline has no post-execution hook — `StructuredQueryEntityResolver.rewrite` runs before translation. This change adds one as a general seam rather than a one-off branch, because the same problem recurs immediately for total run cost (dial-adas, today a separate `POST /api/v1/costs/test-suite-runs` call). That cost extender is not part of this change; only the seam must accommodate it.

## What Changes

- **Post-execution extension seam.** New `QueryResultPageExtender` SPI (`query.service.repository`) with one method, `extend(StructuredQuery, QueryResultPage)`; each implementation decides whether it applies and returns the page unchanged when it does not. `JooqStructuredQueryExecutorExtender` — the `@Primary` pass-through wrapper already scaffolded on this branch — folds the page through `List<QueryResultPageExtender>` in bean order, wrapping **each** extender in its own try/catch so a query that succeeded never fails because a derived value could not be added. Implementations are additive, non-overwriting, order-preserving and never mutate jOOQ's row maps in place. See design D1, D3.
- **A result page's key set is open.** A row's keys are the projection's keys plus zero or more extension-derived keys — never a closed set equal to the projection or the published schema. Derived keys are merged after SQL and after paging, so they stay unusable in `filter`/`sort`/`group_by`/`select` (still 400 as unknown fields) and unpublished in schema discovery, which continues to advertise exactly the queryable field set. Stated once at the mechanism, so the forthcoming cost extender needs no further spec amendment. See design D2.
- **First implementation: `OverallScoreTestSuiteRunsPageExtender`.** Attaches `overall_score_value` to each row of a non-aggregate `test_suite_runs` query, carrying that run's latest computation's run-level overall score. Two page-bounded analytics queries, never per-row fan-out: per-run latest computation for the whole page, then one `StructuredQuery` against `metric_score_results` filtered by run id, computation id and `metric_score_name`/`metric_name` = `overall`. Skipped, leaving the page untouched, on aggregate mode, a projection without `id`, a non-UUID `id`, a row that already carries the key, or a non-Postgres analytics vendor. See design D4, D5.
- **Batch latest-computation lookup.** New `EvalSummaryRepository.findLatestComputationIds(Collection<UUID>)` + Postgres impl resolving a page in one statement; a run with no eval summaries is absent from the map, never mapped to null. Exposed as `ComputationResolver.resolveLatest(Collection<UUID>)`, keeping that class the single authority for "latest" and the extender out of a foreign domain's repository. Shape and rejected alternative: design D6.
- **One system-wide same-millisecond tiebreak: `computed_at_ms DESC, computation_id ASC`.** Today three latest-computation lookups disagree — `PostgresEvalSummaryRepository.findLatestComputationId` has no tiebreak, while the snapshot repository lookup and the `metric_names` subquery both take the greatest id. The divergence is invisible until this change puts `overall_score_value` (eval-summary path) beside `metric_names` (snapshot path) in one row, where a tied run would show one computation's score next to another's metric catalog. All four lookups converge; behaviour changes only on same-millisecond ties. Direction, and the deliberate absence of an index change: design D7.

Non-goals: making derived keys queryable or published; the total-run-cost extender; a new REST endpoint; any change to `GET /api/v1/test-suite-runs` or to the `/queries/execute` request contract; DB migration, `generateJooq` or new configuration (the page is already bounded by `StructuredQueryBuilder.MAX_LIMIT` / `pagination.max-size` = 1000).

## Capabilities

### New Capabilities
- `query-result-page-extension`: the post-execution extension pass — the `QueryResultPageExtender` SPI and its contract, coordinator-owned failure isolation, how the `@Primary` wrapper applies registered extenders, and the **open key set** requirement (a row's keys are the projection's plus zero or more extension-derived keys, for every entity) that the specs below defer to rather than restate. Derived keys are neither queryable nor published.

### Modified Capabilities
- `test-suite-runs-query-entity`: "Entity field set" — the requirement that all fields resolve from meta in one statement and that the entity carries no field derived outside the database is narrowed to the entity's *queryable* field set; its scenario "Empty select projects the whole entity and nothing more" is amended to the open key set. New requirement for the derived `overall_score_value` key: value and latest-computation semantics, omission when absent, skip conditions, exclusion from the queryable set, degradation to an unextended page when analytics is unavailable. "Latest-computation metric names" breaks ties on the **smallest** `computation_id`, and its scenario "Same-millisecond computations resolve deterministically" flips from greater to smaller. "Enrichment cost is proportional to the runs visited" drops its `computation_id DESC` index-direction pin.
- `query-schema-discovery`: discovery publishes the queryable field set only, for every entity, so an extension-derived key legitimately has no schema entry. Scenario "test_suite_runs base schema matches what the executor accepts" — its "each returned row has exactly those keys" becomes the open key set. The published field list is unchanged.
- `metrics-storage`: the "Computation versioning model" latest-resolution scenario gains the system-wide tiebreak and batch resolution for a page of runs in one statement, with runs having no eval summaries absent from the result. Scenario "Metric-catalog lookups stay on run metric snapshots" flips its tiebreak from the greatest to the smallest `computation_id`.
- `metric-score-statistics`: "Metric-score results read exclusively via the unified Query API" gains a carve-out — the run-level `overall` value may additionally surface as a derived key on a `test_suite_runs` result page, read server-side through that same `metric_score_results` entity (no bespoke SQL, no new REST read surface).

## Impact

- **Code (new)**: `query.service.repository.{QueryResultPageExtender, OverallScoreTestSuiteRunsPageExtender}`.
- **Code (modified)**: `JooqStructuredQueryExecutorExtender` (applies the extender list instead of passing through, owns per-extender failure isolation, drops its duplicate `@LogExecution`); `{EvalSummaryRepository, PostgresEvalSummaryRepository}` (batch lookup; `computation_id ASC` tiebreak added to the untiebroken single-run `findLatestComputationId`); `ComputationResolver` (batch `resolveLatest`); `PostgresRunMetricSnapshotRepository.findLatestComputationId` and the `metric_names` subquery in `PostgresTestSuiteRunEntityResolver` (tiebreak `DESC` → `ASC`); `TestSuiteRunQueryFields` (the `overall_score_value` constant, documented as extension-only); `MetricScoreConstants` (the `metric_score_results` entity name, today duplicated as a literal in `PostgresMetricScoreResultEntityResolver` and `MetricScoreResultSchemaProvider`, both repointed, plus the two field-name constants — and a widened class javadoc, see design D8).
- **API**: additive only — one extra key on `test_suite_runs` result rows. No DTO or request-contract change. `StructuredQueryController` / `StructuredQueryResultDto` gain the OpenAPI description of the key, which is its only contract since it is in no schema.
- **DB / config**: none. No migration, no `generateJooq`, no new `@ConfigurationProperties`, so no `docs/database-schema.md` or `docs/configuration.md` change.
- **Perf/risk**: two extra page-bounded, index-served analytics queries per listing; a slow or failing analytics database degrades to an unextended page rather than a failed query. The tiebreak change alters resolution on the four `ComputationResolver` call paths (`EvalSummaryService`, `EvalSummaryExportService`, `MetricScoreLatestComputationDefaulter`, `RunComparisonService`) whenever the planner does not use the index — deterministic where it was not, but a real change, not a formalization. Result rows stop being a closed key set, which can surprise strict clients. Full list: design "Risks / Trade-offs".
- **Unaffected by design**: `eval-cli` / `evaluation-runner-core` (no DB, no extender beans); the three in-process DSL consumers `MetricScoreComputationExecutor`, `EvalSummaryRowScoreComputer`, `FilteredMetricScoreAggregator` (all query `eval_summaries`, which no extender claims); eval-summary CSV export/preview, which does not go through the query DSL at all.
- **Tests**: two existing tiebreak tests invert — `RunMetricSnapshotFunctionalTests.findLatestComputationIdBreaksTieByGreaterComputationId` (:197) and `TestSuiteRunStructuredQueryFunctionalTests.metricNamesTiebreaksByGreaterComputationId` (:312) — names and `@DisplayName`s included. Two exact-key-equality assertions move to containment of the queryable fields, since the open key set makes exact equality a hostage to every future extender: `TestSuiteRunStructuredQueryFunctionalTests.emptySelectProjectsExactlyTheEntityFields` (:149) and `QuerySchemaDiscoveryFunctionalTests.shouldMatchTestSuiteRunsSchemaToExecutor` (:291), the latter also needing its unfiltered `limit 10` query pinned to the run it creates (see design D10). New: unit tests for the wrapper, the extender and `resolveLatest`; functional coverage for the batch lookup, for extended rows end to end, and for the cross-path invariant that a tied run's `metric_names` and `overall_score_value` resolve to the same computation.
- **Docs**: new `docs/patterns/query-result-page-extension.md` + AGENTS.md Unique Patterns row; tiebreak updates to `docs/patterns/{computation-versioning,test-suite-runs-query-entity,query-dsl-entity-resolution}.md`; `openspec/specs/README.md` row for the new capability.
- **Rollout**: plain rolling restart; additive on the response, so an older FE ignoring the key keeps working. Rollback is removing the extender bean — the seam then folds an empty list.
