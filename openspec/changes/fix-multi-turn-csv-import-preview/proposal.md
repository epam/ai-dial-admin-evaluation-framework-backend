## Why

GitHub issue #120 — *"[Eval > Datasets] CSV re-import loses per-turn values and falsely flags multi-turn rows as duplicates"*. Exporting a dataset that contains a multi-turn test case and re-importing that same CSV (the default `importMode=OVERRIDE`) both (a) warns on the preview step that every legitimate turn row *"would cause import failure (409) — duplicate of earlier row with same name"*, and (b) destroys the case's per-turn values: it still reports "3 turns", but turn 1's value has been promoted to the group row and turns 2..N are gone.

Reproduced on branch `fix/120-multi-turn-import` with a throwaway functional test (export → import OVERRIDE ×2 into the same dataset): after import #1 the dataset schema is `[{name=prompt, required=false, type=STRING}]` — `perTurn` gone — and after import #2 the case is `data={prompt=first}`, `multiTurnData=[{}, {}]`. Both symptoms trace to CSV import treating a field's *scope* (`FieldDefinitionDto.perTurn`) as disposable, and to CSV preview having no notion of a multi-turn case at all.

## What Changes

### 1. Schema rebuild drops `perTurn` — the data loss

`CsvImportService.buildSchemaFromInferred` builds each `FieldDefinitionDto` with `name` + `type` + `required(false)` only, dropping `perTurn`. Its caller `persistSchema` rewrites the dataset's persisted `test_case_schema` from it on every OVERRIDE / empty-schema import, so **the default import mode silently resets every field's scope to shared**. `buildFinalSchema` (fixup re-validation) and `buildAutoDetectedSchema` (the preview's `autoDetectedSchema`, which a client may write back) share the same defect.

`buildValidationSchema` already patches scope back for the *running* import via `applyScopeFromDataset`, which is why import #1 stores turns correctly and only corrupts the schema; import #2 then partitions every column as shared, the values differ between turn rows → `sharedConflict` → `data` = turn 0's values, `multiTurnData` = `[{}, …]`, `valid=false`.

- Carry `perTurn` forward by field name from the dataset's current schema in **every** schema-building path (validation, persisted, final/fixup, auto-detected), via one injectable component rather than one code path's patch.
- A CSV column with no same-named field in the current schema is a new field and keeps today's defaults (`perTurn` absent ⇒ shared).
- The component builds new `FieldDefinitionDto` instances and neither mutates nor returns the dataset schema objects it reads. (Today's `applyScopeFromDataset` calls `setPerTurn` on the freshly-built list it is handed, so nothing is corrupted right now; the invariant is stated so the builder cannot later be pointed at a shared list.)
- **Only `perTurn` is carried forward.** `required`/`displayName`/`description` are also lost by the same method — a real but separate defect, deliberately out of scope here (see Non-goals).

### 2. Preview is turn-blind — the false 409 warnings

`preview` parses `turnIndex` into `ParsedRow` and then ignores it: `seenNames` is keyed on name alone, so every turn row after the first is flagged as a within-CSV duplicate (the exact warning in the issue); `totalRows` counts rows; `sampleRows` is one entry per turn row with per-turn and shared columns flattened into `data` and `multiTurnData` never set; and the multi-turn checks import *will* apply (duplicate `turnIndex`, non-contiguous name, shared-column conflict) live only in `processRun`/`validateRunAsMultiTurn`.

- Extract import's contiguous-run grouping and multi-turn assembly/validation into injectable components consumed by **both** `preview` and `importCsv`. Preview keeping a divergent copy of this logic is the defect; one implementation is the fix.
- Preview reports **per assembled test case**. Crucially *run ≠ test case*: a run whose rows carry a `turnIndex` is one multi-turn case, but K adjacent rows sharing a name with a **blank** `turnIndex` are still K separate test cases (today's behavior, pinned by `CsvImportModeFunctionalTests.skipStrategyWithinCsvDupFirstWins`). Duplicate/collision detection therefore keys once per multi-turn run and once **per row** of a single-turn run.
- Multi-turn sample rows carry `multiTurnData`; preview surfaces the same duplicate-`turnIndex` / non-contiguous-name / shared-column-conflict warnings import produces, anchored to the run's first CSV row number (matching import).
- Preview's memory profile is bounded by the largest single run, exactly as `importCsv` already is, on top of the per-name list preview already retains for collision detection (`allCsvNames`/`seenNames`, O(rows) today and unchanged here).
- **API**: `CsvImportPreviewDto.totalRows` keeps its meaning (CSV data rows parsed); a new `totalTestCases` field reports how many test cases the CSV assembles into. Additive — for a single-turn CSV no pre-existing field changes value and `totalTestCases == totalRows`. `sampleRows` granularity does change for multi-turn CSVs; that is the fix, and it is shape-compatible (`TestCaseResponseDto` already carries `multiTurnData`).

### 3. Post-persist fixup ignores `multiTurnData`

`fixupTestCases` deserializes and coerces only `tc.getData()`. For the canonical multi-turn case — every field per-turn, so `data` is `{}` — no changed column is ever found and the pass is **inert**: per-turn values are never coerced to the newly inferred schema types at all. When a multi-turn case does have shared columns and one of them changes, the pass then re-validates the row with the single-turn `validateTestCase(data, finalSchema, …)` against the *full* schema, giving it wrong validity and wrong warnings.

- The fixup coerces per-turn maps as well as shared `data` — and its change detection widens to cover them, so the pass stops being inert for turn-only cases — and re-validates a row carrying `multiTurnData` via `TestCaseValidationService.validateMultiTurn` (which takes the full schema and splits it by scope internally), persisting the updated `multi_turn_data` through the existing `batchUpdate`, which already writes that column. Being a recomputation pass, it carries forward the stored `SOURCE_CONFLICT` warnings per §4.
- **Data-safety guard**: `ValidationWarningsSerializer.deserializeTurns` returns `null` on a parse error (documented graceful degradation for *read* paths). On this write path that is destructive — `null` → `serializeTurns(null)` → `batchUpdate` sets `MULTI_TURN_DATA = NULL`, converting a multi-turn case to single-turn and destroying every turn. A row whose `multi_turn_data` is non-null but deserializes to `null` SHALL be skipped entirely (never written back) and logged at WARN with the exception as the last SLF4J argument.

### 4. Every pass that recomputes a verdict erases the import's conflict findings

`importCsv` calls `RevalidationService.startDatasetRevalidation(datasetId)` whenever it persists a schema — i.e. on every OVERRIDE import. That method self-invokes its own `@Async` method, so Spring's proxy never intercepts it and Phase 1 runs **synchronously inside the import transaction**. Phase 1 re-validates every case from its shared `data` against the whole schema (`validateTestCase`), never looking at `multiTurnData`, and writes through `updateValidationIfUnchanged` — whose guard passes, because the row it re-reads is the one this request just wrote.

Measured on this branch: importing `dup,0,a` / `dup,0,b` (duplicate `turnIndex`) returns `invalidCount=1` in the response, yet the persisted case is `valid=true`, `validationWarnings=null`. **The multi-turn conflict the import detected is erased before the response is sent**, making the existing spec scenario *"a conflict warning is reported and the case is invalidated"* false in the database.

The important part is *why* it cannot be fixed by validating better. A CSV-shape conflict describes the submitted **rows**, not the stored case: `dup,0,a` / `dup,0,b` assembles to `multiTurnData=[{prompt:a},{prompt:b}]`, `data={}` — a perfectly well-formed two-turn case. The duplicated `0` was read off the CSV and is stored nowhere; a shared-column mismatch is collapsed because assembly keeps only the first row's shared map; non-contiguity lives in a per-request set. **Any** pass that re-derives validity from stored state alone returns `valid=true, warnings=[]`, no matter how correct it is — and there are two such passes inside a single import request (`fixupTestCases`, then Phase 1), plus Phase 1 again on every later dataset schema PUT. Fixing them one at a time reproduces the defect in the next pass.

So this change states the rule once:

- **Import-derived conflict warnings are durable.** The two conflicts `validateRunAsMultiTurn` folds into the case's persisted verdict — duplicate `turnIndex`, and shared-column mismatch across turn rows — are persisted with a distinguishing code — a new `ValidationWarningCode.SOURCE_CONFLICT` — that marks them as derived from the import source rather than from stored data. Any pass that **recomputes** a case's validity without receiving new user-authored content SHALL carry forward the stored `SOURCE_CONFLICT` warnings and SHALL keep the case invalid while any remain. That covers `fixupTestCases` and revalidation Phase 1 with one rule and no per-pass exception.
- Direct API writes (`PUT`/`PATCH` of a test case) are **not** recomputation — the user supplied new content — so they clear these warnings as they do today. No change there.
- Non-contiguity is deliberately **not** made durable. It is emitted in `processRun` as a response-only `CsvImportWarningDto`, never enters the case's `ValidationResult`, and by definition describes a *second* run of a name that already exists — which under `conflictStrategy=FAIL` 409s the request and under `SKIP` is not persisted at all. There is no stored case for the warning to live on, so it stays request-scoped, exactly as today.
- **Revalidation Phase 1 is also genuinely multi-turn-blind**, independently of CSV import: it never coerces or validates turn contents, so a type-invalid per-turn value is silently marked valid, on the dataset-schema-PUT trigger too. Phase 1 SHALL branch on a stored turn array: coerce the values inside each turn as well as shared `data`, validate via `validateMultiTurn` (which takes the full schema and splits it by scope itself), and persist the turn array under the same `updated_at` guard. `TestCaseRepository` has no guarded update that writes `multi_turn_data` (`updateDataIfUnchanged` writes `data` only), so one is added.
- The unreadable-turn-array guard RC3 defines applies to Phase 1 too — the wider blast radius of the two, since Phase 1 runs on every schema PUT. Distinguishing "absent" from "unreadable" needs a throwing read, so `ValidationWarningsSerializer` gains a strict `deserializeTurnsStrict`; its existing lenient `deserializeTurns` and every current caller are untouched.
- The `@Async` self-invocation is left exactly as it is — orthogonal, load-bearing for current transactional behavior, and changing it would alter when every revalidation runs.

### Non-goals

- **ZIP export/import** — `ZipExportService`/`ZipImportService` are untouched, tracked as a separate deferred change. (`previewZip`/`importZip` delegate to `CsvImportService` and inherit these fixes; that inheritance is not asserted here.)
- **`DatasetCloneService.cloneRowAndTestCases`** — it rebuilds each cloned case without `.multiTurnData(...)`, so `batchInsert` writes `multi_turn_data = NULL` and cloning a dataset (or a suite, and therefore `eval-cli clone`) silently converts every multi-turn case to single-turn while copying a schema that still says `perTurn: true`. Same class of defect as #120, on a path this change does not touch; tracked separately alongside the ZIP work, not fixed here.
- **`CsvExportService`** — its turn multiplication (one row per turn, `turnIndex` `0..N-1`, shared columns repeated) is correct and is the reference the import side round-trips against. Note it derives its column set solely from the dataset schema, so a key held by a case but absent from the schema is omitted from the export; that is why the round-trip guarantee below is scoped to datasets whose schema declares every field the case carries. Not changed here.
- **The `@Async` self-invocation in `RevalidationService.startDatasetRevalidation`** — Phase 1 running synchronously inside the import transaction is left exactly as it is; only its multi-turn blindness is fixed.
- **Widening schema carry-forward beyond `perTurn`** — `required`/`displayName`/`description` are lost by the same method and merit their own change with its own scenarios; carrying them here would silently change validation strictness dataset-wide.
- **Blank-cell round-trip fidelity** — `CsvCellParser.parseCell` returns `""` (never `null`), so an exported blank returns as an empty string and can warn on a non-STRING field. Changing that contract affects every cell of every CSV import and contradicts existing `test-cases` scenarios. Known limitation, not fixed.
- **Type inference itself** — a field's `type` is still (re)derived from CSV values.
- No DB schema change, no Flyway migration, no new configuration property, no security impact.

**Status**: everything here corrects behavior that exists in code today. Note the `test-cases` requirement *Schema-change revalidation auto-coerces test case data* is still marked `Status: **Planned**` and scopes Phase 1 to a dataset schema PUT, although the code also runs it from CSV import; that stale tier/trigger is not re-tiered here — the new multi-turn requirement is added to `multi-turn-test-case` and states the CSV-import trigger explicitly.

Rollout note, not a requirement.

**Risks**
- **Collapsing same-named single-turn rows into one case** while keying detection per case — highest-risk regression: it would delete the duplicate warning and under-count `totalTestCases` while N cases are written. Mitigated by the explicit run ≠ test case rule plus a new adjacent-identical-names preview test (the existing `DupRow`/`duprow` test uses names that differ in case, so run grouping splits them and it cannot catch this).
- **Emitting new non-contiguity warnings for single-turn runs** — today's `completedMultiTurnNames` tracker is populated only in the multi-turn branch. The grouper must track non-contiguity for multi-turn runs only, or `CsvImportModeFunctionalTests` gains unspecified warnings.
- Preview's per-case grouping changes numbers/warnings clients already display for multi-turn CSVs. Mitigated by keeping `totalRows` untouched and leaving single-turn responses additive-only.
- Sharing the assembler between preview and import means a defect there surfaces in both. Mitigated by unit tests on the components plus functional tests on both endpoints.
- **Touching `RevalidationService` affects every revalidation trigger, not just CSV import** (dataset schema PUT also drives it). Mitigated by branching strictly on the presence of a stored turn array and by making warning carry-forward a no-op when no `SOURCE_CONFLICT` warning is stored — which is every single-turn case today. `RevalidationServiceTest` constructs the service positionally and gains one argument; that edit is an explicit task, not an accident.
- **Validating turn contents exposes orphan per-turn keys.** Removing a field from a dataset schema prunes it from `data` only (`removeDataFields` → `UPDATE … SET data = data - $1`); `multi_turn_data` keeps the key. Today Phase 1 ignores turns so nothing notices; once it validates them, every affected multi-turn case turns invalid with an unknown-field warning per turn. So the prune is widened to `multi_turn_data` in the same change. It reaches only fields actually removed from a schema — that is the case it fixes.
- **A dataset already corrupted by this bug is reported invalid until its schema is repaired.** With `perTurn` stripped, no field is per-turn, so turn validation reports every turn key as unknown: from the first revalidation after deploy, such a dataset's multi-turn cases carry one warning per turn key per turn and are marked invalid. Restoring the `perTurn` flags with a PATCH clears it on the next revalidation. Accepted rather than mitigated — the warnings truthfully describe what the stored schema now says, and these datasets already need their original CSV re-imported to recover their lost turns.
- **A stale `SOURCE_CONFLICT` warning could outlive the problem it describes** — it survives every recomputation until the case is written by a direct API call or re-imported. That is the intended lifetime (the case really was authored from conflicting rows, and nothing in the stored data can prove otherwise), but it means a user must edit or re-import to clear it. Stated explicitly in the spec rather than left implicit.
- **Re-serializing turn maps drops explicit JSON nulls** — the shared `ObjectMapper` uses `NON_NULL` content inclusion, so a per-turn key whose value is an explicit null disappears when the fixup rewrites the array. Pre-existing on the import write path (`serializeTurns` in `toMultiTurnEntity`), inherited not introduced; accepted, with a key-set assertion so it cannot silently widen.

**Rollout / test plan**
- No feature flag, no migration, no config: code-only, deployable in one step.
- Unit tests for the new components: `perTurn` carry-forward on rebuild and merge, new-column defaults, no mutation of the input schema; run grouping, single-turn passthrough, turn ordering, duplicate `turnIndex`, multi-turn-only non-contiguity, shared-column conflict; fixup branch selection including the unreadable-turn-array skip.
- Extend `CsvImportServiceSchemaTest` for the four schema-building paths. It constructs `CsvImportService` positionally and its `validateTestCase` stub is strict, so new constructor args must be threaded through and any test whose CSV becomes multi-turn needs `validateMultiTurn` stubbed.
- Functional tests: persisted-schema `perTurn` survives OVERRIDE; **import the same exported CSV twice** (OVERRIDE) asserting identical turns after both, and the same for APPEND/MERGE with `conflictStrategy=OVERRIDE` (the other modes the round-trip guarantee covers); multi-turn preview emits no within-CSV duplicate warnings and returns assembled samples with `multiTurnData` and `totalTestCases`; adjacent identical single-turn names still warn with `totalTestCases == totalRows`; predicted multi-turn conflicts; a multi-turn run does not collide with itself under `FAIL`/`SKIP`/`OVERRIDE` on **import**; fixup over a multi-turn case; and the persisted multi-turn `isValid`/`validationWarnings` survive the in-request revalidation (the `dup,0,a`/`dup,0,b` case must stay invalid). `MultiTurnCsvFunctionalTests` has no `previewCsv` helper yet — add one.
- Regression: `CsvImportModeFunctionalTests` must pass **unchanged**, then `./gradlew spotlessApply`, `./gradlew checkstyleMain checkstyleTest`, `./gradlew clean build`.
