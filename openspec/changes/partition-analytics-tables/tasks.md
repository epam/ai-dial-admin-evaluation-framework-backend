## 7. Functional tests for partitioned read paths

- [x] 7.1 Add a `PostgresFunctionalTests` nested test class seeding `test_case_run_results`/`test_case_eval_summaries`/`test_case_eval_scores` rows spanning three UTC months and asserting the full REST cursor-pagination chain returns an ordered, gap-free, duplicate-free sequence across partition boundaries, including correct `hasMore`/`nextCursor` at a page boundary that coincides with a partition boundary, and that scores are correctly joined at every point. Implemented as two tests: `test_case_run_results` (suite-scoped, unconstrained by a single run's `created_at_ms`, so one query naturally spans 3 partitions with page boundaries aligned to partition boundaries) and a per-partition eval-summaries+scores JOIN correctness check across 3 separate runs (its REST API mandates single-run scoping, so a single query cannot itself span partitions — verified per-partition instead).
- [x] 7.2 Add a nested test class verifying `AnalyticsPartitionMaintenanceService.ensureFuturePartitions()` creates the expected partition set idempotently across all three tables and that each created partition inherits all secondary indexes plus the PK/unique constraint. Uncovered and fixed a real bug: the existence check was name-only, but the current UTC month has no dedicated partition at all (it's covered by `_p_legacy`) until that legacy partition is eventually pruned — a name-only check would try to `CREATE ... PARTITION OF` a range overlapping `_p_legacy` and fail in production on the very first real maintenance run after every deployment. Fixed to check range coverage against all non-DEFAULT partitions instead of an exact name match.
- [x] 7.3 Add a nested test class verifying retention removal always acts on a `test_case_eval_summaries` partition and its paired `test_case_eval_scores` partition together: both dropped (rows gone from both) when `archive-instead-of-drop=false`, both left as readable detached tables when `true`, with an adjacent month's partitions in both tables left intact either way. Implemented via a `ScopedPartitionRepository` test decorator that only ever reports synthetic, dedicated far-future partitions to the service under test — the shared functional-test schema's real `_p_legacy`/look-ahead partitions (which other tests' fixtures rely on) are never visible to it and can never be touched, however far the test's fixed `Clock` is advanced.
- [x] 7.4 Add a nested test class verifying a write with an out-of-range `created_at_ms` lands in `_p_default` and is readable via the existing list endpoint, for all three tables. Implemented as two tests: a `test_case_run_results` row and a paired `test_case_eval_summaries`/`test_case_eval_scores` row, both far-future-dated, verified to land in `_p_default` (via row counts) and to be fully readable/correct through the real REST list endpoints.
- [x] 7.5 Extend `JooqSchemaDriftTest` to assert no partition-child relation (matching the naming convention, for any of the three tables) leaks into the generated `analytics.Tables` set.
- [x] 7.6 Add one advisory `EXPLAIN`-based test confirming a run-scoped query (`created_at_ms = runCreatedAtMs`) touches at most one dated partition plus the default, using a containment assertion rather than exact plan-string matching.

**Additional bug found and fixed during this task group**: the migration's month-boundary arithmetic used `timestamptz + interval 'N months'`, which Postgres evaluates using the connection's session timezone (not pure UTC) — on a non-UTC session timezone, this silently shifted computed month boundaries by an hour across a DST transition (caught by an exact-bounds assertion in the 7.2 test, off by exactly 3600 seconds at a Nov/Dec boundary). Fixed by doing all month arithmetic on naive (`timestamp without time zone`) values with no attached zone, converting to `timestamptz`/epoch-millis only at the final extraction point. See `design.md` D3.
