## Context

Issue #32 asks for scheduled suite runs. DIAL Core provides a scheduler application (`public/dial_scheduler__1.0.0`) reachable at `{DIAL_URL}/v1/deployments/applications/{appId}/route/v1/schedules/...` (API: `scheduler-openapi.json` in the project root; Postman collection in `postman-scheduler/`). It fires an HTTP call on a cron using credentials registered under a `service_id`. Existing EF pieces reused: `POST /api/v1/test-suites/{id}/runs` (`TestSuiteRunService.createRun`), `dialCoreRestClient` plus `callerCredentialInterceptor`, `DialCoreClientException` handling.

Facts from `scheduler-openapi.json` that shape the design:

- Endpoints under `/v1/schedules`: `POST /` (201), `GET /` (paged), `GET|PUT|DELETE /{id}` (delete 204, soft), `POST /{id}/pause|resume` (return full `ScheduleResponse`), `GET /{id}/runs[/{runId}]`. (`POST /{id}/run` and `GET /v1/sign-in/status` exist but are out of scope.)
- `ScheduleRequest`: `display_name`, `service_id`, `description?`, `trigger {cron{fields{year,month,day,week,day_of_week,hour,minute,second}, start_date?, end_date?}}`, `timezone` (IANA, default `UTC`), `properties{target_type, method, url, payload, timeout, retry, ...}`, `metadata`.
- `ScheduleResponse` has no `paused` flag (only `next_run_time`, null when paused); `trigger`/`properties` are free-form objects. Timestamps are ISO date-time.
- The list is paged (`limit` default 20, `offset`) and its items omit `properties` and `metadata`, so a suite's schedules cannot be found through the scheduler alone.

Decisions taken with the user: EF persists a suite→schedule mapping table (reversing the earlier "no table" idea once the list limitation was found), callback URL from a new property, caller credential for now, `service_id` default `dial-native`, no run-now and no sign-in check.

## Goals / Non-Goals

**Goals:** manage cron schedules for suite runs through the scheduler; per-suite listing with EF paging; validate early; reuse existing auth, client and error handling; feature-flagged.

**Non-Goals:** per-schedule API key, concurrency policy, local fire history, run tagging, notifications, non-cron triggers (`crons`, `date`), run-now, sign-in check, cleaning up scheduler schedules when a suite is deleted.

## Decisions

1. **Mapping table, scheduler as source of truth.** Meta table `test_suite_schedules(schedule_id VARCHAR(255) PK, test_suite_id VARCHAR(36) NOT NULL FK→test_suites(id) ON DELETE CASCADE, created_by VARCHAR(255) NOT NULL, created_at BIGINT NOT NULL)` plus index on `test_suite_id`, in `V1.39__CreateTestSuiteSchedulesTable.sql` (follow `V1.32` conventions: epoch-millis `BIGINT`, `VARCHAR(36)` UUIDs). Only the link and audit data are stored; cron, runConfig, state and history live in the scheduler. Model/RecordMapper/repository (`TestSuiteScheduleRepository` + `PostgresTestSuiteScheduleRepository`, `@Qualifier("metaDsl")`) follow the `run_metric_snapshots` template. `./gradlew generateJooq` output is committed; `docs/database-schema.md` is updated.
2. **Package `client.scheduler`.** `DialSchedulerClient` (`@Service @LogExecution`), scheduler DTOs (snake_case, `@JsonProperty`, unknown fields ignored), `SchedulerClientConfiguration` building `dialSchedulerRestClient` from `DialCoreProperties.baseUrl`, reusing the public static `callerCredentialInterceptor()` and `tracingInterceptor(...)` from `DialCoreClientConfiguration`. `SchedulerProperties` already lives in `configuration.properties.scheduler`. Conditional on `dial.scheduler.enabled`. `client.*` must not depend on `.service`/`.data`.
3. **No retry.** Scheduler writes are non-idempotent and `DialCoreClient.withRetry` is GET-oriented; the client calls `RestClient` directly. Errors: catch `RestClientResponseException`, rethrow `DialCoreClientException(status, message, body)` with the exception as the last log argument.
4. **URI building.** `appId` contains `/`; build the path with `UriComponentsBuilder` using `pathSegment` per `/`-split part so it is not percent-encoded; the collection endpoint keeps its trailing slash (`.../schedules/`).
5. **Service split.** `TestSuiteScheduleService` (`service.domain`, `@LogExecution`, `@ConditionalOnProperty`) orchestrates; it never holds a DB transaction across an HTTP call. `ScheduleRequestBuilder` (injectable `@Component`) builds the scheduler body from DTO + suite id using `ObjectNode`; `ScheduleCronMapper` converts cron DTO ↔ `trigger.cron.fields`. Suite existence via `TestSuiteService`; the mapping table via its own `TestSuiteScheduleRepository` (a domain service depends only on its own repository). `runConfig` is validated with the same validators `createRun` uses; if they are private to `TestSuiteRunService`, extract an injectable `RunConfigValidator` used by both. Repository writes are single statements and take `createdAt` from the injected `Clock`.
6. **Flows.**
   - *Create:* validate suite + runConfig + cron → scheduler POST → insert mapping row. If the insert fails, best-effort scheduler DELETE (log WARN with the exception as last argument) and rethrow.
   - *List per suite:* page the mapping rows (`PageRequest`, `PaginationParamResolver` in the controller, `Page<T>`), then GET each schedule from the scheduler. A scheduler 404 for a mapped id is skipped and logged (externally deleted); other errors propagate.
   - *Get/edit/pause/resume/runs:* look up the mapping row first (404 if absent); edit rebuilds `properties` for the stored suite id, which never changes.
   - *Delete:* scheduler DELETE (a 404 is tolerated) → delete mapping row.
7. **Controller.** `TestSuiteScheduleController` (`web.controller`, `@Validated`, OpenAPI, `@ConditionalOnProperty`). Routes: `/api/v1/test-suites/{suiteId}/schedules` (POST, GET) and `/api/v1/schedules/{scheduleId}` (GET, PUT, DELETE, `/pause`, `/resume`, `/runs`). The list takes `page`/`size` only (no `filter`/`sort`), so it needs a registry entry in `OpenApiQueryParamCustomizer` for pagination docs. Examples in `src/main/resources/openapi/examples/` named per registered path.
8. **DTO contract.** Request: `name`, `description?`, `cron {minute,hour,day,month,dayOfWeek,...}` (at least one non-blank), `timezone?` (IANA, validated with `ZoneId.of`, default `UTC`), `runConfig` (`RunConfigDto`). Response: `id`, `name`, `testSuiteId`, `cron`, `timezone`, `runConfig`, `paused`, `nextRunTime`, `createdBy`, `createdAt`, `updatedAt` (epoch ms `Long`; scheduler ISO timestamps converted by the mapper). `paused` = `next_run_time == null` (documented approximation: also true for an expired `end_date`). `runConfig` is read back from `properties.payload.runConfig`.
9. **Callback auth.** At fire time the scheduler calls EF with the credential it holds for `service_id` (`dial-native`). EF validates it with the existing OIDC/API-key filters; no new security code. Documented as a prerequisite.
10. **Error handling.** Scheduler errors propagate via `DialCoreClientException` → `DefaultExceptionHandler`. Local-state inconsistencies are reconciled lazily (skipped on list, tolerated on delete), never silently hidden on write paths.
11. **Run tagging with a column, not a join table.** `test_suite_runs.schedule_id VARCHAR(255)` is nullable with **no FK** and a partial index. The issue requires scheduled runs to be *listed, filtered and audited* by schedule. The Query DSL `test_suite_runs` entity builds its fields from the generated table's plain columns, so the column is filterable there with no extra wiring, and the response DTO returns it. The simple REST list (`GET /api/v1/test-suite-runs`) deliberately gets **no** `scheduleId` filter: its string `eq`/`ne` operators are case-insensitive (`lower(column)`, which bypasses the index) and `ne` is not null-safe (it would drop every manual run), neither of which suits an opaque, nullable id. A join table would serve only "runs of schedule X" and would need new subquery-filter machinery plus per-row enrichment. No FK keeps the tag for audit after the schedule is deleted. "Runs of schedule X" needs no new endpoint: clients query the `test_suite_runs` entity with an `eq` on `schedule_id`. *Alternative considered:* a `test_suite_schedule_runs` join table (less change to the run entity, but cannot filter the global list).
12. **Tagging channel: `scheduleRef` query parameter.** The callback URL becomes `.../api/v1/test-suites/{id}/runs?scheduleRef=<uuid>`. The scheduler calls `properties.url` as given, so the parameter is certain to arrive; `extra_headers` exists in the scheduler API but is not verified to be applied to REST fires, so it is not relied on. The value is an **EF-generated ref** (stored in `test_suite_schedules.schedule_ref`), not the scheduler's id: that id does not exist until create returns, so using it would need create-then-PUT (two writes and a window where an early fire is untagged). The run stores the real schedule id, resolved from the ref. `ScheduleRequestBuilder` generates the ref on create; edit reuses it; a schedule without a ref (created before tagging) gets one on its first edit.
13. **Honouring rule: never block a run.** `TestSuiteRunService.createRun(suiteId, runConfig, scheduleRef)` asks a small schedule-domain resolver service (own repository only, no dependency on the run service, so no cycle) for the schedule id of `(scheduleRef, suiteId)`. Unknown, blank or other-suite refs are ignored with a warning and the run is created untagged. Resolution and the run insert share the existing `@Transactional("metaTransactionManager")`. Any authenticated caller can pass a `scheduleRef`; the suite match limits spoofing to mislabelling a run within a suite the caller can already run.
14. **Scheduled run naming.** For a scheduled (tagged) run, a provided `testRunName` becomes `"<testRunName> #<seq>"` using the existing `nextRunNameSequenceValue()`; the base is truncated so the result fits 255 characters. A blank name stays `Run #<n>`. Manual runs and the import path are unchanged, so a duplicate manual name is still a 409. This fixes the guaranteed second-fire failure caused by the unique `(test_suite_id, test_run_name)`.
15. **Link a fire to its run through the fire's recorded response.** The scheduler stores the target's response in the fire detail (`GET .../runs/{runId}` -> `result`). For a real fire it is `{"body": <EF's 202 TestSuiteRunResponseDto>, "status_code": 202}`, so `result.body.id` is the EF run id. This is exact, needs nothing from the scheduler beyond what it already records, and avoids guessing by timestamps. A new `ScheduleFireRunExtractor` component reads it defensively: the run id is taken only when `status_code` is 2xx and `body.id` is a valid UUID; every other shape (null result, 4xx body, non-UUID id) yields no run id. *Alternatives rejected:* matching fires to runs by time (wrong for same-second fires and retries); asking the scheduler to send its fire id (static URL, no evidence it supports it).
16. **Status comes from EF, live.** The `status` inside the recorded body is the value at fire time (`PENDING`), so it is never shown. `testSuiteRunStatus` is read at request time from EF's own run table in one batched query (`TestSuiteRunRepository.findStatusesByIds`, exposed through `TestSuiteRunService`). A run that was deleted keeps its `testSuiteRunId` (it is what the fire created) and shows a null status. The schedule domain depends on the run service, and the run service depends only on `ScheduleRefResolver`, so there is no cycle.
17. **Cost control and failure isolation.** The fire list (`RunListItem`) has no `result`, so a page needs one detail call per fire. Only fires with status `success` can have produced a run, so only those are fetched; they are fetched with bounded concurrency (the caller's credential is propagated across threads with `TokenPropagationHelper`); finished fires (`success`, `error`, `missed`) never change, so their extracted run id is cached (Caffeine, as `ApiKeyCache` does), and `in_progress` fires are never cached. A failed detail call leaves that fire's run fields null and logs a warning with the exception, and never fails the page: the data is re-derivable on the next request.

Component flow: Controller → `TestSuiteScheduleService` (suite check, validation, build request) → `DialSchedulerClient` → DIAL Core → scheduler app; mapping rows via `TestSuiteScheduleRepository`; later scheduler → EF `POST /runs`.

## Risks / Trade-offs

- [Suite deleted → schedule keeps firing into 404] → the mapping row cascades away, the schedule remains in the scheduler; documented, follow-up to delete schedules on suite deletion.
- [Create is not atomic across scheduler and DB] → compensating scheduler DELETE; residual orphan possible if both the insert and the compensation fail (logged).
- [List costs 1 + N scheduler GETs per page] → bounded by EF's page size (configured max); acceptable for expected volumes.
- [Callback credential not accepted by EF] → documented prerequisite; a stubbed-scheduler functional test only covers EF's side, so verify end-to-end in a DIAL environment.
- [`paused` derived from `next_run_time`] → documented; expose `nextRunTime` too so clients can see the raw value.
- [Caller's token expiring] → the scheduler stores its own credential per `service_id`; EF only forwards the caller's token for management calls.
- [Scheduler may not preserve the query string of `url`] → verify once on dev with a single schedule; the failure mode is untagged runs, never failed runs.
- [Spoofed or stale `scheduleRef`] → honoured only for a link row of the same suite, otherwise ignored with a warning.
- [Schedules created before tagging have no ref] → their runs stay untagged until the schedule is edited once.
- [Shared `TestSuiteRunResponseDto` gains a field] → nullable and omitted when null; `evaluation-runner-core` and `eval-cli` tests must pass.
- [`result` shape is only verified for a successful fire] → a 4xx or otherwise different body yields no run id instead of an error; the fire itself still shows its own status.
- [N detail calls per history page] → only successful fires, bounded concurrency, cache of finished fires; the page size still bounds the worst case.

## Migration Plan

Flyway meta `V1.39` creates the table (runs regardless of the feature flag; empty table is harmless). Deploy with the feature off; enable with `DIAL_SCHEDULER_ENABLED=true`, `SCHEDULER_CALLBACK_BASE_URL` and optionally `SCHEDULER_APP_ID`/`SCHEDULER_SERVICE_ID`. Rollback: disable the flag; schedules stay in the scheduler and can be removed there; the table can stay.
