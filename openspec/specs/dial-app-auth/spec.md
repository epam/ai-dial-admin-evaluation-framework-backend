# DIAL App Auth

## Purpose

Defines EF's integration as a DIAL Application via DIAL Application Routes. Covers the per-request key (PRK) lifecycle, eval execution trigger, SSE keepalive, and file auto-sharing to evaluated deployments. PRK-based deployment invocation and user identity resolution are **not new requirements** here — they are satisfied by EF's existing, credential-kind-agnostic `CallerCredential` propagation and DIAL API-Key auth chain, which this spec's requirements explicitly reuse rather than duplicate.

## Key Terms

- **per-request key (PRK)**: Ephemeral key generated by DIAL Core per HTTP request to an application or route. Lives for the duration of the request. Carries user identity, trace-id, and cost attribution. Grants access to DIAL models, applications, and auto-shared files. Represented in EF as an `API_KEY`-kind `CallerCredential` — the same type an end-user's own DIAL API key already uses.
- **`DialRouteTriggerClient`**: EF component that fires eval execution by calling DIAL Core's Application Route, maintaining the SSE connection open to keep the PRK alive.
- **`EvalExecuteInternalController`**: Spring controller at `/api/internal/runs/{runId}/execute`, authenticated by EF's existing DIAL API-Key auth chain, that receives DIAL Core's PRK-injected request, dispatches the existing eval job, and streams SSE back.
- **DIAL App mode**: Operational mode activated by `dial-app-proxy.enabled=true`. When active, a run is triggered via DIAL Core's Application Route (yielding a PRK) instead of being dispatched in-process directly from the public endpoint.

## Requirements

### Requirement: Feature flag controls DIAL App mode activation
The system SHALL support a configuration property `dial-app-proxy.enabled` (boolean, default `false`) that controls whether the DIAL App integration is active. When `false`, all existing JWT-based flows MUST remain unchanged. When `true`, DIAL App mode components are active. All DIAL App mode beans MUST be conditionally wired via `@ConditionalOnProperty(name = "dial-app-proxy.enabled", havingValue = "true")`. The system SHALL fail fast at startup if `dial-app-proxy.enabled=true` and `config.rest.security.api-key.enabled=false`, since the internal endpoint has no other authentication mechanism.

Status: **Implemented**

#### Scenario: DIAL App mode disabled by default
- **WHEN** the application starts without `dial-app-proxy.enabled` configured
- **THEN** JWT-based eval execution SHALL be used (existing `TokenPropagationHelper` path)
- **AND** no DIAL route trigger is attempted

#### Scenario: DIAL App mode enabled
- **WHEN** `dial-app-proxy.enabled=true`
- **THEN** eval runs SHALL be triggered via `DialRouteTriggerClient` (DIAL Application Route)
- **AND** `EvalExecuteInternalController` SHALL be active

#### Scenario: Startup fails without required API-Key auth
- **WHEN** `dial-app-proxy.enabled=true` and `config.rest.security.api-key.enabled=false`
- **THEN** the application SHALL fail to start with a clear `IllegalStateException` message naming both properties

### Requirement: DIAL Route trigger client
The system SHALL provide a `DialRouteTriggerClient` component (`client.dialcore`) that triggers eval execution via the DIAL Application Route. The client SHALL: (a) call `POST /v1/deployments/{deploymentName}/route/api/internal/runs/{runId}/execute` on DIAL Core using the user's JWT in the `Authorization` header; (b) maintain the SSE connection open by consuming the SSE stream from DIAL Core until the stream terminates; (c) run on a virtual thread (non-blocking for the REST response). `deploymentName` defaults to `EF` (configurable via `dial-app-proxy.deployment-name`).

Status: **Implemented**

#### Scenario: Trigger call dispatched asynchronously after run creation
- **WHEN** a new eval run record is created with DIAL App mode enabled
- **THEN** `DialRouteTriggerClient.triggerEvalRun(runId, jwt)` SHALL be called on a virtual thread
- **AND** the run-creation REST response SHALL be returned immediately (before trigger completes)

#### Scenario: Trigger call uses user JWT exactly once
- **WHEN** `DialRouteTriggerClient.triggerEvalRun(runId, jwt)` is called
- **THEN** the `jwt` value SHALL appear only in the `Authorization` header of the outbound DIAL Core call
- **AND** it SHALL NOT be stored, logged, or propagated further

#### Scenario: Trigger connection kept open via SSE consumption
- **WHEN** DIAL Core proxies the SSE stream from EF's internal endpoint back to `DialRouteTriggerClient`
- **THEN** `DialRouteTriggerClient` SHALL consume (read and discard) the SSE stream until stream close
- **AND** the HTTP connection SHALL remain open for the duration of eval execution

#### Scenario: Connection drop during eval
- **WHEN** the SSE stream from DIAL Core is interrupted (network error, DIAL Core restart)
- **THEN** `DialRouteTriggerClient` SHALL log a warning with the runId
- **AND** the eval execution in `EvalExecuteInternalController` SHALL detect the write failure and cancel the run

### Requirement: Internal eval execute endpoint
The system SHALL expose `POST /api/internal/runs/{runId}/execute` (Spring `@RestController`, no request body). This path SHALL be part of the same authenticated path set as `/api/v1/**` — it is NOT excluded from Spring Security's JWT/API-Key filter chain. The endpoint SHALL: look up the existing run (404 if not found); reject with 409 if a dispatch is already active for `runId`; capture the already-authenticated caller's `CallerCredential` (the PRK, as an `API_KEY`-kind credential) from `AuthorizationTokenHolder`; dispatch eval execution using the existing `TestSuiteEvaluationJob.dispatch(runId, credential, false)`; and return a streaming SSE response (`text/event-stream`).

Status: **Implemented**

#### Scenario: Endpoint triggers eval execution
- **WHEN** DIAL Core POSTs to `/api/internal/runs/{runId}/execute` with `Api-Key: <prk>` and the key is successfully authenticated by the existing API-Key auth chain
- **THEN** the endpoint SHALL dispatch eval execution for the given `runId` using the existing `TestSuiteEvaluationJob.dispatch` method with the PRK as the run's `CallerCredential`
- **AND** return HTTP 200 with `Content-Type: text/event-stream`

#### Scenario: Run not found
- **WHEN** the `runId` path parameter does not correspond to an existing run
- **THEN** the endpoint SHALL return HTTP 404 and NOT dispatch anything

#### Scenario: Unauthenticated request rejected by the existing security chain
- **WHEN** the request arrives without a valid `Api-Key` (or `Authorization`) that the existing security chain can authenticate
- **THEN** Spring Security SHALL reject the request with HTTP 401 before it reaches `EvalExecuteInternalController`

#### Scenario: Concurrent trigger for same runId rejected
- **WHEN** `EvalExecuteInternalController` receives a trigger for a `runId` that already has an active dispatch (`ActiveRunRegistry` handle already registered)
- **THEN** it SHALL return HTTP 409 (Conflict)

### Requirement: SSE heartbeat to maintain PRK liveness
The SSE stream returned by `EvalExecuteInternalController` SHALL emit a heartbeat event at a configurable interval (`dial-app-proxy.heartbeat-interval-ms`, default `30000`) to prevent DIAL Core's idle connection timeout from firing. The heartbeat format SHALL be `data: {}\n\n`. Progress and status-update events already produced by the existing `TestSuiteRunSseService` (via `notifyStatusUpdate`/`notifyProgress`, called from `TestSuiteEvaluationJob`/`PostgresResultBatchWriter`) MAY also be emitted on the same stream — no new progress-notification wiring is required in those classes.

Status: **Implemented**

#### Scenario: Heartbeat emitted within idle timeout window
- **WHEN** no eval progress event has been emitted within `heartbeat-interval-ms` milliseconds
- **THEN** a heartbeat SSE event SHALL be emitted on the stream

#### Scenario: Stream terminated on eval completion
- **WHEN** eval execution reaches a terminal state (completed, failed, cancelled)
- **THEN** the SSE stream SHALL complete/close, consistent with `TestSuiteRunSseService`'s existing emitter-completion behavior on terminal status updates

### Requirement: DIAL Core Application Route registration documentation
The system's `docs/configuration.md` SHALL document the required DIAL Core deployment configuration for EF: the Application Route definition (path pattern, upstream, `rewritePath`), the EF deployment name (`EF`), and the bucket access configuration granting EF's deployment access to the EF file bucket for DIAL Core's file auto-sharing chain.

Status: **Implemented**

#### Scenario: Documentation covers DIAL Core config
- **WHEN** an operator reads `docs/configuration.md`
- **THEN** they SHALL find the complete DIAL Core Application Route config block
- **AND** the EF bucket access registration instruction
- **AND** a note that withholding `/api/internal/runs/*/execute` from public ingress is a recommended defense-in-depth measure (authentication itself does not depend on it)

### Requirement: File auto-sharing to evaluated deployments
When EF App (running with PRK1) constructs a test case sub-request to an evaluated deployment that contains DIAL file references (format: `files/{bucket}/{path}`), DIAL Core SHALL automatically check EF's registered bucket access, and if granted, propagate read access to those files in the evaluated deployment's PRK2. EF SHALL use standard DIAL file URL format in test case request bodies to ensure DIAL Core's attachment scanner processes them.

Status: **Implemented**

#### Scenario: EF bucket files accessible to evaluated deployment
- **WHEN** EF (PRK1) sends a sub-request to an evaluated deployment containing `files/ef-bucket/suites/{suiteId}/input.csv` in the request body
- **AND** EF's DIAL Core deployment registration grants bucket access to `ef-bucket`
- **THEN** DIAL Core SHALL generate PRK2 for the evaluated deployment
- **AND** PRK2 SHALL have read access to `files/ef-bucket/suites/{suiteId}/input.csv`
- **AND** the evaluated deployment SHALL be able to fetch the file via DIAL Core file API

#### Scenario: File access denied if EF lacks bucket registration
- **WHEN** EF's DIAL Core deployment is NOT configured with bucket access
- **THEN** DIAL Core SHALL reject the sub-request with HTTP 403 (file not accessible)
